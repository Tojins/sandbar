# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm run build` — compile `src/` → `dist/` via `tsc` (also runs on `prepare`).
- `npm run check` — type-check only (`tsc --noEmit`). No lint tool is configured; this is the only static gate.
- `npm test` — run the Vitest suite (`vitest run`, non-watch).
- `npx vitest run src/plan-resolver.test.ts` — run a single test file. Add `-t "<name>"` to filter by test name.

Node ≥ 20 is required. The package is ESM (`"type": "module"`); imports inside `src/` use the `.js` extension even when the on-disk file is `.ts` (NodeNext resolution).

## What this package is

`@offergeist/sandbar` is a **library**, not a CLI. It exports `run(config: RunConfig)` from `src/index.ts`. A host repo wires it up by supplying its own `Containerfile`(s), env file, anchor docs (`CLAUDE.md`, `CONTEXT.md`, optional ADR dir), and a **gate stack** — the containers and steps that produce a verdict about a commit (`config.gateStack`, #24). The reviewer's coding standards ship built-in (`prompts/coding-standards.md`); a host may optionally extend them with its own `CODING_STANDARDS.md` (`config.codingStandardsPath`) but is not required to. Sandbar then drives an issue-tracker-driven (GitHub Issues via `gh`) coding-agent loop against that host.

## Architecture — the four-phase outer loop

The orchestrator (`src/run.ts`) cycles plan → execute → merge → finalise until an exit condition fires. Each phase has a dedicated module and the dataflow between them is intentionally narrow.

1. **Phase 1 — Plan** (`src/plan-resolver.ts`): purely deterministic. Lists GitHub issues labelled `ready-for-agent`, parses each body's `## Blocked by` section, and selects the top-K unblocked issues (default 3) sorted by issue number. No LLM involvement.

2. **Phase 2 — Inner loop** (`src/inner-loop.ts` + `src/inner-loop-machine.ts`): each planned issue runs in parallel (`Promise.allSettled`) inside its own agent sandbox + per-issue gate stack (a podman pod on a podman network). The issue worktree is prepared **before** the sandbox/stack pair starts (stack `mounts` bind-mount fixture files from it). The inner loop is ralph-style — up to `maxImplAttempts` (default 8) attempts in the **same** sandbox so commits accumulate on the issue branch.
   - All transitions live in a pure state machine (`inner-loop-machine.ts`); `inner-loop.ts` is I/O glue that executes the action the SM emits and feeds the result back as an event.
   - Per attempt: build 3-layer prompt → run implementer agent → parse `<promise>` token (`promise-parser.ts`) → if `COMPLETE` **and the worktree is clean**, run **gate-1** (the host's gate steps in the issue's stack, `gate-stack.ts`). `COMPLETE` over a dirty tree is re-prompted to commit instead — see the clean-tree invariant below. On gate-1 green, run the **reviewer** — strictly advisory, never commits — which emits `<verdict>APPROVED|CHANGES-REQUESTED</verdict>` (parsed by `verdict-parser.ts`). On `APPROVED` → `DONE`. On `CHANGES-REQUESTED`, the prose is stashed and the loop runs another implementer attempt with the prose surfaced in its prompt.
   - **Two orthogonal budgets.** Each implementer pass consumes one of `maxImplAttempts`; each reviewer pass consumes one of `maxReviewRounds` (default 5). Exhausting impl attempts → `NEEDS-HUMAN` (last gate trace). Exhausting review rounds → `NEEDS-HUMAN-REVIEW` (latest reviewer prose).
   - **HARD-ERROR is for infra failures only.** The SM never emits it; the runner wraps unhandled exceptions (setup, container) as HARD-ERROR so the outer-layer `decideAfterTerminal` can retry with a fresh sandbox (up to `HARD_ERROR_MAX_RETRIES = 2`).
   - **UI-prototype escalation (#21).** An implementer that judges the issue to imply non-trivial *user-visible* UI with no prototype in the issue emits `<promise>NEEDS-UI-PROTOTYPE</promise>` + a `<ui-impact>` block and terminates immediately — no gate, no reviewer, no retry. The judgment is the agent's alone (there is no deterministic detector, and it must fire before a diff exists); the prompt's tiebreak is "when unsure, escalate". Deliberately not guarded on zero commits: a late escalation beats a merged guess.
   - Terminals: `DONE | NEEDS-INFO | NEEDS-UI-PROTOTYPE | NEEDS-HUMAN | NEEDS-HUMAN-REVIEW | HARD-ERROR`.

3. **Phase 3 — Merge** (`src/merger.ts` + `src/resolve-loop.ts` + `src/merger-worktree.ts` + `src/forge-verify.ts`): procedural. Runs in a **dedicated ephemeral worktree** detached at `origin/<sourceBranch>` (`createMergerWorktree`), never the operator's primary checkout — so uncommitted operator edits can't be swept into a merge commit (issue #10). For each DONE branch in ascending issue order: capture `preMergeSha`, `git merge --no-ff`, then either succeed and push, or invoke the **agentic resolve loop** for conflict OR post-merge-gate-red. The resolve loop sees the bodies of all sibling issues in the cycle so it can reason about cross-branch intent collisions. On `<promise>ABANDON</promise>` or budget exhaustion, the merge is reverted to `preMergeSha` and the branch is skipped. The operator's local branch fast-forwards on their next pull.

   **How the cycle lands is `config.mergeMode` (#22).** `direct` (default) is a single `git push origin HEAD:<sourceBranch>` at the end. `verified` gives the forge the last word (`src/forge-verify.ts`): force-push the merge result to a scratch `integrationBranch`, poll **that sha's** check runs, and only green earns `git push origin <sha>:<sourceBranch>`. Red feeds the failing jobs' logs (capped at `MAX_FAILED_JOB_LOGS`, elision stated in the trace) to the resolve loop in `forge-red` mode; with `VERIFY_MAX_ROUNDS` rounds the loop gets at most `VERIFY_MAX_ROUNDS - 1` shots, since the last round's red is terminal. The loop's own local gate is then only a cheap pre-filter between expensive CI rounds, never the verdict. Cost is one CI run per cycle when green, up to `VERIFY_MAX_ROUNDS` otherwise — and a round is also consumed with no agent involvement when `origin/<sourceBranch>` moves and the result has to be re-merged.

   **Reading the checks is the whole safety argument, and six things independently break it** — each has been a real green-on-red: the listing must be **paginated** and cross-checked against `total_count`, counting **distinct run ids** (a truncated read of an all-green first page is not a verdict, so an incomplete listing is `pending`; and because the pages are unordered and fetched separately, a run can come back twice while another never does — counting rows would hit `total_count` with the red one unread. A missing `total_count` or run id throws rather than defaulting); supersession is per **(suite, name)**, never per name (two suites legitimately report the same job name, and collapsing them lets one suite's success erase another's failure); a green snapshot must **settle** across `GREEN_SETTLE_POLLS` identical polls (`workflow_run` chains and `fromJSON` matrices create checks *after* earlier ones conclude); `skipped` is **not** a pass (a job the `if:` guard skipped ran nothing); and an **unfinished check outside `requiredChecks` still holds the verdict up** — it will conclude, and it can conclude red, so skipping past it would make green mean "everything that had finished when I looked was fine". The forge also reports verdicts in a *second* place — the legacy commit-status API, which Buildkite/Jenkins/older deploy apps use and which creates no check run — so failing statuses are folded in as synthetic `status:<context>` runs. That fold is deliberately one-way: a failing status turns a verdict red, a pending one is never waited for (third-party integrations leave statuses pending forever), so it can never manufacture a green or a new way to hang. On top of those, `requiredChecks` is mandatory and non-empty — it is the floor of checks that must *exist*, the only way to distinguish "hasn't started" from "will never run". A check outside that list still sinks the cycle if it fails. And the exist/never-exist distinction is *acted on*: a required name still absent once every other check on the sha has concluded, held for the grace window, is `missing-required` and fatal — a name that doesn't match what the forge publishes (`test` vs `test (20.x)`) is the likeliest misconfiguration there is, and parking on it spends a full CI timeout every cycle.

   Verification failure is a **cycle-level** outcome (the forge judged the composed result; the red isn't attributable to one of several individually-gated merges), so the whole cycle resets to the sha the merger worktree started at, `merged` comes back empty, and every merged issue is skipped as `forge-unverified` with a comment naming the **verified sha** (not the scratch branch, which the next cycle overwrites) and saying it may not be the one at fault. The comment's lede is written from the *reason*: on `source-moved` the checks passed and the cycle lost a race, on `checks-timeout` nothing was rejected at all — telling an author their build failed when it went green sends them to read a passing log. If the resolve loop committed fixes during verification, the comment says those commits are being discarded — they live on the merge result, not on the issue branch. **Parked vs fatal is a judgment about whose failure it is:** checks that never conclude park (CI was slow); anything that is a property of the repo rather than of this cycle's code is `fatal`, because it recurs every cycle and parking would quietly convert the whole backlog to `agent-stuck`. Fatal covers: a sha the forge never builds at all; a required check name that never appears; a rejected integration push; a fast-forward refused while `origin/<sourceBranch>` turns out **not** to have moved (a successful re-merge that produces no commit proves the branch is where it was, so the refusal was branch protection, a hook, or a token without push access); and anything thrown out of the landing itself — an unreachable forge for `CHECK_POLL_MAX_CONSECUTIVE_ERRORS` polls, an unreadable response. All of them arrive as `MergerError` → loud halt, and `MergerError.partial` carries the tracker state already applied so Phase 4 still runs for those issues before the halt. That wrapping is load-bearing rather than decorative: verified landing runs *after* earlier issues in the cycle were commented and de-labelled, so a raw throw would leave them on no queue and under no handoff label. A fast-forward rejected because `origin/<sourceBranch>` genuinely moved mid-verification is neither: the composed result changed, so it is re-merged and **re-verified**, consuming a round. Landing is always a fast-forward of locally-authored commits, so `openPullRequest` changes attribution not at all — the PR is an audit/review handle the forge marks merged on its own (create-or-**update**: a PR surviving an earlier cycle is re-titled, never left describing issues it no longer contains).

4. **Phase 4 — Finalise** (`src/finalize.ts`): per-issue branch lifecycle (push/delete worktree + branch), bot-prefixed issue comments, label flips (`ready-for-agent` ↔ `needs-info`/`needs-human`/`ready-for-human`). The `needs-ui-prototype` input reuses the needs-info label (same human round-trip: supply the missing artifact, re-label) but pushes the branch **only** when the escalation arrived after commits — otherwise there is nothing to hand over and pushing would publish a ref identical to the source tip, so the empty branch is deleted instead. That delete escalates to `-D` only once `branchIsContainedInOrigin` confirms the branch holds nothing unpushed: `hasCommits` is per-sandbox-cycle, so a HARD-ERROR retry reports `false` while an earlier attempt's commits are still on the branch. **A `git branch -d` refusal is never on its own a licence to force** — it also fires when the local source branch merely trails origin. Pure orchestration via `FinalizeAdapter`; the real adapter shells out to `git`/`gh`. The `review-budget-exhausted` input pushes the branch and posts the **latest reviewer prose only** (not the per-round transcript — that stays in the run-log for offline diagnosis).

### Exit conditions (`src/exit-conditions.ts`)

The outer loop terminates on the first of:
- **plan-empty** → success (exit 0)
- **stuck-same-plan** — same plan as previous cycle AND 0 DONEs this cycle (exit 2)
- **stuck-zero-dones** — `MAX_CONSECUTIVE_ZERO_DONE_CYCLES = 2` (exit 2)
- **budget** — `issuesAttempted >= maxTotalIssues` (default 50, exit 3)

`MAX_ITERATIONS = 100` in `run.ts` is a defensive ceiling — the conditions above terminate first.

`SILENT_NOOP_RETRY_LIMIT = 2` caps per-issue retries when the resolve-loop reports `resolved` but HEAD did not advance (the "silent `git merge --abort`" failure mode). Under the cap, the branch is discarded and the issue stays `ready-for-agent` for the next cycle's planner.

## Key design constraints

- **Pure decision functions where possible.** The inner-loop state machine (`step`, `decideAfterTerminal`), `parsePromise`, `parseVerdict`, `renderReviewerSlot`, `resolvePlan`, `applyCycle`, `checkInvariants`, `finalizeOne` are all pure functions over their inputs. I/O wrappers (`fetchCandidates`, `realAdapter`, etc.) are thin shells around them. Add tests against the pure layer; don't mock `gh`/`git` if you can table-test the decision instead.
- **Adapters for I/O boundaries.** `MergerAdapter`, `FinalizeAdapter`, `ResolveAdapter` define the contract; tests use fakes, production uses `realAdapter(...)`. Don't reach for `execFile` from new code if there's an adapter slot. The *real* adapters are the blind spot in that scheme — a fake satisfies the contract no matter what argv the real one builds — so `realVerifyAdapter` takes an optional `exec` seam and its argv/parsing are table-tested (`forge-verify.test.ts`), with the git primitives exercised against actual repos in `forge-verify-git.test.ts`. Behaviour that git defines is asserted by running it, not by asserting the command string: does a non-ff push reject rather than clobber, does a failed merge leave `MERGE_HEAD` (and *where* — in a linked worktree it is under `.git/worktrees/<name>/`, which is why `isMergeInProgress` asks `git rev-parse --git-path` instead of stating a path), which stream does `git merge` write `CONFLICT` to (stdout, so a reason built from stderr alone loses it), and how much the scratch ref's `--force-with-lease` really protects (only against a write landing between the `ls-remote` and the push — it is read fresh each round, so anything already on the ref is overwritten. That is intended for a ref sandbar owns, and is why config confines `integrationBranch` to the `sandbar/` namespace). The gate stack gets the same treatment (#24): its argv builders (`containerRunArgs`, `podCreateArgs`, `stepExecArgs`, `mountSpec`, `parsePortBindings`) are pure and table-tested in `gate-stack.test.ts`, and what *podman* defines is asserted by running podman in `gate-stack-podman.test.ts` — that a connect to a published port succeeds with nothing listening (hence the settle window), and that a pod container running as root writes worktree files owned by the invoking user (hence dropping `--userns=keep-id` is survivable). That file skips itself when podman or its image is unavailable, resolved at **collection** time: a `runIf` flag set in `beforeAll` arrives too late and silently skips everything, which is a test file that passes by never running.
- **Per-issue isolation.** Every issue gets its own podman network (`sandbar-net-<id>`), pod (`sandbar-pod-<id>`) and containers (`sandbar-<id>-<name>`); the merge phase gets the same under `merger`. `cleanupOrphanContainers` sweeps stale prefixed resources at start and between cycles — **including pods**, which is not tidiness: a pod's infra container is named `<pod-id-prefix>-infra` (a podman hash) and matches no sandbar prefix, so a container-only sweep would leave the pod and its network alive forever. The naming prefixes are centralized in `src/naming.ts`, which also lists the legacy `sandcastle-*`/`sandcastle/*` prefixes the sweep/clean paths still recognize during the transition window.
- **Container runtime is podman.** Hard-coded `RUNTIME = "podman"` in `src/runtime.ts`; the agent sandbox uses the in-house `podman()` provider (`src/agent-sandbox.ts`), now constructed with an explicit `imageName: config.sandboxImage` rather than falling through to `defaultImageName(repoDir)` (which silently coupled the image to the host's *directory name*, #24 D7).
- **The gate stack is config-driven (#24).** `config.gateStack` (REQUIRED — what it takes to test this repo is repo identity, no preset) is `{containers, steps}`. A container carries image, `lifecycle`, env, image `args`, read-only `mounts`, `mountWorktree`, `hold`, `readiness` + `readinessTimeoutMs`, `postReadyCommands`. A step is `{name, in, command}` — argv `podman exec`'d in a named container. `resolveGateStack` validates all of it at resolve time (before the lock), because every one of those mistakes otherwise surfaces as an opaque podman error minutes in: unknown `step.in`, duplicate names, `hold` + `args`, a relative `mountWorktree`, a colon in a mount path, a NaN timeout, and **a stack where nothing mounts the worktree** — which would return the same verdict for every commit, green included.
  - **One pod, not an anchor chain.** Containers share a network namespace via `podman pod`, so the stack addresses itself as `127.0.0.1` and publishes nothing. The `--network container:<anchor>` pattern is a docker tax sandbar doesn't owe: the anchor owns the `--dns` flags and its removal destroys the namespace, so an anchor can never be a per-attempt container. The pod holds the #18 resolvers and survives every container's removal, so `anchor` never appears in sandbar's config.
  - **`lifecycle` decides whose failure a failed bringup is (D5).** `issue` containers depend only on image + env → infra → throws → HARD-ERROR → retry with a fresh stack. `attempt` containers mount the worktree and run branch code → **gate red**, with the container's log as the trace. Backwards, an agent that breaks the service bootstrap burns two fresh-stack retries reproducing the same failure and lands on NEEDS-HUMAN with an "environment" trace. Default is `attempt` — the safe side, since a container wrongly reused across attempts gates stale code.
  - **`--userns=keep-id` is impossible in a pod** (podman refuses to combine them) and `--user 1000:1000` maps to a *subuid*, not the invoking user. Container root under rootless podman maps to the invoking user, so an image behind `mountWorktree` must run as root **or** as the host uid. Enforced before the run by `checkWorktreeImageUids`, which resolves the uid **empirically** (`podman run --rm <img> id -u`) rather than parsing `.Config.User` — a non-numeric `USER agent` is exactly the case an inspect-based check skips and that then fails as a silent EACCES mid-gate. `config.images[].buildArgs` is the escape hatch for aligning a genuinely non-root image at build time.
  - **`tcp` readiness is probed from the host**, through a loopback-only `127.0.0.1::<port>` publish with a podman-assigned ephemeral host port (so concurrent stacks can't collide). Probing inside the namespace would need a shell and a socket tool in images sandbar doesn't control — and mail catchers and scratch-based services, the ones that most need a TCP probe, have neither. **A bare connect is a green-on-red**: the rootless port forwarder accepts at the host and asks the backend afterwards, so `connect` succeeds against a pod with nothing listening. The probe therefore requires the socket to stay open for `TCP_SETTLE_MS`; a dead backend and a mid-initialisation mariadb are both closed ~190ms after connect, a serving one is not. Pinned in `gate-stack-podman.test.ts`.
  - **A red gate carries every container's log tail** (D9) — when a browser step fails because the backend is 500ing, the diagnosis is in a container the step never touched. It rides in its own `GateResult.containerLogs` field rather than on `stderr`, and that separation is load-bearing: `summarizeGateFailure` collapses lines sharing a timeout signature, and a service log is full of near-identical lines, so folding them in would have it collapsing text that was never one test run. Callers summarize the step output, then append.
  - **`config.sandboxImage` is required**, and `config.images` (default `[{tag: sandboxImage, containerfile: "Containerfile"}]`) is what sandbar builds; `stdinContext` builds with no context at all. Every *other* referenced image must already be pulled — preflight refuses with the exact `podman pull` line rather than pulling, so no run does silent network work at startup.
- **A gate verdict is about a COMMIT, so the tree is asserted ≡ HEAD (#24 D1).** `dirtyWorktreePaths` (`git-ops.ts`) gates both entry points: the inner loop reads it after every implementer attempt and the SM routes `COMPLETE` + dirty to another attempt with "commit your work" (no stack bringup paid), and `stack.runGate()` re-checks it so gate-2 in the merger worktree is covered when the resolve agent leaves edits. Deliberately **refuse, not clean**: `git clean -fd` would delete exactly the set this reports — untracked, non-ignored files, overwhelmingly a forgotten `git add`. A materialized-commit tree was rejected too: build artifacts are gitignored and live *inside* the mounted tree, so a second tree costs a cold build every attempt (~768M of ext4 copying per issue for outdoor) for a verdict identical to the assert's. **Corollary on consumers:** a gate step must write only into gitignored paths, or its own exhaust is reported as uncommitted work every attempt until the budget dies.
- **Branch naming is load-bearing.** `sandbar/issue-<n>-<kebab-slug>` (prefix in `src/naming.ts`) — the preflight cleanup, orphan sweeper, and worktree path computation (`worktreePathFor`) all rely on this prefix. Don't change it casually.
- **Verified merge mode is about independence, not coverage (#22).** The local gate and the code under test share one process, one podman, one image cache, one env file and one author — nothing disagrees. CI is a second, differently-authored implementation of "does this work". So a coverage gap belongs in `gateStack.steps` (cheaper, per-attempt); `mergeMode: "verified"` exists for the thing expanding the gate can't buy. Its non-negotiable invariant: **no unknown verdict ever lands** — and "unknown" includes a partial read, an unsettled snapshot, a skipped job, an unfinished check nobody named, and a check that was never reported, not just a pending one. `integrationBranch` is a remote-only scratch ref (never a local branch: it is pushed as `HEAD:refs/heads/<b>` from the detached merger worktree, so the `refs/heads/sandbar/issue-*` glob the preflight cleanup uses can't reach it, and `resolveMergeMode` rejects a name inside that namespace). It must also *start* with `sandbar/`: the ref is force-pushed every round, so pointing it at a branch someone else uses would destroy that branch on cycle 1, and the lease is no defence against that.
- **Issue branches seed from `origin/<sourceBranch>`,** not local. The preflight emits a soft warning when local is ahead of origin because per-issue worktrees won't see unpushed work.
- **Single-instance lock.** `src/lock.ts` uses `proper-lockfile` plus a PID sidecar for stale-PID takeover. Don't try to run two sandbar processes against the same workdir.
- **Promise-token contract.** Agents signal state with a single `<promise>TOKEN</promise>` tag. Implementer: `COMPLETE` (which also means *the worktree is clean*) | `NEEDS-INFO` (paired with `<questions>`) | `NEEDS-UI-PROTOTYPE` (paired with `<ui-impact>`). Resolve-loop: `COMMITTED` | `ABANDON` (paired with `<reason>`). Anything else is a no-signal — the loop re-prompts. The orchestrator gates *between* attempts; the agent never decides "this is green".
- **Verdict-token contract.** The reviewer emits a single `<verdict>APPROVED|CHANGES-REQUESTED</verdict>` tag (parsed by `verdict-parser.ts`). Missing or malformed token defaults to `CHANGES-REQUESTED` — convergence relies on the bar being sharp, i.e. on the coding standards (the built-in `prompts/coding-standards.md`, plus any project `CODING_STANDARDS.md` that extends them) being precise enough to be deterministic, not on round-trip retries. The reviewer is read-only: prompt instructs it not to modify the branch, commit, push, or run gates.
- **Prompt prose lives in `prompts/*.md`, not in code.** `src/prompts.ts` loads templates and does `{{placeholder}}` substitution; `prompt.ts` and `resolve-loop.ts` load them into module-level consts at import and fill the placeholders. Keep substantive instructional prose in the markdown files; only structural scaffolding (headings, code-fence wrapping, data interpolation, which optional block to include) stays in TS. The `prompts/` dir sits beside `src/`/`dist/` so the same `../prompts` path resolves from both, and is shipped via package.json `files`.
- **Logs are append-only and unbuffered** (`src/logs.ts`). Crash-safe by construction; don't introduce in-memory buffering.

## When making changes

- **Strict TypeScript** — `strict`, `noUncheckedIndexedAccess`, `noImplicitOverride`. Array/Map lookups are `T | undefined`; handle accordingly.
- **`*.test.ts` files are excluded from `tsc`** (see `tsconfig.json`) but checked by `vitest`. The strict type-checking gate is on production code only.
- **Always import with `.js` extensions** even from `.ts` files — NodeNext resolution.
- Module headers (the long comments at the top of `src/*.ts`) are the authoritative architecture notes per module. Update them when behavior changes; future Claude reads them first.
