# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Read @AGENTS.md first. It holds the working rules that apply to every commit made
here (starting with: bump the version in the same commit), and it is shared with
the sandbar agents — `sandbar.config.mjs` names it as an anchor doc, so they get
an `@ref` to it directly rather than through this import. The rest of this file is
architecture.

## Commands

- `npm run build` — compile `src/` → `dist/` via `tsc` (also runs on `prepare`).
- `npm run check` — type-check only (`tsc --noEmit`). No lint tool is configured; this is the only static gate.
- `npm test` — run the Vitest suite (`vitest run`, non-watch).
- `npx vitest run src/plan-resolver.test.ts` — run a single test file. Add `-t "<name>"` to filter by test name.

**Whatever bounds a test run has to kill the process GROUP, not the pid (#25).** Vitest's fork pool runs each file in a separate *process*, so a worker that gets stuck — a spin, not a hang — outlives anything that kills only the top of the tree: it reparents to init, keeps burning a full core, and leaves nothing on screen to say it exists. Bare `timeout 90 npx vitest run <file>` is fine and was checked (GNU `timeout` puts the command in its own process group and signals the group), but two things reach for the pid alone and are what actually leaked: `timeout --foreground`, which is documented to signal only the child, and a Python harness's `subprocess.run(..., timeout=N)`, whose timeout path calls `Popen.kill()` on the direct child and abandons its descendants. From Python use `start_new_session=True` + `os.killpg`. After any run you interrupted, `ps -ef | grep [f]orks.js` is the check — a leftover there is measured in cores, not megabytes. The production-side half of this is in `forge-verify.ts`'s header: a poll's pacing and its deadline must come from the same clock, or a faked one turns the wait into exactly that spin.

Node ≥ 20 is required. The package is ESM (`"type": "module"`); imports inside `src/` use the `.js` extension even when the on-disk file is `.ts` (NodeNext resolution).

## What this package is

`@offergeist/sandbar` is a **library with a bin** (#38). `run(config: RunConfig)` is still the contract and `src/index.ts` is what a host imports; `src/cli.ts` → `dist/cli.js` is a thin wrapper that resolves `--config` (default `./sandbar.config.mjs`), dynamically imports it, and hands the default export to `run()`. The bin exists because being a *pure* library forced every consumer to author and commit its own runner, which is how a host repo ends up with a `sandbar/` directory beside its `.sandbar/` one. It is thin because `run()` already owns its exit codes and the SandbarError-vs-stack top-level handler; all the bin adds is that same treatment for throws that escape **before** that handler exists (chiefly `resolveConfig`'s validation, which fires before the lock) and the `cwd` default below. Since #45 it also dispatches one subcommand, `sandbar gate` → `runGateCommand` (exported from the package root alongside `run`, because a thin bin can do nothing an embedding host cannot) — which is a second thing the bin *runs*, not a second way to configure it: `--worktree` and `--keep` duplicate no `RunConfig` field, since a run derives the tree it gates from an issue branch and tears the stack down with the issue.

A host repo supplies one committed `sandbar.config.mjs` at its root, plus its own `Containerfile`(s), anchor docs (`CLAUDE.md`, `CONTEXT.md`, optional ADR dir), and a **gate stack** — the containers and steps that produce a verdict about a commit (`config.gateStack`, #24). The reviewer's coding standards ship built-in (`prompts/coding-standards.md`); a host may optionally extend them with its own `CODING_STANDARDS.md` (`config.codingStandardsPath`) but is not required to. Sandbar then drives an issue-tracker-driven (GitHub Issues via `gh`) coding-agent loop against that host.

**The config file is a PROGRAM, not data** — that is why it is imported rather than parsed. A computed image tag, a gate stack read from JSON, top-level await: all of it survives. `vite.config.js`-shaped, not `package.json`-shaped. Four constraints are decisions rather than drift: exactly one configuration-carrying flag (`--config`; `--help`/`--version` duplicate no config field, so they are not exceptions); **no** search up the directory tree (an ambiguous "which config did it find" is a run against the wrong repo); `.mjs` rather than `.ts`, since `engines` is node >= 20 and cannot import TypeScript without a loader; and the default export is the config **object**, not a factory — config files may use top-level await, so a factory buys nothing and would leave two shapes to guess between.

## Architecture — the four-phase outer loop

The orchestrator (`src/run.ts`) cycles plan → execute → merge → finalise until an exit condition fires. Each phase has a dedicated module and the dataflow between them is intentionally narrow.

1. **Phase 1 — Plan** (`src/plan-resolver.ts`): purely deterministic. Lists GitHub issues labelled `ready-for-agent`, parses each body's `## Blocked by` section, and selects the top-K unblocked issues (default 3) sorted by issue number. No LLM involvement.

2. **Phase 2 — Inner loop** (`src/inner-loop.ts` + `src/inner-loop-machine.ts`): each planned issue runs in parallel (`Promise.allSettled`) inside its own agent sandbox + per-issue gate stack (a podman pod on a podman network). The issue worktree is prepared **before** the sandbox/stack pair starts (stack `mounts` bind-mount fixture files from it). Since #44 the sandbox may also carry a **sandbox stack** — the `inSandbox` subset of the same gate-stack containers, in the agent container's own network namespace — brought up after the sandbox exists, because the siblings attach to it. The inner loop is ralph-style — up to `maxImplAttempts` (default 8) attempts in the **same** sandbox so commits accumulate on the issue branch.

   - All transitions live in a pure state machine (`inner-loop-machine.ts`); `inner-loop.ts` is I/O glue that executes the action the SM emits and feeds the result back as an event.
   - Per attempt: build 3-layer prompt → run implementer agent → parse `<promise>` token (`promise-parser.ts`) → if `COMPLETE` **and the worktree is clean and HEAD is still the issue branch**, run **gate-1** (the host's gate steps in the issue's stack, `gate-stack.ts`). `COMPLETE` over a dirty tree is re-prompted to commit instead, and a HEAD that has wandered off `refs/heads/<branch>` is re-prompted back onto it (once) — see the clean-tree and on-branch invariants below. On gate-1 green, run the **reviewer** — strictly advisory, never commits — which emits `<verdict>APPROVED|CHANGES-REQUESTED</verdict>` (parsed by `verdict-parser.ts`). On `APPROVED` → `DONE`. On `CHANGES-REQUESTED`, the prose is stashed and the loop runs another implementer attempt with the prose surfaced in its prompt.
   - **Two orthogonal budgets.** Each implementer pass consumes one of `maxImplAttempts`; each reviewer pass consumes one of `maxReviewRounds` (default 5). Exhausting impl attempts → `NEEDS-HUMAN` (last gate trace). Exhausting review rounds → `NEEDS-HUMAN-REVIEW` (latest reviewer prose).
   - **A reviewer that produced no review is not a verdict (#41).** The failure that named the issue: a reviewer emitted zero bytes for fifteen minutes, the idle timeout's error text was written into `reviewerStdout`, and the verdict parser turned it into `CHANGES-REQUESTED` — no token, so the safe default — which spent a review round, ended the attempt, and handed the next implementer a harness message as its entire feedback under a "Previous reviewer feedback" heading. The fail-safe direction was right and the bookkeeping was not: an unknown outcome must never read as APPROVED, but nothing licenses charging the issue for it or inventing a finding. `reviewer-run.ts` now owns the judgment and it turns on ONE question — did this invocation reach a verdict about the code? Completed with output, yes (a missing token is the parser's business, and the default-to-CHANGES-REQUESTED is a statement about the code). Failed but the partial output holds a `<verdict>` token, also yes — the run decided and then died on the way out, and calling that "the reviewer never ran" is the same fabrication facing the other way. Anything else, no; retried once, because a flake and a fault are told apart by trying again and the retry costs no budget. **That distinction is unimplementable unless the bytes survive the throw**, which is why `invokeAgent` now carries its collected output out on the rejection (`agentPartialOutput`, F9): before it, every failure was byte-identical to silence. The resulting `reviewer-harness-failed` event spends **no review round**, never touches `latestReviewerProse` (that string is what finalize shows a human), and re-prompts through the *orchestrator-note* slot with a note that quotes none of the harness detail — an implementer cannot act on an idle timeout from inside its sandbox, and an agent handed a failure it cannot fix will try anyway. **Every claim that note makes is scoped to the round**, which is the other half of not lying to an implementer: `latestReviewerProse` is carried forward untouched, so an earlier round's real report may still render directly above the note under "Address the reviewer's concerns" — a note saying there is no reviewer feedback above would be false in every harness failure past round 1, i.e. this issue's own bug moved one prompt slot over. So it says there is no *new* feedback, that anything above is an earlier round's and still stands, and what it means if nothing is above. It does spend an impl attempt, which is the accepted residual: re-dispatching the reviewer from the SM is an unbounded loop against a component that just failed twice, so the bound is the **second consecutive** failure, which terminates as `NEEDS-HUMAN cause: "reviewer-harness-failed"` — `reviewer-blocked` would send its reader to resolve a CHANGES-REQUESTED nobody wrote (#17, one terminal along). "Consecutive" means the attempt immediately before, so a real verdict or a gate red between two failures makes them two incidents. **The handoff comment is scoped the same way and for the same reason**, since that terminal is reachable with an earlier round's genuine CHANGES-REQUESTED behind it: it says *this round's* reviewer produced nothing rather than that no verdict was ever reached, and it **renders** that earlier report — under its own heading, described as an earlier round's and possibly unaddressed, never as the blocker. Dropping it would lose the only review the branch ever received exactly as the comment tells its reader to review the branch themselves; nothing else surfaces it, since the attempt logs are offline and this is not the `review-budget-exhausted` arm. With no such prose the stronger sentence is the true one and is kept.
   - **The idle timeout kills what it stops waiting for (#41).** It used to reject and nothing else, despite the comment above it calling it the "idle kill timer": the `podman exec` client, its pipes and the run's growing output buffer stayed alive for the rest of the ISSUE, since the sandbox is per-issue and nothing else was going to collect them. Both timer paths now abort the exec (`ExecOptions.signal` → `killOnAbort` → SIGKILL), the completion-grace one included — past the completion signal, whatever still holds the pipe is producing output nobody will read. Be precise about the reach: this kills the CLIENT. The process inside the container is podman's, and gate-stack's `reapKilledStep` records the same finding from the other side — the only total handle podman offers is the container itself, and here that handle belongs to the issue rather than to one agent run, so an idled agent process still dies with the sandbox and not before. `killOnAbort` is exported rather than inline because the provider needs a real podman and a real image, so anything left inside it is asserted by nothing (#42's argument for `sandboxRunArgs`); the end-to-end half rides on `agent-sandbox.test.ts`'s local fake provider, which wires the same helper.
   - **HARD-ERROR is for infra failures only.** The SM never emits it; the runner wraps unhandled exceptions (setup, container) as HARD-ERROR so the outer-layer `decideAfterTerminal` can retry with a fresh sandbox (up to `HARD_ERROR_MAX_RETRIES = 2`).
   - **UI-prototype escalation (#21).** An implementer that judges the issue to imply non-trivial *user-visible* UI with no prototype in the issue emits `<promise>NEEDS-UI-PROTOTYPE</promise>` + a `<ui-impact>` block and terminates immediately — no gate, no reviewer, no retry. The judgment is the agent's alone (there is no deterministic detector, and it must fire before a diff exists); the prompt's tiebreak is "when unsure, escalate". Deliberately not guarded on zero commits: a late escalation beats a merged guess.
   - Terminals: `DONE | NEEDS-INFO | NEEDS-UI-PROTOTYPE | NEEDS-HUMAN | NEEDS-HUMAN-REVIEW | HARD-ERROR`.

3. **Phase 3 — Merge** (`src/merger.ts` + `src/resolve-loop.ts` + `src/merger-worktree.ts` + `src/forge-verify.ts`): procedural. Runs in a **dedicated ephemeral worktree** detached at `origin/<sourceBranch>` (`createMergerWorktree`), never the operator's primary checkout — so uncommitted operator edits can't be swept into a merge commit (issue #10). Since #38 the worktree is registered in the bare cache, which makes that guarantee structural rather than procedural: the repo the merge runs in holds none of the operator's refs and no working tree of theirs. For each DONE branch in ascending issue order: capture `preMergeSha`, `git merge --no-ff`, then either succeed and push, or invoke the **agentic resolve loop** for conflict OR post-merge-gate-red. The resolve loop sees the bodies of all sibling issues in the cycle so it can reason about cross-branch intent collisions. On `<promise>ABANDON</promise>` or budget exhaustion, the merge is reverted to `preMergeSha` and the branch is skipped. The operator's local branch fast-forwards on their next pull.

   **How the cycle lands is `config.mergeMode` (#22).** `direct` (default) is a single `git push origin HEAD:<sourceBranch>` at the end. `verified` gives the forge the last word (`src/forge-verify.ts`): force-push the merge result to a scratch `integrationBranch`, poll **that sha's** check runs, and only green earns `git push origin <sha>:<sourceBranch>`. Red feeds the failing jobs' logs (capped at `MAX_FAILED_JOB_LOGS`, elision stated in the trace) to the resolve loop in `forge-red` mode; with `VERIFY_MAX_ROUNDS` rounds the loop gets at most `VERIFY_MAX_ROUNDS - 1` shots, since the last round's red is terminal. The loop's own local gate is then only a cheap pre-filter between expensive CI rounds, never the verdict. Cost is one CI run per cycle when green, up to `VERIFY_MAX_ROUNDS` otherwise — and a round is also consumed with no agent involvement when `origin/<sourceBranch>` moves and the result has to be re-merged.

   **Reading the checks is the whole safety argument, and six things independently break it** — each has been a real green-on-red: the listing must be **paginated** and cross-checked against `total_count`, counting **distinct run ids** (a truncated read of an all-green first page is not a verdict, so an incomplete listing is `pending`; and because the pages are unordered and fetched separately, a run can come back twice while another never does — counting rows would hit `total_count` with the red one unread. A missing `total_count` or run id throws rather than defaulting); supersession is per **(suite, name)**, never per name (two suites legitimately report the same job name, and collapsing them lets one suite's success erase another's failure); a green snapshot must **settle** across `GREEN_SETTLE_POLLS` identical polls (`workflow_run` chains and `fromJSON` matrices create checks *after* earlier ones conclude); `skipped` is **not** a pass (a job the `if:` guard skipped ran nothing); and an **unfinished check outside `requiredChecks` still holds the verdict up** — it will conclude, and it can conclude red, so skipping past it would make green mean "everything that had finished when I looked was fine". The forge also reports verdicts in a *second* place — the legacy commit-status API, which Buildkite/Jenkins/older deploy apps use and which creates no check run — so failing statuses are folded in as synthetic `status:<context>` runs. That fold is deliberately one-way: a failing status turns a verdict red, a pending one is never waited for (third-party integrations leave statuses pending forever), so it can never manufacture a green or a new way to hang. On top of those, `requiredChecks` is mandatory and non-empty — it is the floor of checks that must *exist*, the only way to distinguish "hasn't started" from "will never run". A check outside that list still sinks the cycle if it fails. And the exist/never-exist distinction is *acted on*: a required name still absent once every other check on the sha has concluded, held for the grace window, is `missing-required` and fatal — a name that doesn't match what the forge publishes (`test` vs `test (20.x)`) is the likeliest misconfiguration there is, and parking on it spends a full CI timeout every cycle.

   Verification failure is a **cycle-level** outcome (the forge judged the composed result; the red isn't attributable to one of several individually-gated merges), so the whole cycle resets to the sha the merger worktree started at, `merged` comes back empty, and every merged issue is skipped as `forge-unverified` with a comment naming the **verified sha** (not the scratch branch, which the next cycle overwrites) and saying it may not be the one at fault. The comment's lede is written from the *reason*: on `source-moved` the checks passed and the cycle lost a race, on `checks-timeout` nothing was rejected at all — telling an author their build failed when it went green sends them to read a passing log. If the resolve loop committed fixes during verification, the comment says those commits are being discarded — they live on the merge result, not on the issue branch. **Parked vs fatal is a judgment about whose failure it is:** checks that never conclude park (CI was slow); anything that is a property of the repo rather than of this cycle's code is `fatal`, because it recurs every cycle and parking would quietly convert the whole backlog to `agent-stuck`. Fatal covers: a sha the forge never builds at all; a required check name that never appears; a rejected integration push; a fast-forward refused while `origin/<sourceBranch>` turns out **not** to have moved (a successful re-merge that produces no commit proves the branch is where it was, so the refusal was branch protection, a hook, or a token without push access); and anything thrown out of the landing itself — an unreachable forge for `CHECK_POLL_MAX_CONSECUTIVE_ERRORS` polls, an unreadable response. All of them arrive as `MergerError` → loud halt, and `MergerError.partial` carries the tracker state already applied so Phase 4 still runs for those issues before the halt. That wrapping is load-bearing rather than decorative: verified landing runs *after* earlier issues in the cycle were commented and de-labelled, so a raw throw would leave them on no queue and under no handoff label. **The same wrapping covers the per-issue loop (#33)**, where the writes actually originate and where the throw sites are not hypothetical: `getIssueBody` throws `SandbarError` by design (a resolve agent reasoning about cross-branch intent without the issue specs is worse than a halted merge phase) and runs at the top of every resolve loop, and `runGate` throws rather than reddens when an `issue`-lifecycle container has died under it (#24 D5). Either one arriving on the second branch of a cycle strands the first. `partial.merged` is `[]` on every one of these paths, never the local `merged` — a halt means nothing landed, which holds by construction because the merges exist only in the ephemeral merger worktree; `run.ts` asserts it, so forwarding them would trade one halt for a more confusing one. That an unexpected throw can leave that worktree mid-merge is not an objection: the partial describes tracker writes already durable on the forge, not the state of a directory about to be deleted. **The wrapping stops the instant the cycle lands** (`landed` in `runMergerWithAdapter`), and that boundary is the point: past the push, `merged: []` and `pushed: false` are lies, and a partial that lies is worse than none — run.ts would report a halt, finalise only the skipped, and leave landed issues open, queued and unclosed against a source branch that has already moved. Throws *before* the first tracker write are left raw for the mirror reason (nothing to carry, and the top-level handler prints a stack this branch does not). The log sink is inside the boundary, not outside it: `emit` wraps its own failure, because `no merges, no push` fires exactly when every issue in the cycle was parked and an ENOSPC there would strand all of them. One residual window is accepted and known: the verified path's fast-forward happens inside `runVerifiedLanding`, which logs one line after it, so a throw from that single write is still wrapped and would report `merged: []` against a branch that did move (`fastForwardSource` catches and returns `rejected`, so that log line is the whole of it). And because run.ts's merger-halted branch never reaches the top-level handler that prints stacks, `asHalt` attaches the original error as `cause` and that branch prints its stack for anything that is not an operator-actionable `SandbarError` — otherwise wrapping would make unexpected bugs *quieter* than leaving them raw. A fast-forward rejected because `origin/<sourceBranch>` genuinely moved mid-verification is neither: the composed result changed, so it is re-merged and **re-verified**, consuming a round. Landing is always a fast-forward of locally-authored commits, so `openPullRequest` changes attribution not at all — the PR is an audit/review handle the forge marks merged on its own (create-or-**update**: a PR surviving an earlier cycle is re-titled, never left describing issues it no longer contains).

4. **Phase 4 — Finalise** (`src/finalize.ts` + `src/finalize-inputs.ts`): per-issue branch lifecycle (push/delete worktree + branch), bot-prefixed issue comments, label flips (`ready-for-agent` ↔ `labels.needsInfo`/`labels.agentStuck` — those are the only two sandbar ever applies). The `needs-ui-prototype` input reuses the needs-info label (same human round-trip: supply the missing artifact, re-label) but pushes the branch **only** when the escalation arrived after commits — otherwise there is nothing to hand over and pushing would publish a ref identical to the source tip, so the empty branch is deleted instead. That delete escalates to `-D` only once `branchIsContainedInOrigin` confirms the branch holds nothing unpushed: `hasCommits` is per-sandbox-cycle, so a HARD-ERROR retry reports `false` while an earlier attempt's commits are still on the branch. **A `git branch -d` refusal is never on its own a licence to force** — it also fires when the local source branch merely trails origin. Pure orchestration via `FinalizeAdapter`; the real adapter shells out to `git`/`gh`. The `review-budget-exhausted` input pushes the branch and posts the **latest reviewer prose only** (not the per-round transcript — that stays in the run-log for offline diagnosis).

   **It runs in two passes, straddling the merge (#30).** The inputs are built by two pure functions in `finalize-inputs.ts`: `terminalFinalizeInputs` over Phase 2's non-DONE terminals, `mergeFinalizeInputs` over the merger's merged/skipped lists. The first pass runs **before** Phase 3, because nothing in it depends on the merge having happened, and the merge phase has more than one way to throw something that is not a `MergerError` — since #24 a `ContainerBringupError` from the merger stack is the live one. Finalising afterwards meant that throw escaped to the top-level handler and exited before a single write, discarding the whole cycle's Phase-2 output — NEEDS-INFO questions unposted, NEEDS-HUMAN traces unposted and unparked (so the issue kept `ready-for-agent` and burned another full attempt budget next run), reviewer prose gone — for a failure that happened after all of it and had nothing to do with it. `MergerError.partial` is unaffected: it still carries the tracker state the merger had already applied, and the second pass finalises it before the halt. The mirror-image risk is accepted as strictly smaller: a required side-effect failing in the first pass now stops the cycle before the merge, but a DONE branch that misses its merge keeps its commits and its `ready-for-agent` label, so preflight classifies it `resumable` (#13) and the next run continues from it. That resume is not automatic once the pass has parked anything — an `agent-stuck` issue is an open issue no longer queued, so its leftover local branch is preflight-`unmerged` and refuses the next run until the operator clears it, which is the steady state every successful parking cycle already produces and costs a `git branch -D` against a branch already on origin. The prose an agent produced once and nobody stored has no such fallback. One knock-on worth knowing: `getIssueBody` renders comments, so the resolve loop's sibling-issue context now includes the handoff comment a sibling earned this cycle — context rather than noise, and bot-stamped, but those comments are addressed to a human and phrased as imperatives.

### Exit conditions (`src/exit-conditions.ts`)

The outer loop terminates on the first of:
- **plan-empty** → success (exit 0)
- **relaunch** (#65) — with `config.relaunchAfterLanding`, any cycle whose merger landed merges exits `EXIT_CODE_RELAUNCH` (75, sysexits' EX_TEMPFAIL): "landed work; relaunch me to continue". Checked **ahead of the stuck/budget conditions** — a landing is progress and budgets are per-run by design, so a cycle that both landed and exhausted the budget relaunches into a fresh budget exactly as a human re-launch would. No spin: it requires a landing, and a landless cycle falls through to the codes below, which break the launcher's loop. Deliberately not fired on a halt or on a landed-but-unclosed cycle (both exit 1 first) — relaunching past an operator-actionable mess would bury it.
- **stuck-same-plan** — same plan as previous cycle AND 0 DONEs this cycle (exit 2)
- **stuck-zero-dones** — `MAX_CONSECUTIVE_ZERO_DONE_CYCLES = 2` (exit 2)
- **budget** — `issuesAttempted >= maxTotalIssues` (default 50, exit 3)

`MAX_ITERATIONS = 100` in `run.ts` is a defensive ceiling — the conditions above terminate first.

`SILENT_NOOP_RETRY_LIMIT = 2` caps per-issue retries when the resolve-loop reports `resolved` but HEAD did not advance (the "silent `git merge --abort`" failure mode). Under the cap, the branch is discarded and the issue stays `ready-for-agent` for the next cycle's planner.

## Key design constraints

- **Pure decision functions where possible.** The inner-loop state machine (`step`, `decideAfterTerminal`), `parsePromise`, `parseVerdict`, `renderReviewerSlot`, `resolvePlan`, `applyCycle`, `checkInvariants`, `finalizeOne` are all pure functions over their inputs. I/O wrappers (`fetchCandidates`, `realAdapter`, etc.) are thin shells around them. Add tests against the pure layer; don't mock `gh`/`git` if you can table-test the decision instead.
- **Adapters for I/O boundaries.** `MergerAdapter`, `FinalizeAdapter`, `ResolveAdapter` define the contract; tests use fakes, production uses `realAdapter(...)`. Don't reach for `execFile` from new code if there's an adapter slot. The *real* adapters are the blind spot in that scheme — a fake satisfies the contract no matter what argv the real one builds — so `realVerifyAdapter` takes an optional `exec` seam and its argv/parsing are table-tested (`forge-verify.test.ts`), with the git primitives exercised against actual repos in `forge-verify-git.test.ts`. Behaviour that git defines is asserted by running it, not by asserting the command string: does a non-ff push reject rather than clobber, does a failed merge leave `MERGE_HEAD` (and *where* — in a linked worktree it is under `.git/worktrees/<name>/`, which is why `isMergeInProgress` asks `git rev-parse --git-path` instead of stating a path), which stream does `git merge` write `CONFLICT` to (stdout, so a reason built from stderr alone loses it), and how much the scratch ref's `--force-with-lease` really protects (only against a write landing between the `ls-remote` and the push — it is read fresh each round, so anything already on the ref is overwritten. That is intended for a ref sandbar owns, and is why config confines `integrationBranch` to the `sandbar/` namespace). The gate stack gets the same treatment (#24): its argv builders (`containerRunArgs`, `podCreateArgs`, `stepExecArgs`, `mountSpec`, `healthCheckArgs`, `parseHealthLog`) are pure and table-tested in `gate-stack.test.ts`, and what *podman* defines is asserted by running podman in `gate-stack-podman.test.ts` — chiefly that a pod container running as root writes worktree files owned by the invoking user (hence dropping `--userns=keep-id` is survivable), and since #43 the whole `podman healthcheck run` layer: its exit codes, that the health log records an `exit 3` probe as `1`, and that `--health-timeout` does not enforce. The one readiness fact a gate runner cannot see is whether podman created a transient systemd timer on the *host*, so that lives in `gate-stack-hostpodman.test.ts` alongside the local client's signal semantics. Those files skip themselves when podman or its image is unavailable, resolved at **collection** time: a `runIf` flag set in `beforeAll` arrives too late and silently skips everything, which is a test file that passes by never running. Where a podman was *promised* — the gate runner, `SANDBAR_REQUIRE_PODMAN_TESTS=1` — the same unavailability is a failing test instead, because a skip there is the silent green #48 exists to kill. The podman file also pins what `ok` alone cannot: that an `issue` container keeps its **container id and its state** across gate runs while the `attempt` container gets a new id (an `ok`-only assertion passes both the recreate-the-database-every-attempt regression and the reuse-stale-code one), that a red gate carries the log of a container the failing step never ran in (D9 asserted on a single-container stack is vacuous), and that an `attempt` container which will not come up is a gate red while a dead `issue` container throws. `checkWorktreeImageUids` takes a `UidProbe` seam for the same reason — the D3 rule decides whether a run proceeds at all, and its argv (`--entrypoint id`, not a trailing `id -u`) is the whole argument.
- **The repo sandbar operates on is NOT the repo the human stands in (#38).** `config.cwd` used to be a dedicated operating clone the consumer had to create and then not touch — machine-managed, gitignored from nothing, and the directory every git call, every worktree and the credentials all had to live in. It is now the operator's **real checkout**, and sandbar does not operate on it at all. `src/repo-cache.ts` derives one `RepoLayout` from `(cwd, workDir)` and everything hangs off it: `<cwd>/<workDir>/repo.git` is a **bare** object cache, `<cwd>/<workDir>/worktrees/{source,issue-<n>-<slug>,merger}` sit beside it, and `run.lock`/`run.pid`/`logs/` are where they were. The layout is threaded as one object (`layout`) rather than as `cwd` + `workDir`, because the two directories stopped being the same thing and a field named `cwd` was about to mean "the repo commands run in" at some call sites and "the root worktree paths hang off" at others — the confusion #34 spent a release removing.
  - **Nothing in the state directory is authoritative, which is what licenses it to live inside the human's checkout.** The tracker is GitHub Issues, branches are pushed at finalise, merged work is on `origin/<sourceBranch>`. `rm -rf .sandbar` costs agent time, never correctness. That is a stronger property than "disposable, but be careful", and it is what makes the `node_modules` analogy exact — including its other half: `node_modules` is disposable *because* `package.json` is one committed root file read by an **installed** tool, which is the gap the bin closes.
  - **The cache is BARE, and that is a safety property rather than a space saving.** The three genuinely destructive operations — `git branch -D` in `deleteMergedIssueBranches`, `git worktree remove --force`, the force-pushed `integrationBranch` — are now provably unable to reach the operator's refs, because the repo they run in holds none of them. This is the sharp edge of the change and it runs the opposite way to how it looks: while `cwd` *was* an operating clone, pointing the delete at it was harmless; threading `cfg.cwd` into it now would run `git branch -D` in the human's own repo. `preflight-git.test.ts` pins the property (the operator's `my-wip` and their identically-named `sandbar/issue-*` both survive a real preflight against a real cache), not the argument string.
  - **The clone carries the URL, not the config that makes the URL usable.** `git clone` writes a fresh config, so a deploy key or credential helper the operator set on their checkout with plain `git config` (`core.sshCommand`, `credential.helper`, `http.extraHeader`, `url.<base>.insteadOf`) does not reach the cache — only `user.name`/`user.email` are read across, and those are read from `hostCwd` at commit time rather than copied. The first run halts loudly on the initial fetch, but every later run's fetch is `runOk` and swallowed, so the symptom becomes preflight's missing-`origin/<sourceBranch>` complaint; that message therefore names the trap and gives the command that reports the real error. Global transport config is unaffected, which is the ordinary case.
  - **Never ask git *which* repository this is; tell it.** Every path in the layout sits inside the operator's checkout, and `git rev-parse --git-dir` discovers by walking **up** — so for a `repo.git` or a `worktrees/source` that exists but is not a repository it exits 0 and answers `<cwd>/.git`. Used as the "does the cache exist" probe (as it was when #38 landed) it reports the cache present and then hands the operator's own repo to `branch -D`, `worktree remove --force`, `reset --hard` and the force-pushed integration ref — the bare-cache safety argument above, inverted, in exactly the state `rm -rf .sandbar` leaves when it is interrupted, which this document invites. The probes therefore **name** their subject: `--git-dir=<path>` (git exits 128 rather than climbing) for the cache, and `--git-common-dir` compared against `layout.repoDir` for a worktree. `repo-cache-git.test.ts` constructs the degenerate states directly, because a fixture that builds a valid cache passes with the discovering probe restored.
  - **Cache creation is atomic** — prepared under `repo.git.incoming` and renamed into place. Preparing in place made "the directory is there" and "the directory went through every preparation step" different facts, and the gap was permanent rather than transient: a run killed between the clone and the head-deletion leaves a structurally valid bare repo carrying the operator's branches, and every later run sees a cache and never revisits what was skipped, so an imported `sandbar/issue-42-*` is a hard preflight refusal on every run over a branch in a repo the operator does not know exists. SIGTERM is the likely path, not an exotic one: the cleanup traps exit the process without killing the child, so the clone completes while nothing after it does. A fixed scratch name is safe because the lock is already held, and it leaves at most one leftover to overwrite rather than one per crash.
  - **`git clone --bare <cwd>`, then retarget `origin` to whatever URL that checkout carries. No config names the remote** — a derived value cannot drift from the repo the config file sits in, whereas a `remoteUrl` knob could disagree with `cwd` and merge the right branches into the wrong repo, silently. The clone is local, so git hardlinks the objects: a multi-gigabyte repo costs a few hundred milliseconds and no network. `remote.origin.fetch` is then set **explicitly** to `+refs/heads/*:refs/remotes/origin/*` — `--bare` sets no refspec at all and `--mirror` (the other obvious spelling) maps the remote's heads onto local `refs/heads/*` and produces no `refs/remotes/origin/*` whatsoever, which every issue-branch seed, the merger worktree and `branchIsContainedInOrigin` read. The imported `refs/heads/*` are **deleted**: the cache's local branch namespace is sandbar's alone, and an operator who happened to have a `sandbar/issue-*` branch checked out for review would otherwise get a hard preflight refusal over a branch sandbar had itself imported out of their repo. The resulting unborn HEAD is fine for everything sandbar does, which `repo-cache-git.test.ts` pins by running it rather than asserting it — every `worktree add` names its commit-ish.
  - **The image build context becomes a commit.** `ensureImages` runs before any issue worktree exists, so its context was `config.cwd` — whatever was checked out there, uncommitted edits included. It is now the persistent `worktrees/source`, detached at `origin/<sourceBranch>` and reset to it after preflight's fetch. Strictly more correct than before rather than merely relocated: the fingerprint recorded on the image is a claim about a *named tree*, and #37's validation moves with it (`rebuildOn`'s must-exist check resolves against this root; `checkWorktreeImageUids` resolves no path at all — it probes images with `podman run --entrypoint id`, so it was unaffected). The reset is `reset --hard` + `clean -ffdx` — **`-x`, not `-d` alone**: an ignored file left behind would still be tarred into the context and make that claim false.
  - **The anchor layers were split in two, because they ask two different questions** — and are now split in *three*, because the tracker is a third. `repoDir` answers the `git log`; `repo` (`ghOwner`/`ghRepo`) answers the `gh issue view`; `probeWorktree` answers "does this doc exist". The `git log` also had to become `origin/<sourceBranch>` rather than the bare name, since the cache deliberately keeps no local copy. #38 pointed the probe at `worktrees/source` — a clean tree at `origin/<sourceBranch>`, which was right about the bare cache having no files and about the operator's checkout carrying their uncommitted edits, and still wrong: it is what an issue worktree *seeds from*, not what the agent reads. **The probe and the resolver must be the same tree**, and the closing argument is that it is the *emitted `@ref`* being decided — a path the agent resolves inside its sandbox, against its own worktree. So the probe takes the issue worktree, and the commit that introduces a `CODING_STANDARDS.md` is reviewed *against* it. **The two prompt builders DERIVE it** from the worktree they are already about rather than taking it as a field — which matters because "which tree" is type-invisible: every candidate is a string, so a call site handed the wrong one type-checks and every test that drives `prompt.ts` directly stays green. The merge phase is the one site that still passes one by hand, and it buys less there than it looks: the anchor is one string built once per cycle, *before* any merge, so the merger worktree is still detached at `origin/<sourceBranch>` when it is probed. A doc added by a branch in the same cycle is therefore still invisible to the resolve agent — a known residual, closable only by rebuilding the anchor per resolve attempt. The history deliberately does **not** follow the branch: the reviewer's worktree is its subject, and sourcing the project anchor's `git log` from it would make the standard a function of the branch being judged.
  - **Two preflight checks were DELETED rather than retargeted (#38 item 7).** "Not on `<sourceBranch>`" and "an in-progress merge/rebase/cherry-pick was detected" existed only because a human might be standing in the operated-on directory. Against a bare cache they are vacuous; pointed at `config.cwd` they would be worse than vacuous — they would refuse to start because the *operator* is mid-rebase in their own repo, which is none of sandbar's business. Exactly one check still reads the host checkout, on purpose: the soft warning that local `<sourceBranch>` is ahead of `origin/<sourceBranch>`. It was near-useless against a machine-managed clone that is never ahead; against a real working repo it is what it was written for, since per-issue worktrees seed from origin and unpushed work is invisible to every agent.
  - **`worktreeRemove` names its repo now.** It used to walk three levels up from the worktree path, which was sound only while the repo was the worktrees' grandparent *and* `workDir` was a single path segment. Three levels up from `<hostCwd>/.sandbar/worktrees/<n>` is the operator's checkout, a repo the worktree is not registered in — and every caller swallows that failure, so the whole class would have been a silent worktree leak.
  - **`resolveGitMounts` asks git instead of deriving the path.** It hardcoded `<repo>/.git`, or the gitlink's target up two levels; `git rev-parse --git-common-dir` answers correctly for a bare repo, a normal repo and a linked worktree of either. The mount *shape* — identity, at the same absolute host path — was already right; only discovery was wrong.
  - **Accepted, and recorded so it is a decision:** `run.lock`/`run.pid` live in the state directory, so `git clean -xfd` can delete the lock out from under a live run. A second sandbar then acquires immediately and, because the podman scope is `runScope(realpathSync(lockPaths.workDir))`, computes the **same** scope — #28's collision replayed inside a single workdir, with `startStack` force-removing the live sibling's namesake pod. Do not clean while a run is in flight. Likewise a clean takes whatever the run had in flight (branch refs in the cache), which costs agent time and leaves the issue queued.
  - **`copyToWorktree` now reads the human's working tree**, since its sources resolve against `cwd` (the cache is bare and has nothing to copy). That is arguably the intent — the feature exists for host-only files that are not in git — but it makes issue-worktree content a function of the operator's uncommitted state, which is the class of bug #10 was. Stated in `config.ts` rather than discovered; a consumer who wants it stable points at absolute paths outside the checkout.
  - **Gitignore does not leak into the worktrees**, and this is worth recording because it is the obvious fear and it is unfounded. Git resolves ignore rules from within the repo whose working tree you are standing in — that worktree's `.gitignore` files downward, plus that repo's `$GIT_DIR/info/exclude` and `core.excludesFile` — and never walks *above* the worktree root into an enclosing repo. It matters because D1 is ignore-sensitive: if an enclosing checkout's ignores applied, a gate could go green over files the parent had hidden. The config-inheritance hazard below (`status.showUntrackedFiles` reaching a linked worktree from `.git/config`) points at the **cache's** config, not the host checkout's.

- **Every shell-out names the repo; nothing inherits `process.cwd()` (#34).** *Read this with the #38 bullet above: what every call site now receives is `layout.repoDir`, the bare cache, while `config.cwd` is the operator's own checkout. #34 made the directory* explicit*; #38 changed* which *directory it is — which is precisely why that retarget was a pass over call sites that were all already named. The paragraph below describes the state #34 left, and it is what made #38 tractable.* `config.cwd` was what the lock, the podman scope, the worktrees, the merges and the tracker writes were all about — and `DEFAULT_CWD()` is `process.cwd()`, so on the author's own checkout the two coincide and an omitted `cwd` is invisible. On a host that sets `config.cwd`, which the config explicitly supports, preflight was inspecting *and* `git branch -D`-ing a different repo from the one the run belonged to (which also quietly qualified #32: the destructive delete was under *a* lock, just not the one covering the repo it deleted from), `ensureIssueBranch` wrote the issue branch into that repo, `prepareWorktree`/`createSandbox` rooted the whole worktree tree there while `worktreePathFor(config.cwd, …)` computed somewhere else, `fetchCandidates` read its tracker for both the plan and preflight's resume classification, and the implementer's and reviewer's anchor layers quoted its history and its issues. The parameter is therefore **required and positional** everywhere it was threaded (`runOk`/`captureOk`, `ensureIssueBranch`, `fetchCandidates`, `fetchIssueText`, `ProjectAnchorOptions`, `InnerLoopConfig`): an optional `{ cwd }` is precisely what went missing, and it goes missing silently. (Present tense, for anyone about to thread one: the three `gh`-facing entries on that list no longer take a directory at all — see the `--repo` bullet at the end.) The remaining exceptions are principled rather than leftovers — `fetchIssueStates` names the repo in its GraphQL variables, and `worktreeRemove` derives the repo three levels up from the worktree path (which is sound only while `workDir` is a single path segment, and nothing validates that). Podman calls need no cwd at all, being host-global; preflight's `image exists` is threaded anyway because `runOk` takes the parameter unconditionally, and that is the one call in the module where a bad `cwd` would turn a true answer into a false one — `execFile` fails `ENOENT`, `runOk` swallows it, and every image is reported missing with a `podman pull` line that will succeed and not help. `acquireLock` mkdirs the directory before preflight runs, so it is not reachable today. **The two path classes were handled differently on purpose.** `envFilePath` was resolved against `cwd` once, in `resolveConfig`, because every consumer (run.ts's GH_TOKEN check, preflight's credential invariants, the sandbox's env resolver) only ever read it on the host — *#38 retired the field entirely; see the credentials bullet below.* **`cwd` itself is resolved to absolute in the same place, and that is not tidiness.** Now that every git call runs *with* `cwd` as its working directory, a relative one is applied twice: `worktreePathFor("sub/repo", …)` is passed as an argument and re-resolved against `<launch>/sub/repo`, which real git turns into `sub/repo/sub/repo/.sandbar/worktrees/merger`. Preflight's `worktree remove` survives it on git's suffix-match fallback; `merger-worktree.ts`'s `worktree add` does not, and podman rejects a relative `-v` source outright, so `merger.ts`'s `-v ${cwd}:/workspace` would fail every resolve-loop attempt. Fixing it at the source is what makes the per-call-site threading safe — and it retires the first half of #28's scope argument (two repos configured `cwd: "."` can no longer hash one scope) while leaving the symlink half exactly where it was, which is why `run.ts` still canonicalises with `realpathSync` rather than `resolve`. `claudeMdPath`/`contextMdPath`/`adrDir`/`codingStandardsPath` must stay exactly as the host wrote them, because they are emitted as `@refs` the agent resolves from the repo root *inside its sandbox* — so only the host-side `existsSync` probe is rooted at `cwd`, and that probe is silent in both directions (a real `CONTEXT.md` dropped from the prompt, or a dead `@ref` handed to the agent). **The wrong-*tree* residual is now closed too, and it took two more passes to get there:** `cwd` was the host checkout while the agent reads the issue **worktree**, so the probe and the reader disagreed whenever the file was uncommitted on the host or added by the branch itself. #34 was about naming the wrong repo; that was naming the wrong tree. #38 moved the probe to `worktrees/source` and killed the uncommitted-on-the-host half; the probe now takes `probeWorktree` — the issue worktree, or the merger worktree in the merge phase — which kills the branch-adds-it half, so a reviewer judging the commit that adds `CODING_STANDARDS.md` is handed the `@ref` to it. See the anchor-layers bullet above for why the *history* must not move with it. Pinned against two real repos with `process.cwd()` pointed at the wrong one (`preflight-git.test.ts`, `git-ops.test.ts`, `prompt-cwd.test.ts`) and, for `gh`, through a shim on PATH that reports the `--repo` it was handed and otherwise **models gh's own fallback** — reading `remote.origin.url` from its working directory — while the process stands in a real repo whose `origin` names a *different* one (`plan-resolver-gh.test.ts`, `prompt-cwd.test.ts`). Both halves of that are the trap: a shim test run from a directory with no remotes passes just as happily with `--repo` deleted, because there is nothing to infer from; and a shim that prints a made-up sentinel instead of inferring makes the different-origin repo, and every `not.toBe("other/wrong")` beside it, dead weight that can never fail. The **write** paths — the comment, the label flip and the issue *close* — get the same treatment in `gh-argv.test.ts`, driving the real adapters against a shim that records its argv, because `finalize.test.ts` and `merger.test.ts` drive fakes and a fake cannot see argv. **Every half of the fix is pinned by at least one assertion that fails when that half alone is reverted, which is the property worth stating** — not that every assertion in those files is a cwd pin. One is deliberately not: `leaves an unmerged branch alone` is a merged-ness assertion. (The `MERGE_HEAD` pair went with the in-progress-marker invariant #38 deleted.) The trap those files exist to avoid is a test that stands in the same directory it configures — it passes just as happily with the fix deleted, which is why the converse case chdirs to the *other* repo instead of the one it points config at. **The `gh` calls named a directory rather than a repo, and that was the last of it.** `gh` infers the repository from the working directory's git remotes unless given `--repo`, so threading a `cwd` only moved the answer from "wherever the process was launched" to "wherever the cache's `origin` points" — neither of which is `ghOwner`/`ghRepo`, both of which split sandbar's tracker access in two: `fetchCandidates` listing from one repo while `fetchIssueStates` (which has always named the repo, in its GraphQL variables) resolves the same numbers in the other, so `resolvePlan` silently drops or mis-states every candidate rather than failing. Every `gh` call now passes `--repo <owner>/<name>` (`repo-ref.ts`), and the functions that make them take a `RepoRef` and **no directory at all** — with `--repo` given there is no directory left for one to be wrong. `fetchCandidates`, `fetchIssueText`, the finalise writes and the merger's comment/label/close calls all read the same required config fields, which is what makes the never-desync coupling preflight relies on (its resume classification calls `fetchCandidates`) structural instead of an assumption.
  - **Naming the tracker cannot make it AGREE with the git remote, so preflight compares them** — in two separate checks, because the repository and the *host* fail differently. `gh` now follows the config; `git push` still goes to the cache's `origin`, copied from the operator's checkout and declared by nobody. An `owner/name` disagreement is fatal rather than a warning because every symptom is silent and lands somewhere real: the planner queues issues from the configured repo, the work is pushed to origin's, the merger *closes* the configured repo's issues for commits that landed in the other, and `verified` mode polls checks for a sha the configured repo has never seen — which reports as `sha-never-built`, i.e. as a CI problem.
    - **The host is checked separately because a matching `owner/name` on a different host is the worse failure** — it passes the repository comparison while pointing every call at an unrelated repo that happens to share a name. `gh`'s flag is `[HOST/]OWNER/REPO` and `repoSlug` emits the two-part form, so every tracker call goes to gh's *default* host (`GH_HOST`, else github.com) and `ghOwner`/`ghRepo` have nowhere to carry one. A GHE `origin` under a github.com default is therefore refused, naming `GH_HOST` — which is gh's own mechanism and the only fix available, since the config has no host field. Note this was already broken before, and silently: `gh issue list` followed the remote's host while `gh api graphql` went to the default one, which is this issue's own bug wearing a different hat.
    - **`parseRepoFromRemoteUrl` returns null rather than guessing**, and that asymmetry is the whole of its design: this answer refuses a run, so a wrong parse turns a working configuration into one that cannot start, which is worse than the split it is catching. The first version got exactly this backwards for the likeliest mirror spelling there is, and the shape of the bug is the reason the rule is now *positive* rather than subtractive. It rejected filesystem paths by testing the whole URL for a leading `/`, `.` or `~` — which catches `/srv/git/app.git` and sails past `git@gitserver.internal:/srv/git/app.git` and `ssh://git@mirror.internal/srv/git/app.git`, the same path reached over ssh. Those parsed confidently as `git/app`: a permanent refusal naming a repository that exists nowhere, i.e. the precise outcome the null contract promises cannot happen. The path must now *look* like a forge path — **exactly two** segments (a third is a directory tree, and it takes GitLab subgroups out too, correctly: `gh` does not speak GitLab), no leading `/` or `~` on the scp side, and both segments matching GitHub's own name charset so `~acme` and `app.git?x=1` fail rather than parse. Everything else lands on null, which is the safe direction: a warning naming the URL.
- **Per-issue isolation, inside a per-run scope.** Every issue gets its own podman network (`sandbar-<scope>-net-<id>`), pod (`sandbar-<scope>-pod-<id>`) and containers (`sandbar-<scope>-<id>-<name>`); the merge phase gets the same under `merger`, the agent sandbox is `sandbar-<scope>-<uuid>`, and its sandbox-stack siblings (#44) are `sandbar-<scope>-sbx-<id>-<name>` — a fourth shape rather than a fourth `stackId`, because `stackContainerNameFor` would produce the identical string for a stack whose id were the literal `sbx`, and an alias there is one stack force-removing the other's live container before a gate run. `cleanupOrphanContainers` sweeps stale prefixed resources at start and between cycles — **including pods**, which is not tidiness: a pod's infra container is named `<pod-id-prefix>-infra` (a podman hash) and matches no sandbar prefix, so a container-only sweep would leave the pod and its network alive forever. The naming prefixes are centralized in `src/naming.ts`, which also lists the legacy `sandcastle-*`/`sandcastle/*` prefixes.
  - **`<scope>` is `w` + 8 hex of the workdir the run locked (#28), and it is a safety property, not a namespacing nicety.** Podman names are host-global while the lock is per-workdir, so two runs against different repos each hold their own lock legitimately and then collide — and both halves of the collision were destructive: `startStack` force-removes a namesake pod before creating (a survivor of a crash is stale and must never be reused), which reached into the sibling's *live* stack; and the sweep force-removes by prefix at startup and between cycles, which by name alone could not tell "orphan of a dead run" from "live resource of another run". The scope is what makes that distinction decidable — one lock ⇔ one scope, so anything in this run's scope is this run's or a dead predecessor's on the same workdir. Everything outside it is invisible. **The two must partition the host identically, and that is the caller's job, not the hash's:** `proper-lockfile` resolves symlinks on the path it locks, while `resolveConfig` passes `config.cwd` through untouched, so `run.ts` hashes `realpathSync(lockPaths.workDir)`. Hash the configured string instead and two repos both configured `cwd: "."` get one scope and two locks — #28 verbatim — while one workdir reached through a symlink gets one lock and two scopes, stranding its debris in a scope nothing computes and nothing reports.
  - **Image tags are the one podman resource class the scope does NOT partition** — they are host-supplied names and `config.images` maps tag → Containerfile. Two workdirs sharing a `sandboxImage` tag on one host will race the build and then silently share whichever image won, built from one repo's Containerfile. On a shared host, give each workdir its own tag. The per-branch tags `rebuildOn` creates (#37) are the exception and are scoped, because sandbar picks those names — see below.
  - **What the sweep can no longer attribute it reports rather than removes.** `findUnattributableResources` names pre-scope `sandbar-*` and legacy `sandcastle-*` debris at startup with copy-pasteable `podman` commands. Not "remove it anyway, it's probably old": a pre-#28 sandbar running concurrently is precisely the case here, and a wrong guess is silent and destructive. The leading `w` in the scope is what keeps this decidable — a uuid's first segment is also 8 hex, so without it the old `sandbar-<uuid>` sandbox name would read as scoped. Accepted residual: a scope whose workdir never runs again leaks its debris, since no live run may claim it — the price of never destroying a sibling. The report therefore repeats every startup until the operator acts; nothing else clears it. Neither function is allowed to be silent about podman failing, and the two halves differ on purpose: a failed **list** throws (a blind sweep cannot know what it missed, so continuing would assert "no debris" on no evidence), while a failed **remove** is collected into `SweepResult.failures` and reported (it knows exactly what leaked, and `startStack` force-removes a namesake next cycle — throwing would let one wedged leftover block every future run). Preflight already hard-fails on a missing runtime before the sweep runs, so the old "runtime not installed" excuse for swallowing either was unreachable.
- **Container runtime is podman.** Hard-coded `RUNTIME = "podman"` in `src/runtime.ts`; the agent sandbox uses the in-house `podman()` provider (`src/agent-sandbox.ts`), now constructed with an explicit `imageName: config.sandboxImage` rather than falling through to `defaultImageName(repoDir)` (which silently coupled the image to the host's *directory name*, #24 D7).
  - **The sandbox container runs under `--init`, and it is not optional (#42).** Its entrypoint is `sleep infinity`, so without it pid 1 is `sleep`, which never calls `wait()`: every process an agent orphans — a test runner's browser, a build's worker, any child whose parent exits first — is reparented to pid 1 and stays `Z` for the lifetime of the issue. Nothing shrinks that count, so it grows with how hard the agent works, each corpse holding a pid slot against the container's pids limit; and well ahead of that ceiling, `ps` is the first tool an agent reaches for to diagnose its own sandbox. There is no config surface because there is no sandbox that wants this, and no consumer-side fix because pid 1 is sandbar's choice and cannot be delegated after the fact — an entrypoint shell that traps and reaps would reimplement catatonit in bash, in every consumer's image. The argv moved into the pure, exported `sandboxRunArgs` to be table-testable at all: the provider needs a real podman and a real image, so the suite drives a fake one and every flag it built was asserted by nothing. What podman *does* with the flag is pinned separately against real podman, with the control half — the same argv minus `--init` — carrying the weight, since "no zombies" is vacuous unless the planted orphan would otherwise become one. Held gate-stack containers have the same `sleep infinity` pid 1 and are deliberately out of scope here; the accumulation there is bounded by the container's lifetime (an `attempt` container is recreated every gate run) rather than by the issue's.
  - **No container ever takes podman's default anonymous image volume (#50).** `--image-volume=ignore` on every container sandbar creates — `containerRunArgs` (so both topologies, gate pod and sandbox chain) and `sandboxRunArgs`. The default is `bind`, which provisions an **anonymous** volume per builtin `VOLUME` in the image — `mariadb`, `postgres` and `redis` all declare one — and podman allocates one lock per container, pod **and volume** from a single pool (`num_locks`, default 2048). Sandbar's removals passed no `-v`, so each volume outlived its container as a permanently consumed lock, and `2000 volumes + 47 containers + 1 pod = 2048` was measured on a real host: past that, **every** podman object creation fails host-wide, in unrelated projects too, and nothing degrades on the way up. **The volume is pure waste in this model, which is what makes it one flag rather than a removal-hygiene campaign** — an anonymous volume is by definition never reused, and an `attempt` container is recreated every gate run (D5), so each recreate got a fresh empty one that was written once, read by nothing and abandoned. `ignore` over `tmpfs`: both create nothing, but tmpfs is RAM-backed and unbounded by default while three issues gate in parallel each with a database, which trades a leak bounded by a known number for an OOM bounded by nothing. No config knob — nothing a consumer can want is reachable through an *anonymous* volume. **`-v` on the container removals is a transitional backstop, not the fix**, and can only ever fire against a container a **pre-upgrade** sandbar created: live at `bringUpContainers`' pre-create removal of a stale namesake and at the orphan sweep, carried but unreachable at `reapKilledStep`, `removeSibling` and `sandboxRemoveArgs` so that a missing flag at one removal is never read as a decision. It reaches only the anonymous volume podman made for the container and can never touch a **named** one — sandbar declares none, every mount it builds is a host bind mount. Three measured negatives, so they are not re-derived: `podman pod rm` has no `-v` at all (4.9.3), so `POD_RM_ARGS` cannot carry one and `stop()` does not enumerate members to get round it (under the flag they carry no volume, so it would buy nothing); `podman run --rm` **already** reaps its own, so `ensure-images.ts`'s uid probe is not a leak site despite looking like one; and `num_locks` is raisable in `containers.conf` but is host config sandbar does not own and only moves the wall. Already-leaked volumes are the **operator's** to clear (the command is in `containers.ts`'s header and repeated in `podman-test-scope.test-util.ts`'s) and nothing in sandbar may do it for them: an anonymous volume carries no label, so sandbar's are indistinguishable from another project's — `findUnattributableResources`' argument, one resource class along. The test fixtures go through `runFixtureContainer`/`removeFixtureContainer` in `podman-test-scope.test-util.ts` rather than a dozen identical literals, because this class of bug is invisible until it is total and literals regress one at a time.
- **The application runs BESIDE the agent too, when the consumer asks for it (#44).** A container marked `inSandbox: true` in `config.gateStack` gets a second copy next to the agent sandbox (`src/sandbox-stack.ts`), so an implementer can run the app before the gate does instead of writing a test it has never watched fail. It exists because the alternative was observed in the wild: a consumer rebuilt the entire stack as **processes** inside its sandbox image — apt-installed mariadb, a libc-matched mailhog binary downloaded because the official image is musl, a hand-written my.cnf to match the gate container's `--sql-mode`, and 163 lines of `pgrep`/`mysqladmin ping`/`curl -sf`/`setsid`/`pkill` supervision. That is a fourth environment (prod, dev, gate, sandbox) whose only defence against drift is being built `FROM` the gate's images, every bug in it is a bug podman does not have, and the description of what it takes to run the app already existed one field away.
  - **`inSandbox`, not the `lifecycle: "issue"` set, and not a second `config.sandboxStack`.** `lifecycle` answers a different question — whose failure a failed bringup is — and the motivating consumer's application server is `attempt`-lifecycle and is precisely what the agent needs to see. A separate stack literal would reintroduce the second description of the application the flag exists to delete. **Opt-in by construction:** declare it nowhere and the subset is empty, so no sibling is created, no log mount is added and the prompt slot renders to "". One new validation rule, mirroring `servesWorktree`'s: `inSandbox` + `hold` + no `postReadyCommands` is a container that provably runs nothing, and the prompt would then offer the agent a neighbour with no process behind it. It needs no rule of its own about ports: since #43 the probe runs inside its own container and nothing is published, so two siblings probing the same port is as harmless here as it is in the gate — #44 inherited a rule forbidding it that #43 had already deleted.
  - **A netns chain off the agent container, not a second pod** — see the anchor-chain sub-bullet under the gate stack for why that inverts the gate's argument rather than contradicting it, and the `keep-id` bullet for why a pod is unavailable rather than merely unattractive. The last link in that chain is the one worth restating here: `claude --print --dangerously-skip-permissions` refuses to run as root, sandbar passes that flag on every agent invocation, and a pod would force the agent to root. "Put the sandbox in a pod" is therefore "bet the loop on an undocumented `IS_SANDBOX=1` escape hatch". Nothing about the agent's own environment moved: keep-id, uid 1000, `HOME`, `--init` and the sandbox image's `agent` user are exactly what they were, and `checkWorktreeImageUids` needs no change because the images it probes are the same worktree-mounting gate containers.
  - **Whose failure a sandbox bringup failure is — D5 rotated onto a stack with no verdict to redden.** An `issue` sibling (a database, a mail catcher; depends only on image and env) **throws**, and the runner takes HARD-ERROR and a fresh sandbox, unchanged. An `attempt` one (mounts the worktree, runs branch code) comes up **degraded**: the agent is told in its prompt, with that container's log tail, because the agent is the one entity in the system that can fix its own app's bootstrap and spending two fresh-sandbox retries to reproduce an error it could have read is exactly what D5 was written to stop. The loop gains no event and no terminal from this — only the prompt gains a slot. That is also why the `attempt` siblings are brought up one at a time while the `issue` ones go as a group: `bringUpContainers` abandons the rest on the first failure, and "degraded" has to mean the others still came up. That shared bringup is the **gate's** code, so it is told which stack it is speaking for (`BringUpCtx.label`) — its messages are the one string D3 hands the agent, rendered directly under a prompt paragraph saying the gate's stack is a namespace it cannot reach, so a `gate stack:` prefix there is a red gate that never ran, and the operator's half is the same error one arm along, sending a run log's reader to inspect a pod where nothing is wrong. A field rather than something derived from the attachment kind, which agrees with it today: one answers which topology, the other whose failure, and deriving it means the day a gate needs a chain every gate message names the sandbox. The statuses are assembled in **declaration order** afterwards rather than as each group lands, since the list is read as a description of the stack the consumer wrote and the two groups are an internal detail of blame. **Ordering:** worktree → `onWorktreeReady` → the anchor (carrying the chain's publishes) → the siblings → `onSandboxReady`, which is deliberately last because that hook is where a consumer runs the migration or the seed that wants the database — ordered the other way, the one hook that most wants the stack is the one hook that cannot see it. `createSandbox`'s `beforeSandboxReady` callback is what buys that position, and it is a callback rather than a return-then-continue split because a throw there has to tear the container down and only `agent-sandbox.ts` has the handle. Siblings are created once per **sandbox**, not per attempt: the gate's recreate-every-run rule exists so a verdict is never formed against stale code, and this stack forms no verdict, while recreating would throw away whatever the agent had accumulated.
  - **The agent can read its siblings' logs; it cannot restart them.** This is the one place the design is *worse* than the script it deletes, so it is stated rather than discovered: sandbar follows each sibling's `podman logs -f` into a file on the host and bind-mounts that directory **read-only** at `/sandbar/logs/<name>.log` (logs are not negotiable — an agent debugging a 500 with no log is a regression), and there is no restart. **Every** sibling is followed, a degraded one included, and that case is the one that needs it: the commonest failed bringup is a container that started and then missed its readiness or a `postReadyCommand`, so it keeps logging for the whole issue while the prompt tells the agent that log says why — frozen at the bringup tail, that sentence is false. The bringup error is written into the same file first, because the path is quoted to an agent that will follow it and an ENOENT reads as sandbar having lost the log; a container that never started costs nothing, since `podman logs -f` then writes its own complaint there. **A sibling that reads configuration at boot is stale for the rest of the issue after the agent edits it, and nothing here restarts it.** Mounted interpreted code and any service the agent only talks to are unaffected, which covers the motivating consumer — but that is a claim about one consumer. It is also the only long-lived `spawn` sandbar still holds — #43 retired the gate's `log` follower — so the signal caveat that used to sit in `gate-stack.ts`'s header sits in `sandbox-stack.ts`'s: `stop` kills every follower and runs on each path out, so SIGINT and SIGTERM are covered, while SIGKILL, an untrapped SIGHUP and a teardown that throws before it reaches them can each orphan one on a quiet container — a stray process, holding no lock and no podman resource. The follow-on, if the missing restart bites, is a control channel: a shim over a bind-mounted unix socket offering `restart <name>`, with sandbar making the podman call host-side so the agent still never gets a runtime. Its own issue; deliberately not built here, as is giving the sandbox a podman socket at all — the isolation between the agent and the stack its verdict is formed in should be structural, not a matter of which socket happened to be mounted.
  - **#37 does not extend to the SIBLINGS, and the confusion mode that buys is real.** They run the image their config names — never a `rebuildOn` variant — resolved once at sandbox creation. The gate re-resolves before every gate run because an image that bakes a lockfile is a function of the branch and a stale one is a *wrong verdict*; a sibling is part of a workspace rather than of a verdict, so a stale layer costs the agent a command rather than an answer. That is the same reasoning #46 makes one level along in resolving `sandboxImage` **once per sandbox** instead of per gate run — and the line falls between the two: since #46 the agent's own container is built against the branch and its siblings still are not. So the agent's suite may pass against baked dependencies the branch has since changed while the gate, which rebuilds, reds. **The gate is authoritative**, and the prompt says so outright.
  - **The two stacks run concurrently over one worktree**, deliberately: the sandbox's app keeps writing while gate-1 forms a verdict. Not paused and not stopped — pausing is a fourth state to reason about for a hazard the consumer already handles for the gate, and a paused database holding live connections buys a new class of flake. See the D1 corollary below for what that extends. Cost, stated: at the default plan size a consumer declaring four `inSandbox` containers goes from 3 gate stacks to 3 gate stacks plus 3 sandbox stacks — roughly double the containers and memory per cycle, which is the price of the isolation, and it is opt-in per container.
  - **The merger's resolve agent is deliberately out of scope.** It is the identical shape one level along — `merger.ts` runs an agent in a lone keep-id container beside the `merger` gate stack — but it is a single bounded pass over a conflict or a red gate, not an eight-attempt build loop, and it never writes a test it needs to watch fail.
- **The gate stack is config-driven (#24).** `config.gateStack` (REQUIRED — what it takes to test this repo is repo identity, no preset) is `{containers, steps}`. A container carries image, `lifecycle`, env, image `args`, read-only `mounts`, `mountWorktree`, `servesWorktree`, `hold`, `readiness` + `readinessTimeoutMs`, `postReadyCommands`. A step is `{name, in, command, timeoutMs?}` — argv `podman exec`'d in a named container, bounded per step (#26). Milliseconds, not the `timeoutSeconds` #26 proposed: two units inside one `gateStack` literal is worth more than writing `900` instead of `900_000`. `resolveGateStack` validates all of it at resolve time (before the lock), because every one of those mistakes otherwise surfaces as an opaque podman error minutes in: unknown `step.in`, duplicate container names, duplicate step names (compared **trimmed** — the rule exists so the failing step is identifiable in the trace, and `test` and `test ` render identically there), `hold` + `args`, a relative or `/` `mountWorktree`, a colon in **any** mount path including `mountWorktree` (which every valid stack has, so it is the most-travelled `-v` spec sandbar builds), a relative `containerPath` or empty `hostPath` (empty resolves to the worktree *root*), an empty `postReadyCommand`, a container setting the reserved `CI` key (sandbar applies it last, so the consumer's value would be silently lost), a NaN or non-positive timeout — `readinessTimeoutMs` **and** `step.timeoutMs`, since node reads `timeout: 0` as "no bound" and NaN compares false against every deadline, so both are the one value a bound must never silently become — an empty `readiness.command` and **any of the three retired readiness kinds** (`tcp`, `log`, `exec`, rejected by name with the replacement config in the message, #43 — a consumer crossing that change has a working config in front of them, and "unknown kind" would send them to read a type instead), **a stack where nothing mounts the worktree** — which would return the same verdict for every commit, green included — and **`lifecycle: "issue"` on an un-held container that mounts the worktree** — it boots branch code at bringup, which contradicts D5's definition of `issue` (depends only on image + env, which is *why* its bringup failure is infra) and so blames the environment for a branch that breaks its own startup. Scoped to **un-held** deliberately: under `hold` the entrypoint is `sleep infinity` and nothing of the branch's runs at bringup, so `issue` is honest there — and it is the only home for per-issue setup, since `postReadyCommands` run once per *container* while an `attempt` container is recreated every gate run. That shape re-opens the misblame window through its own `postReadyCommands`, which is the consumer's argv and the consumer's call. `mounts` is what an issue container uses when it only needs fixture files from the worktree. The check runs **after** the reachability rule below, because #29's own reproducer trips both and only the reachability error names the reported symptom — fixing the lifecycle first would just hand back a config that throws the other error next run.
  - **The steps must be able to see the code, and that is not structurally decidable (#29).** "Something mounts the worktree" is satisfied by a stack whose every step runs in a container that cannot see the branch — the same verdict for every commit, verbatim the failure the check claims to prevent. But the fix is not "every step's container mounts it": an app that mounts the worktree and serves it over 127.0.0.1 to a playwright container is correct and fails that. The two are byte-identical in config (a stale mount a refactor left on a database looks exactly like the app, and a realistic database declares `readiness` too, so readiness separates nothing). So the **sound** half is enforced — at least one worktree-mounting container is stepped into, which every ordinary stack satisfies for free — and the serve-over-loopback shape declares itself with `servesWorktree: true`. That declaration is itself checked where it is decidable: rejected on a container that mounts nothing (nothing to serve), and on `hold` **with no `postReadyCommands`** — `sleep infinity` plus nothing exec'd after it is a container that provably runs nothing. Held *and* daemonizing from a `postReadyCommands` entry is accepted, since that is the only route for an image whose ENTRYPOINT is not a shell. A **throw, not a warning**, because the failure mode is silent and green — a startup warning scrolls past and the gate merges broken code until someone re-reads it.
  - **One pod, not an anchor chain.** Containers share a network namespace via `podman pod`, so the stack addresses itself as `127.0.0.1` and publishes nothing — unqualified since #43, which moved the last host-side probe inside the container and took the pod's `-p` with it. The `--network container:<anchor>` pattern is a docker tax sandbar doesn't owe: the anchor owns the `--dns` flags and its removal destroys the namespace, so an anchor can never be a per-attempt container. The pod holds the #18 resolvers and survives every container's removal, so `anchor` never appears in sandbar's config.
    - **Sandbar runs BOTH topologies since #44, and the argument above is what says when each applies.** The *sandbox* stack — the same containers, beside the agent — is an anchor chain, and every objection just made is an objection to the anchor being a **foreign** container. There the anchor is the per-issue agent sandbox: created first, outliving every sibling, never recreated per attempt, and the natural owner of any namespace-wide flag — of which, since #43 moved every readiness probe inside the container, there are none left to want. What forces the choice rather than merely permitting it is that a pod **cannot host it** — `--pod` refuses `--userns=keep-id`, and the agent needs keep-id (see below). So: pods where a pod is possible, the chain where it is not, and one `ContainerAttachment` union in `gate-stack.ts` is the only place the two meet. The chain's tax is paid in full and is exactly one item: teardown removes joiners **before** the anchor — podman refuses to remove a container others are attached to, so getting that backwards leaks the whole chain rather than half of it (`sandboxRemoveArgs`' `--depend` is the backstop for the paths that ordering cannot reach, not a substitute for it). It was two until #43, whose in-container probe deleted the other one outright: a `tcp` readiness was probed from the host through a publish, a joiner cannot take `-p`, and so the subset's ports had to be computed and handed to the anchor before it existed. The gate's other anchor-owned flag never cost anything here either, and it is worth saying why, since the symmetry invites copying it: the pod carries `--dns` only because #18 puts it on a `--disable-dns` network, and the agent container is on podman's default one, whose resolver is intact — the agent has always had to reach the API through it. Give the sandbox such a network and the `--dns` would have to go on the anchor too, because a joiner cannot take one.
  - **`lifecycle` decides whose failure a failed bringup is (D5).** `issue` containers depend only on image + env → infra → throws → HARD-ERROR → retry with a fresh stack. `attempt` containers mount the worktree and run branch code → **gate red**, with the container's log as the trace. Backwards, an agent that breaks the service bootstrap burns two fresh-stack retries reproducing the same failure and lands on NEEDS-HUMAN with an "environment" trace. Default is `attempt` — the safe side, since a container wrongly reused across attempts gates stale code. The mapping has to hold for the stack's whole life, not just its first second, so two liveness checks back it: a container with **no `readiness`** is still asserted alive after a grace interval (`podman run -d` exits 0 for an entrypoint that dies immediately, so otherwise a dead mail catcher passes bringup and every step that talks to it blames the branch), and the `issue` containers are re-checked **before every gate run** — a database OOM-killed at attempt 4 throws rather than reddening, so the fresh-stack retry does its job instead of burning the budget against a corpse. **That check has to be able to see a container that no longer EXISTS (#36),** which `podman inspect` cannot say: it exits 125 both for a removed container and for a podman that is merely unwell, so the one state that is conclusive evidence of death read as "could not answer" and was waved through — and every later step exec'ing into it then exited 125 and reddened the gate against the branch, the exact misblame the check exists to prevent, reached through the check. `podman container exists` (0 in any state, 1 for gone) is what separates them, asked only on the path where inspect already failed, so it costs nothing in the ordinary case and needs no matching on podman's prose, which differs per subcommand (`no such object` from `inspect`, `no container with name or ID … found` from `exec`). The point is to shrink "unanswerable", not to abolish it: a timed-out `exists` is still no evidence, since reading that as death would turn a slow host into a HARD-ERROR storm — and `exists` is asked **only when `inspect` exited non-zero on its own**, never when it timed out, because a wedged podman cannot answer the second question either and the second 15s would come straight off the readiness budget (`pollUntilReady` tests its deadline only *between* probes, so a doubled worst case doubles the overshoot and halves how many polls a 60s budget buys). Classification is table-tested through an injectable probe (`PodmanProbe`), which is the only way to reach a timed-out inspect or a SIGKILLed `exists` — the answers whose misreading *is* the storm — since no real podman produces them on demand. The check runs **once per gate run**, at the top, so a container removed between it and step N still reds that gate: the misblame is narrowed from every remaining attempt to exactly one, not eliminated. The two death states are reported differently because they imply different next steps — a stopped container still has a log to read, a removed one has no log and an operator question about who removed it. `throwIfDead` draws the same distinction during bringup, where the stake is only a misleading message (a removed container polled to its readiness deadline and reported "did not become ready").
  - **That check asked whether a container is RUNNING, never whether it works (#49).** `.State.Running` is `true` for a database that accepts connections and never answers, a service wedged on a lock, a process that survived an OOM with its worker pool dead — so the check passed, every step that talked to the container failed, and the gate reddened against a branch that never touched it. Same misblame as #36, through the other half of the question. #43 is what makes it cheap: the stack already carries a consumer-authored predicate for "this service is working", so the check asks it. **The state question decides first**, and that order is forced rather than chosen — `podman healthcheck run` cannot classify death (stopped, removed and an unwell podman are all 125 with different prose, and matching podman's prose is what #36 refused to do), so `stopped`/`gone` throw with #36's two messages, `unknown` stays inert, and only `running` is asked the second question. Scoped to `issue` containers that declared a `readiness`: an `attempt` one was recreated and probed to its full budget moments earlier by the same `bringUp`, so a second probe is a duplicate call with no window between it and the steps it protects, and D5 already charges its failure to the branch correctly; a container with no `readiness` keeps today's behaviour exactly, because the consumer declared no predicate to ask. Cost in the ordinary case is one `healthcheck run` (~0.3s) per probed `issue` container per gate run.
    - **A healthcheck is not a liveness check — it can be transiently FALSE**, which is why one shot would be the storm rather than the fix: a database mid-GC, a service reloading config or a probe that flakes under load would each become `ContainerBringupError` → HARD-ERROR → fresh stack, and a service unhealthy for ten seconds every few minutes would exhaust `HARD_ERROR_MAX_RETRIES` and park the issue with an "environment" trace — D5 running backwards, introduced by the check meant to prevent it. So it **polls, bounded by `readinessTimeoutMs`, with no new knob**. The worry that this "waits a full readiness budget before every attempt" is not what the loop does: it probes *before* it sleeps and returns on the first success, so the healthy case costs one probe and no wait, and the budget is only ever spent on the path whose current outcome is a HARD-ERROR that pays the same number again on each of two fresh stacks. A second field would also have to mean "how long this may take to *recover*, as distinct from to start", which is not a distinction a consumer can calibrate, and any fixed internal constant is wrong for both a 2s mailhog and a 180s mariadb — which is why the number is per-container to begin with.
    - **An unanswerable probe abandons and the gate proceeds** — at any point in the poll, not at the deadline. `probeOnce` is three-valued now (`healthy` / `unhealthy` / `error`), and the split lives in the probe because **the two callers disagree about what `error` means**: at bringup nothing is yet known to have worked, so a failing probe and an unrunnable one have identical standing and the deadline arbitrates; here the container *had* worked, so reading an unanswerable probe as evidence it stopped is `containerState`'s `unknown` rule broken through a different door, and a flaked podman becomes the storm. Abandoning costs at most the misblame that exists today, i.e. the status quo, and that asymmetry is the whole argument. `error` covers podman's own 125, a timeout, a kill, a null exit code and a maxBuffer overflow; `unhealthy` is exit 1, which podman normalises **every** non-zero probe exit to — including a probe that itself exits 125 — so the consumer's command can never impersonate podman's error. The one thing that is **not** an `error` is sandbar's own deadline expiring: each probe is bounded by what is *left* of the budget, so a poll's last probe is routinely the one killed, and classifying that as podman failing would make the escalation fire or not fire depending on where a 500ms sleep landed relative to a 300ms probe. At the deadline the verdict is what the poll observed — `unhealthy` if any probe ever answered, `abandoned` if none did.
    - **Persistently unhealthy recreates the container in place before anything is thrown.** `reapKilledStep`'s precedent, and its argument transfers verbatim: the alternative is throwing away a working stack and the rest of the issue's attempts for a container sandbar knows exactly how to put back. It cannot lose more than the retry it replaces — a HARD-ERROR destroys a strict superset, recreating this container *and* every other one, discarding the agent sandbox and restarting the issue at attempt 1 — and in the **merge phase there is no retry at all**, since a throw out of `runGate` in gate-2 is not a `MergerError` and halts the phase for the cycle, so there the recreate is the only recovery there is. It carries `reapKilledStep`'s cost too (everything accumulated beyond the declared setup goes with it, which is what a held `issue` container is invited to hold) and its trap: `withImages([c], ctx.running.map)`, the map **as it stands**, because this is the *other* bringup that neither precedes nor follows a `running.map` update and the declared spec there is #37 reintroduced, silently, green included. The remap is done **once** and feeds the *poll* as well as the recreate: the poll renders `c.image` too, through the `throwIfDead` between its probes, so a declared spec handed to it reports a container that died mid-poll under a tag that is not the one that died — `withImages`' own contract is that a substituted image rides on the spec rather than being threaded past each reader of it.
    - **Still unhealthy after the recreate is a HARD-ERROR, with no #37-style carve-out.** #37 carved out the case where the branch authors the *image* — an explicit, content-addressed mechanism sandbar runs per branch; there is no analogous mechanism for health, whose inputs are image + env + `postReadyCommands`, and `postReadyCommands` are config. The tempting exception ("unhealthy because a `postReadyCommand` the branch changed left it that way") is already answered the other way one function up: a `postReadyCommand` that *fails* raises `ContainerBringupError` today, i.e. infra, so making the same misconfiguration a gate red when a later gate run notices it and a HARD-ERROR when bringup notices it would be one question with two answers chosen by timing. Blame is genuinely undecidable at the point of the check anyway — a container healthy after its `postReadyCommands` and unhealthy now was wedged by something that ran since, gate steps (branch code) or the environment, and nothing here distinguishes them — so what matters is which way it fails: a wrong HARD-ERROR costs two stack rebuilds and a misleading terminal, while a wrong red asks an implementer to fix a service it never touched and burns the attempt budget against it, which is the failure this exists to close. The error text tells the **whole sequence** (healthy at bringup, unhealthy at the top of this gate run, no recovery within the budget, recreated, still broken) plus the health log and the container tail, because none of it is recoverable afterwards — which is what `ContainerBringupError.reason` exists for: quoting the inner error's `message` would nest a second log-tail heading inside the first. The wedged container's own `last probe:` text is read **at the deadline, before the recreate**, and for once that is not just #43's discipline about the client's one-word `unhealthy`: the recreate *removes* that container, so it is the last moment the record exists at all — the `healthLog` block on the same error belongs to the fresh container.
    - **Consequence for consumers, worth stating because it changes what `readiness` buys:** declaring one on an `issue` container is no longer only bringup gating, it is mid-issue wedge detection. Residuals: the check still runs once per gate run, so a container that wedges between it and step N still reds that gate (narrowed from every remaining attempt to exactly one, the same sentence #36 already carried); a service transiently unhealthy at the top of *every* gate run pays its recovery poll every attempt, which is visible rather than silent since the recovery and the recreate each log a line; and every probe the deadline kills leaves a process inside the container, bounded by (probed `issue` containers × attempts) and cleared by the recreate when the path ends in one.
  - **Nothing that shells into a container may hang.** The run holds the single-instance lock while the gate works and node's `execFile` has no default timeout, so an unbounded exec is not a slow gate but a run that never ends and never tears down. Readiness probes and `postReadyCommands` are bounded by the container's readiness budget, the calls sandbar makes *about* a container rather than through it (`logs`, `inspect`, `container exists`) by `LOG_READ_TIMEOUT_MS`. Podman's own `--health-timeout` is **not** one of these and is deliberately not passed: it does not kill a slow probe, it lets it run to completion and labels the result afterwards (#43 M4), so a config field spelled like a per-probe bound would be this bullet's own green-on-red wearing podman's colours. Note `readinessTimeoutMs` alone does **not** give this: the poll loop tests its deadline only *between* probes, so one probe that never returns hangs forever inside a valid budget. Steps are bounded per step by `step.timeoutMs` (#26, default 15 min) — a lint step and a browser suite do not want the same ceiling and the consumer is the only one who knows which is which. **But the bound cannot be node's `timeout:` option, and that is the sharpest thing in #26:** node kills the child with SIGTERM, `podman exec` *exits 0* on SIGTERM, and node reports an error only for a non-zero code or a non-null signal — so the call **resolves**. A hung suite was a green gate, a hung `exec` readiness probe a container reported ready, a hung `postReadyCommand` a database reported seeded; the latter two had carried `timeout:` since #24 and neither had ever been able to fail. So `boundedPodman` owns the deadline, kills with SIGKILL, and `timedOut` is a flag the timer sets rather than anything inferred from an exit code. **Every** podman call in the module goes through it — including the teardown in `stop()`, where the same green-on-red made sandbar report a clean `pod rm` of a pod that was still running, under a comment insisting failures there are never swallowed. The create/destroy calls (`pod create`, `network create`, `run`, `rm`) get a much larger `CONTROL_TIMEOUT_MS` because they do real work and 15s would be a spurious bringup failure; they are bounded at all because `reapKilledStep` tolerates a failed remove on the grounds that the next gate run force-removes the container first, so an unbounded remove *there* would be #26's hang reached through #26's fix. Note the class of a control-plane throw is load-bearing: a flaked `pod inspect` raises a plain `Error`, never a `SandbarError` — `inner-loop.ts` rethrows `SandbarError` past HARD-ERROR, which would drop the issue for the cycle with no terminal, no comment and no label flip while leaving it queued. Validation rejects a non-positive, NaN or infinite `timeoutMs`, and the reason is the opposite of node's: the deadline is a `setTimeout` sandbar owns, so 0 and NaN fire on the next tick — every step killed before it runs — and Infinity never fires. A timeout is a **gate red, not a HARD-ERROR** (D5's argument: a suite that hangs is the branch's code, and a hang that is genuinely environmental recurs and exhausts the budget onto NEEDS-HUMAN with the same trace), carrying `exitCode: 124`, the step's name, the bound, and — per D9, and this is the case that needs them most, since a hang's own output is usually empty — the stack's container logs, collected *before* the reap below. **And killing the client reaps nothing:** the process keeps running inside the container (pinned against real podman, for the timer's SIGKILL and for the SIGTERM node sends on a maxBuffer overflow alike — so both kills reap). The only handle podman gives that is total, and that needs no `kill` binary in an image sandbar does not control, is the container itself — so `reapKilledStep` removes it, which is free for an `attempt` container (the next gate run recreates it anyway) and is followed by an immediate re-bringup for an `issue` one. Be precise about what that re-bringup prevents. Until #36 the answer was a red gate *against the branch*: `assertIssueContainersAlive` could not see a removed container at all, so every later step targeting it exited 125 and reddened, D5's blame mapping running backwards for a container sandbar itself removed. That check now catches it, which demotes the re-bringup from load-bearing to a worthwhile optimisation — the alternative is discarding a working stack and the rest of the issue's attempts on a HARD-ERROR, for a container sandbar knows exactly how to put back. The cost is more than re-running `postReadyCommands`: everything the container accumulated beyond its declared setup goes with it — a schema an earlier gate step migrated, rows an earlier attempt wrote — and a held `issue` container is exactly where consumers are invited to keep that. Still better than leaving a runaway inside it for the rest of the issue, or reporting a red the branch cannot act on. A recreate that **fails** is the single exception to "a killed step is always a gate red": the bringup error wins, the step name and D9 logs are discarded, and the run takes a HARD-ERROR. There is deliberately **no** bound on the gate as a whole: a run stops at the first red, so one hung step costs one step's bound, and a second number could only kill a legitimately slow run without being able to name what it killed. The residual — N slow but *passing* steps may run for the sum of their bounds — is finite and computable from the config. At startup the hash is recorded as an image **label**, so a tag left from before the operator pulled new deps is rebuilt rather than reused for its name; and before **every gate run** the gated worktree is hashed, with a match using the base image and a difference getting a content-addressed variant tag (`naming.ts`) built from *that worktree*.
  - **Per gate run, not per issue, and that is the whole correctness argument.** An issue branch starts identical to source, so resolving once at `startStack` would answer "unchanged" for the reachable case: the agent adds the dependency during attempt 1 and gate-1 runs immediately after. `startStack` therefore brings issue containers up with the images config *names* — which is safe because nothing of the branch runs there (`resolveGateStack` refuses `lifecycle: "issue"` on an un-held worktree-mounting container, and a held one's entrypoint is `sleep infinity`) — and the first `runGate` recreates whatever the branch moved. Cost of getting it wrong the other way: putting a per-branch build outside a gate run leaves it only a throw, i.e. HARD-ERROR, i.e. two fresh-stack retries reproducing the same broken lockfile and an "environment" trace.
  - **An unbuildable image is a gate RED, not a HARD-ERROR** — D5's argument, one level up: the image is a function of the branch, so a lockfile that does not install is the branch's to fix. It arrives as `failedStep: "image:<tag>"` carrying the build's own output, which is why the per-branch path *captures* the build (the base build inherits the console instead: a cold multi-minute build should show progress, and its failure halts the run in front of the operator watching it). For the same reason **an `issue` container recreated because its image changed reds rather than throws** — a deliberate exception to D5, whose "depends only on image + env" is exactly what stops being true when the branch authors the image. That recreate also **moves `assertIssueContainersAlive` after it**, which is not cosmetic: `bringUp` removes before it creates, so a recreate that fails leaves the container *gone*, and checking aliveness first would report sandbar's own removal as "it came up once and something killed it" — an infra HARD-ERROR blaming the environment for an image the branch authored, reached through the check that exists to prevent misblame. `running.map` is therefore updated only after the recreate succeeds, so the next gate run retries it and reds again instead. What the check still catches is unchanged: a container nothing touched that died on its own between gate runs.
  - **The image resolution runs after the dirty-tree refusal** (a tree that gets no verdict should not pay for a build) and before any container is created. Variant tags carry the run scope *and* the content hash. The hash makes reuse decidable — but the tag holds only its first 8 hex, so reuse is decided by reading the **full** fingerprint back off the image's label, not by `image exists`: the name alone is a 32-bit key, and a leftover tag from a crashed run in this scope would be accepted on it. The in-flight map stops two parallel issues racing one name, and it **evicts a rejection** — deduplicating work in flight is not an argument for caching a failure, and cached, one transient registry 5xx is a dead end rather than a bad verdict (the fingerprint does not move unless the agent touches the lockfile again, so every remaining attempt re-throws the same stale error, no build is ever retried, and the issue parks with a trace telling its author their dependencies do not install). The scope is what makes a crash's leftovers reapable, and that is *implemented*, not merely asserted: `sweepBranchImages` reclaims this scope's variants at startup and is blind to every other scope, because the run-end removal is an `onCleanup` action and so does not survive SIGKILL — and these are the largest things sandbar creates.
  - **`reapKilledStep` is the one bringup that neither precedes nor follows a `running.map` update, and recreating from the declared image there is #37 reintroduced through its own fix.** A timed-out `issue` container put back on the base image while the map still says it is on the branch's variant is never seen as stale again, so every remaining attempt gates against the source branch's dependencies — silently, green included. It therefore recreates through `withImages(..., ctx.running.map)`: the map **as it stands**, since this is a restore of what was running and not a new resolution (re-resolving mid-red would pay a build for a gate whose verdict is already decided). Pinned by a podman test that fails on the one-word regression; an `ok`-only or id-only assertion passes with the bug present.
  - **The build is bounded and reaped.** `images[].buildTimeoutMs` (default 45 min) is a deadline sandbar owns, killed with SIGKILL and flagged by the timer rather than inferred from an exit code — the same discipline `boundedPodman` uses, and per entry for the same reason `step.timeoutMs` is per step. It exists because a `rebuildOn` build runs *inside* a gate run, from a recipe the implementer agent wrote, while the run holds the single-instance lock; unbounded it is not a slow gate but a run that never ends. Live builds are tracked in one module-level set with a **single** `onCleanup` entry (that registry never forgets an action), so a signal cannot leave a `podman build` running detached to apply a tag `builtTags()` never saw.
  - **D3 is re-asked for anything the branch builds.** The Containerfile's own bytes are in the fingerprint, so a branch is explicitly free to change the recipe's `USER` — and the startup check runs once over the *declared* images and would never see it, leaving a silent mid-gate EACCES, the one failure D3 exists to convert into a refusal. A freshly-built variant behind a worktree-mounting container is probed before any container gets it, and a bad uid is an `ImageBuildError` → gate red, because the branch authored the change. A *reused* variant is not re-probed (it was probed when it was built), and an image no worktree-mounting container runs is never probed at all — widening it would refuse a perfectly good mariadb on uid 999.
  - **`rebuildOn` is validated into non-inertness, because inert is the bug.** Paths are repo-relative with no `.`/`..`/empty segment, must sit **inside the containerfile's own directory** — that directory is the build context, so a path outside it can never be `COPY`d and the image cannot be a function of it, which would rebuild on every change and produce a byte-identical image (the README's own first example was that config) — must **exist in the source worktree** (`worktrees/source` since #38; before it, the host checkout — a typo matches nothing in every tree, compares equal everywhere, and silently restores the pre-#37 behaviour), cannot combine with `stdinContext` (no context, so nothing in the repo can enter the image) or with an absolute `containerfile` (the rebuild re-roots at the worktree), and must be on an image something **runs** — a `gateStack` container's image, or (since #46) `sandboxImage`. An entry sandbar builds and nothing runs is still refused, which is the whole rule: the declaration would be inert.
  - **The fingerprint encoding is fussy on purpose** — a hash two trees can share is a false verdict wearing a hash. Declared paths are sorted (a property of the set, not of the writing order), every record is length-prefixed (otherwise `a="b", b=""` and `a="", b="b"` stream identically), a directory is walked in sorted order with every entry contributing its relative path (so a file moving between two hashed directories changes it), a symlink contributes its target string rather than the bytes it points at (following it hashes one file twice or leaves the root), and an absent path contributes an absence marker (so a deleted lockfile and an empty one differ). Files are streamed, since `rebuildOn` accepts a directory.
- **The agent sandbox's image is a function of the branch too, and the ONLY thing that was ever wrong about that was the timing (#46).** #37 excluded it on a written-down argument — the sandbox image "is resolved once, when the sandbox is created, before the branch it would be a function of exists" — whose first clause is true and whose second is not: `inner-loop.ts` prepares the issue worktree *before* it creates the sandbox (#20, because the stack's mounts are read at container start), so the branch's files are on disk two statements earlier. What the exclusion cost is not hypothetical, and it is the shape #37 exists to abolish: a consumer's boot script inside the sandbox comparing `package-lock.json` against a copy kept in the image and re-running `npm ci` on a difference, per package manager — image cache invalidation reimplemented at run time because the config could not express it, with a copied lockfile standing in for a layer hash. So `sandboxImage` now participates, resolved from the prepared issue worktree and handed to `podman({imageName})`.
  - **Once per sandbox, not once per gate run, and that asymmetry with #37 is the point.** The ralph loop's shape is attempts accumulating in *one* container, so the only way to re-resolve mid-issue is to discard the sandbox the agent is working in — against which the agent can install into its own sandbox with a single command. The gate keeps its per-gate-run resolution, because that is where verdicts come from: what the branch adds during attempt 3 still reaches the image the gate runs, just not the one the agent is sitting in.
  - **A failed build falls back to the declared tag; a throw here would WEDGE the branch rather than fail it.** The sandbox is the container the fix gets written in. An agent that commits a lockfile which does not install would otherwise make every later sandbox for that branch fail before its first turn — including the ones whose whole purpose is to repair it — and the branch outlives the cycle, so a resumable issue would come back and fail identically forever. So it falls back and reports, to the console and the run log; the agent's environment is then a commit behind its own branch, which is precisely the pre-#46 state and is recoverable from inside the sandbox.
    - **What that report may PROMISE depends on the config, so it is told rather than assumed (`gateRunsSameImage`).** Where a `gateStack` container runs the same tag — this repo's own config, one image in both roles — the gate resolves the entry itself, reds with the same build output and blames the branch, so the fallback line is a warning about a verdict already on its way. Where the entry is the **sandbox's alone**, which is the configuration this feature exists to serve and the one the README's example writes, nothing else ever resolves it: `startStack` asks the resolver only about the images its own spec names, so the gate goes green on images that built fine and that line is the whole of the report. A message promising the gate would catch it would send that operator to watch for a red that cannot arrive — this issue's own failure shape, one layer up, so the two cases say different things and `resolveSandboxImage` takes the fact as a required parameter.
    - **A variant whose recipe drops the uid-1000 user is a different failure and is NOT loud.** Worth stating precisely, because it is the reason D3's root-or-host-uid rule is not re-asked for the sandbox and an imprecise version of it would read as a guarantee. That rule genuinely does not apply — the sandbox runs under `--userns=keep-id` and is not a pod member, so worktree ownership is right regardless of what the image declares. But nothing refuses either: `sandboxRunArgs` passes a numeric `--user 1000:1000` and `--userns=keep-id:uid=…,gid=…`, neither of which consults the image's `/etc/passwd`, so the container starts. What breaks is `HOME` (`/home/agent`): absent from the image, podman creates only the bind-mount path beneath it with root-owned parents, and the agent then fails on every write to its own home — per invocation, inside a running sandbox, which is the quiet direction. Making it loud means a probe, and that is a separate call to make deliberately rather than a claim to make here.
  - **`resolve` takes the tags its caller RUNS, and the gate stack computes its own.** One resolver serves both callers and must — a consumer may give one image both roles (this repo does), the variant tag is content-addressed, and the in-flight map then makes the second caller free rather than a duplicate multi-GB build. But they are not asking the same question: resolving the sandbox's entry inside a gate run would pay for an image no container in that stack runs, and — because an `ImageBuildError` from `ctx.images()` is a gate red by design — would let that build's failure redden a gate the image has nothing to do with. So the parameter is required rather than defaulted to "everything that participates", and `startStack` derives it from its own spec so no call site can hand it a superset.
  - **The merger's resolve agent is a known residual.** It runs `config.sandboxImage` as declared (`merger.ts` spawns a fresh `podman run` per invocation), so the merge result's dependencies are not baked into the container that reasons about the conflict — while gate-2 in the same phase *is* resolved per gate run. Closing it means a build per merge inside the merge phase's critical path for an agent that resolves conflicts and can install for itself; the trade was declined, not overlooked.
- **A gate verdict is about a COMMIT, so the tree is asserted ≡ HEAD (#24 D1).** `dirtyWorktreePaths` (`git-ops.ts`) gates both entry points: the inner loop reads it after every implementer attempt and the SM routes `COMPLETE` + dirty to another attempt with "commit your work" (no stack bringup paid), and `stack.runGate()` re-checks it so gate-2 in the merger worktree is covered when the resolve agent leaves edits. **The standalone `sandbar gate` is the one caller that suspends it (#45), and it is the exception that states the rule**: this check exists because a verdict *the merger will act on* has to be about a commit, and standalone there is neither — the operator is asking about the tree in front of them, which on a laptop is the tree with their edits in it. Nothing inside a run may pass `allowDirtyWorktree`. Deliberately **refuse, not clean**: `git clean -fd` would delete exactly the set this reports — untracked, non-ignored files, overwhelmingly a forgotten `git add`. A materialized-commit tree was rejected too: build artifacts are gitignored and live *inside* the mounted tree, so a second tree costs a cold build every attempt (~768M of ext4 copying per issue for outdoor) for a verdict identical to the assert's. **Corollary on consumers:** a gate step must write only into gitignored paths, or its own exhaust is reported as uncommitted work every attempt until the budget dies — and since #44 the same applies to a **sandbox sibling**, which writes continuously rather than only during a step — and when an attempt comes back with the **identical** dirty set, the loop stops there with `NEEDS-HUMAN cause: "uncommittable-worktree"` rather than spending the rest of the budget on a set the agent has already shown it cannot clear.
  - **The `--porcelain` read pins `status.showUntrackedFiles=normal` on the command line.** A bare `git status --porcelain` honours that setting, and `no` is common in large repos — it reaches a per-issue worktree from `~/.gitconfig`, `$GIT_CONFIG_GLOBAL`, or the repo's own `.git/config`, which every linked worktree shares. Inherit it and a forgotten `git add` reads clean: the gate mounts files in no commit, goes green, and the merger lands a branch that does not contain what was tested. Both D1 entry points go blind together, so gate-2 does not catch it. Same pin in `agent-sandbox.ts`'s `hasUncommittedChanges`, where it decides whether a worktree is preserved or deleted.
  - **The merger commits what `npm install` dirties.** `npm install` runs in the merger worktree between the merge and gate-2, and rewrites tracked `package-lock.json` exactly when merging two branches that both touched dependencies — which D1 would then refuse with a `worktree-clean` red that never mentions npm, while each resolve retry re-ran the install and re-created it. The update belongs in the merge result, so it is committed — but **only when the tree was clean beforehand**, since a dirty tree on entry means the resolve agent left edits, which is the case gate-2's check exists to catch.
- **And the commit has to be on the ISSUE BRANCH, which a clean tree does not prove (#27).** D1 asserts tree ≡ HEAD; `headMismatch` (`git-ops.ts`) asserts HEAD ≡ `refs/heads/<branch>`, read beside `dirtyWorktreePaths` after every implementer attempt. An implementer that commits on a detached HEAD — or on a scratch branch of its own — leaves a **clean** worktree, so gate-1 mounts a tree containing the work and goes green while the merger, which only ever reads the branch, cannot see any of it. **Be precise about how far that gets, because #27's own description is of the shape that is currently unreachable.** Commit capture reads `refs/heads/<branch>`, so an agent that detaches on its *first* attempt keeps `commitsAccumulated` at 0 and `parsePromise` already downgrades every `COMPLETE` — it never reaches a gate, and instead burns all eight attempts on "you made no commits this run" before dying as `NEEDS-HUMAN gate-red` naming a gate that never ran. The reachable bug is the ordinary review round-trip: attempt 1 commits on the branch, the reviewer asks for changes, attempt 2 writes the fix on a detached HEAD — `commitsAccumulated` is already positive so `COMPLETE` stands, gate-1 goes green on a tree containing the fix, the reviewer approves, and the merger lands **attempt 1's commits without it**. A green gate certifying a tree the branch does not contain, and a partial land presented as a complete one. Handoff comments must therefore never claim "no gate ran", "nothing merged" or "the branch never moved" — all three are false on the path that actually reaches the terminal.
  - **The check reads `git rev-parse --symbolic-full-name HEAD`, never `git symbolic-ref -q HEAD`.** The latter looks like it distinguishes detached (exit 1) from broken (exit 128) by exit code, but `-q` suppresses only git's *own* message and anything else on stderr still comes through: with `GIT_TRACE=1` in the operator's environment a detached HEAD exits 1 with ~80 bytes of trace, an exit-code-plus-empty-stderr test rethrows, and the mismatch is reported as an infra **HARD-ERROR** — two pointless fresh-sandbox retries, then a terminal that deletes the branch and posts no comment. An env var re-hiding exactly the failure the check exists to expose. `rev-parse` has no such fork: inside a valid repo it exits 0 either way and prints the literal `HEAD` when detached, so non-zero is unambiguously a real failure and is left to throw. It is also the command `prompts/implementer.md` tells the agent to verify itself with, so the check and the instruction are the same question. The branch-tip read is null-on-missing (a missing ref is data); the **HEAD sha read throws**, because it is the whole payload.
  - **Symbolic ref, not `rev-parse HEAD == rev-parse refs/heads/<branch>`** as the issue proposed: a sha comparison accepts a HEAD detached exactly at the branch tip, which is one commit from the bug while the corrective instruction is already identical.
  - **One correction, then `NEEDS-HUMAN cause: "off-branch-head"`.** The asymmetry with `uncommittable-worktree`'s same-set rule is that there is no partial progress here — either HEAD is the branch or it is not, and the fix is two mechanical commands spelled out in the re-prompt. The test is on the previous attempt being off-branch, not off-branch *in the same place*: a new detached sha is not progress, and comparing positions would let an agent grind the whole budget by committing again. It fires on `COMPLETE` **and NO-SIGNAL** — every attempt spent off-branch strands more commits, and off-branch otherwise reads as `commitsAccumulated === 0`, so the agent is told it "made no commits" when it made several.
  - **Neither the re-prompt nor the orchestrator moves the ref.** `git branch -f` is safe only when the branch is an ancestor of HEAD; forcing it otherwise silently drops whatever the branch already had, trading a visible failure for an invisible one. So the agent is told to `cherry-pick`/`merge` unless it has checked — and because that rescue moves the ref *without creating a commit*, `agent-sandbox.ts` anchors the commit range at `refs/heads/<branch>` rather than at the worktree HEAD. With HEAD on the branch the two are the same commit; off it, the HEAD anchor makes a correctly-executed rescue count as zero commits and sends the agent the very message this check exists to stop sending.
  - **NEEDS-INFO and NEEDS-UI-PROTOTYPE are exempt from the correction, but not from the reporting.** Re-prompting them would risk spending the budget on a question the agent had already formed and would swap a precise handoff for a generic one. But "they land nothing anyway" is not a reason to stay quiet: commits are counted on the branch, so an off-branch escalation reports `hasCommits: false`, and finalize then deletes the branch and posts only the `<ui-impact>`/`<questions>` block — the detached sha would exist in no comment, no ref and no log, and go at the next `git gc`. That is #27's own failure arriving through the terminal the check chose not to guard. Both terminals therefore carry the `HeadMismatch`, and `STRANDED_COMMITS_NOTE` appends it to the comment. Its prose **branches on `headRef`**: a detached HEAD is unreachable and on gc's clock, so the reader is told to `git branch <rescue-name> <sha>` now; a scratch branch is a real local ref that survives worktree removal and gc, so telling that reader their work is about to be pruned would send them to rescue something in no danger.
  - Inner-loop only: the merger worktree is detached *by design*, so unlike D1 this has no second entry point in `stack.runGate()` — and needs none, since nothing runs between the implementer result and gate-1.
  - **Known, pre-existing and NOT fixed here:** the `needs-human` arm pushes the branch unconditionally, so a stuck issue whose agent never committed publishes an empty `sandbar/issue-N-*` ref to origin that nothing ever deletes. `off-branch-head` makes it more likely but does not introduce it — `gate-red` with zero commits does the same — and the fix needs `hasCommits` on a terminal that does not carry commits today.

- **Branch naming is load-bearing.** `sandbar/issue-<n>-<kebab-slug>` (prefix in `src/naming.ts`) — the preflight cleanup, orphan sweeper, and worktree path computation (`worktreePathFor`, in `repo-cache.ts` since #38, taking the worktrees directory rather than the repo directory) all rely on this prefix. Don't change it casually.
- **Verified merge mode is about independence, not coverage (#22).** The local gate and the code under test share one process, one podman, one image cache, one credential record and one author — nothing disagrees. CI is a second, differently-authored implementation of "does this work". So a coverage gap belongs in `gateStack.steps` (cheaper, per-attempt); `mergeMode: "verified"` exists for the thing expanding the gate can't buy. Its non-negotiable invariant: **no unknown verdict ever lands** — and "unknown" includes a partial read, an unsettled snapshot, a skipped job, an unfinished check nobody named, and a check that was never reported, not just a pending one. `integrationBranch` is a remote-only scratch ref (never a local branch: it is pushed as `HEAD:refs/heads/<b>` from the detached merger worktree, so the `refs/heads/sandbar/issue-*` glob the preflight cleanup uses can't reach it, and `resolveMergeMode` rejects a name inside that namespace). It must also *start* with `sandbar/`: the ref is force-pushed every round, so pointing it at a branch someone else uses would destroy that branch on cycle 1, and the lease is no defence against that.
- **Issue branches seed from `origin/<sourceBranch>`,** not local. The preflight emits a soft warning when the **operator's checkout** has local `<sourceBranch>` ahead of origin, because per-issue worktrees won't see unpushed work — the one check that still reads `config.cwd` rather than the cache, and the one place that warning was ever going to be true (#38 item 10).
- **One cleanup registry, and it owns the exit (#35).** `onCleanup` actions run from `cleanup.ts`'s SIGINT/SIGTERM traps, and `runCleanup()` is **async** — it returns to the signal handler at its first await. Node runs signal listeners in registration order, so any *other* listener that calls `process.exit` synchronously truncates the registry wherever it had got to. `agent-sandbox.ts` installed exactly that handler, and since `installCleanupTraps()` runs in `run()` before the first sandbox exists it was always second and always won: every Ctrl-C tore down the agent containers that handler owned and skipped everything else — the per-issue pods and networks, the merger worktree, the run log's terminal write, the lock release — while looking like a clean shutdown, because the one resource class the competing handler could see was the one class that survived. (The pods are reclaimed by the next run's scoped sweep and the lock directory by proper-lockfile's own exit hook, which is why this read as "Ctrl-C leaks a cycle's podman resources and truncates the log" rather than as corruption — and why the then-current `log` follower bullet's claim that a signal removes the pod was false when it was written. That follower is gone with #43, so the claim has nothing left to be false about, but the ordering hazard this bullet is about is unchanged.) So the sandbox teardowns are an `onCleanup` entry — **one**, registered lazily and fanning out over a Set, because that registry never forgets an action — and no module but `cleanup.ts` may trap a signal or exit on one. `process.on("exit")` is the exception and stays: synchronous and last-resort, it covers a bare `process.exit` from elsewhere, which runs no action at all. That is also why the teardown set is **drained** rather than iterated — a signal now reaches it twice, once through `runCleanup` and again through the `exit` event that `runCleanup`'s own exit fires, and twice means a duplicated worktree-preserved notice to the operator. Pinned in `cleanup-signal.test.ts` by SIGINTing a **real child process**: the failure was a synchronous exit from a second listener, so in-process there is nothing left to observe, and a listener-count assertion passes just as happily against a handler that still exits.
- **Single-instance lock.** `src/lock.ts` uses `proper-lockfile` for the atomic acquire plus a `run.pid` sidecar for stale-PID takeover. Don't try to run two sandbar processes against the same workdir. Two against *different* workdirs is supported since #28 — the lock's workdir is also what derives the podman resource scope, so the two mechanisms cover the same partition by construction. **The takeover has to remove proper-lockfile's lock DIRECTORY itself, not call `lockfile.unlock` (#32).** `unlock` resolves against a module-level registry of locks *this process* holds and returns `ENOTACQUIRED` for anything else, so against the only holder a takeover can ever face — a dead **other** process — it was a guaranteed no-op, swallowed, leaving recovery from a crashed run entirely to proper-lockfile's 10s mtime staleness, i.e. to the timer the sidecar exists to skip. It succeeded in exactly one arrangement, the same process locking twice, where the recorded pid is our own and therefore alive and the takeover is never reached — which is also the arrangement a same-process *test* constructs, so the first version of `lock.test.ts` certified the broken path as working. Anything pinning the takeover must cross a process boundary or it is pinning the bug. Removing the dir is gated on positive evidence the holder is dead (`process.kill(pid, 0)` → ESRCH); an unreadable sidecar and pid `0` both fail **closed**, and a removal that fails leaves the sidecar alone because it is the next launch's only evidence. **The lock is taken before preflight, not after (#32).** Preflight is not a read-only phase: it fetches, and `deleteMergedIssueBranches` runs `git branch -D` over every `sandbar/issue-*` branch it finds merged — which made the one operation in startup that mutates the repo the one operation the lock did not cover, reached by both of two racing launches before the loser was turned away. (The branch *classification* is not part of that argument: a concurrent run's in-flight branches map to issues still open and still `ready-for-agent`, since the label flips happen in Phase 4, so they read `resumable` rather than a spurious `unmerged`.) The ordering costs nothing to reverse — `acquireLock` is `retries: 0`, so there is no lock *wait* for a fail-fast config error to duck under; a second launch simply hears "another sandbar is running" first, which is the actionable complaint of the two. Preflight's `process.exit(1)` now `await runCleanup()`s first, which recovers the **sidecar** rather than the lock — proper-lockfile's own exit handler rmdirs held locks even on a bare `process.exit`. Preflight still precedes the orphan sweep and every container operation, which is the dependency those rely on for a working runtime.
- **The credentials are a VALUE, not a path (#38).** `config.env` is a `Record<string, string>`; `envFilePath` is gone, and so is the stale `join(hostRepoDir, ".sandbar", ".env")` fallback in `agent-sandbox.ts`. Semantics are preserved verbatim — an **allowlist**: only keys the config declares cross into a sandbox container, each falling back to `process.env[key]` when its value is empty, so `{ GH_TOKEN: "" }` means "inherit it" exactly as a bare `GH_TOKEN=` line did, and the host environment never leaks wholesale. `env.ts` now owns both readers (`makeEnvReader` for preflight, `resolveSandboxEnv` for the container), which is what keeps them from disagreeing — the invariant two module headers used to restate. Co-locating them was not by itself enough, and the gap outlived the move: `makeEnvReader` fell through to `process.env` for **any** key, declared or not, while `resolveSandboxEnv` iterates only the declared ones. With the new `{}` default that is a green preflight over an empty container — sandbar finds `GH_TOKEN` in its own environment, exports none, and every agent runs unauthenticated for its whole attempt budget, which is the failure the credential check exists to prevent reached through the check. An undeclared key now resolves to nothing in both. `resolveConfig` also validates the record's shape (object, string values, usable variable names), because the dotenv parser used to guarantee it and a value is not a schema. Four reasons this beats a smaller path fix: it is the only way sandbar stops naming a file at a repo root (`.env` is the most contested filename there is — compose auto-reads `./.env` for interpolation, as do Vite, Next and Laravel, and outdoor's `.env.example` had to open by explaining *"the application reads none of this"*); one object is structurally one answer; the parser stops being contract and survives as the opt-in `readEnvFile` exported from the package root, so a host whose compose already owns `.env` passes its own loader's output rather than running two parsers with two escape dialects over one file; and CI needs no file at all. The cost, stated: preflight's credential errors name `config.env` instead of a path, which is a fair trade in a repo whose config line says where it read from. `readEnvFile` **throws** on an unreadable file rather than returning `{}` — an empty record is a legitimate configuration, so a silent fallback would turn a typo'd path into "GH_TOKEN is missing" and send the operator to look at their token instead of at the line naming the file.

- **Promise-token contract.** Agents signal state with a single `<promise>TOKEN</promise>` tag. Implementer: `COMPLETE` (which also means *the worktree is clean* and *HEAD is `refs/heads/<branch>`*) | `NEEDS-INFO` (paired with `<questions>`) | `NEEDS-UI-PROTOTYPE` (paired with `<ui-impact>`). Resolve-loop: `COMMITTED` | `ABANDON` (paired with `<reason>`). Anything else is a no-signal — the loop re-prompts. The orchestrator gates *between* attempts; the agent never decides "this is green".
- **Verdict-token contract.** The reviewer emits a single `<verdict>APPROVED|CHANGES-REQUESTED</verdict>` tag (parsed by `verdict-parser.ts`). Missing or malformed token defaults to `CHANGES-REQUESTED`, but only for a run that PRODUCED something: a run that reviewed nothing never reaches the parser at all (#41), because that default is a statement about the code and a harness fault is not evidence about anything. `containsVerdictToken` is the same regex asked the other question — did the reviewer reach a decision — which is what lets a run that emitted a verdict and then failed count as one. Convergence relies on the bar being sharp, i.e. on the coding standards (the built-in `prompts/coding-standards.md`, plus any project `CODING_STANDARDS.md` that extends them) being precise enough to be deterministic, not on round-trip retries. The reviewer is read-only: prompt instructs it not to modify the branch, commit, push, or run gates.
- **Prompt prose lives in `prompts/*.md`, not in code.** `src/prompts.ts` loads templates and does `{{placeholder}}` substitution; `prompt.ts` and `resolve-loop.ts` load them into module-level consts at import and fill the placeholders. Keep substantive instructional prose in the markdown files; only structural scaffolding (headings, code-fence wrapping, data interpolation, which optional block to include) stays in TS. The `prompts/` dir sits beside `src/`/`dist/` so the same `../prompts` path resolves from both, and is shipped via package.json `files`.
- **Every range a prompt slot renders is anchored at `origin/<sourceBranch>`, never the bare name (#40).** The agents read a linked worktree of the bare cache, whose local head namespace is sandbar's alone and holds exactly one ref — the issue branch — so `main..HEAD` exits 128 there and can never do anything else. All three slots (the implementer's `log -p`, the reviewer's commit list *and* its diff) mapped that onto the empty string, which is indistinguishable from the one legitimate empty answer, "attempt 1 has no commits" — so the implementer was told its own committed work did not exist and the reviewer was handed an empty changeset and asked for a verdict on it, for a whole run, silently. `readGit` now **throws `SandbarError`** on a failed read: the ref is one preflight has already verified in a repo sandbar built, so there is no working configuration in which these fail, and a fresh sandbox reproduces it exactly. Node's `maxBuffer` overflow is the single exception and is not a fault at all — the output is real, so the prefix node leaves on `err.stdout` is returned with a truncation marker rather than halting an issue over a large branch (`readGit` takes the bound as a parameter so that path is asserted against real git instead of a 50MB fixture). On top of that, a reviewer over an **empty changeset is refused outright**: the SM reaches a reviewer only through a `COMPLETE` that `parsePromise` did not downgrade (which requires commits) and a green gate-1, so empty is not "nothing to review" but this module and the inner loop disagreeing about what the branch holds — the backstop that catches the next wrong base ref even when it resolves. The project anchor's `git log` is the one read that still degrades, to `(unavailable)`, and the difference is that this is a visible marker rather than a false claim about the branch. `prompts/reviewer.md` names `origin/<sourceBranch>` too, since a reviewer investigating on its own runs into the identical 128. Both throws leave the inner loop as a `SandbarError` — past HARD-ERROR, so the issue is dropped from the cycle with a loud rejection in the run log and stays `ready-for-agent`, which is the right shape for a fault a fresh sandbox would reproduce exactly.
- **Logs are append-only and unbuffered** (`src/logs.ts`). Crash-safe by construction; don't introduce in-memory buffering.

## This repo runs itself (#39)

Sandbar's own backlog goes through sandbar. `sandbar.config.mjs` at the root is the whole host-side surface, `Containerfile` builds the one image, `sandbar.env` (gitignored; `sandbar.env.example` is the template) holds the credentials, and `npm run sandbar` is the launcher — a **loop** since #65: `git pull --ff-only`, build, `node dist/cli.js`, and around again only on `EXIT_CODE_RELAUNCH` (75, hardcoded in the script — a shell loop cannot import the constant), every other code propagated. Build-and-run rather than `npx sandbar` because this repo *is* the package and there is nothing on PATH; a loop because `relaunchAfterLanding: true` makes every landing cycle exit 75, so an unattended series is always driven by what it just landed — the launch tree supplies `dist/`, the config *and* the Containerfile, while judged trees come from `origin/main`, and letting them drift apart is the #37 genus of silent false verdict arriving through the launcher. The pull at the top closes the launch-time half of the same gap (a checkout was once found 40 commits behind across a `feat!`); a dirty or diverged checkout fails it loud with git's own message.

- **One image, both roles.** The agent sandbox runs it as `--user 1000:1000 --userns=keep-id`; the gate runner runs it as a pod member, where keep-id is impossible and container root is what maps back to the invoking user. So the Containerfile defines an `agent` user at uid/gid 1000 *and* leaves its default `USER` as root — `checkWorktreeImageUids` probes exactly that and refuses the run if it changes. glibc, not alpine, and pinned to the host's node major: `node_modules` is installed on the **host** by the `onWorktreeReady` hook and reaches both containers through the bind mount, so vitest's esbuild/rollup binaries are the host's `linux-x64-gnu` builds. That hook carries an explicit `timeoutMs` because the hook default is 60s and a cold-cache `npm ci` runs close to it.
- **The gate runs the podman layer now, over the host's socket (#48).** `gate-stack-podman.test.ts` and `ensure-images-podman.test.ts` resolve their `describe.runIf` at collection time against `podman image exists`, and there was no podman in the gate runner — so ~35 tests skipped, green either way, over exactly the layer most open issues touch: the settle window's green-on-red, root-in-pod file ownership, `inspect` 125 vs `container exists`, SIGKILL reaping, `logs -f` chunk splitting, per-branch image variants. (The first and the fifth of those retired with the `tcp` and `log` readiness kinds in #43, which is what a socket buys: the layer moved and the gate followed it, instead of the coverage lapsing with the mechanism.) The runner now mounts the host's podman socket (read-only) and sets `CONTAINER_HOST`, which is the entire client change: the plain binary switches to remote mode on that variable alone, so `RUNTIME = "podman"` stands and not one `execFile(RUNTIME, …)` moves. **The gate's test containers are therefore SIBLINGS of the run's own, on one podman, and disjointness is structural rather than a naming convention** — since #47 the test scope is per *process*, `cleanupOrphanContainers` and `sweepBranchImages` are scope-blind by construction, and `findUnattributableResources` reports only names carrying no scope segment at all, so a test's force-remove cannot reach a live stack and the operator's debris report cannot be filled with test noise. Three things ride along. `/tmp` is identity-mounted **rw**, because bind sources are resolved by the *host's* podman and the fixtures those tests build under `os.tmpdir()` are otherwise paths it cannot see (podman then fails loudly rather than mounting an empty directory) — identity is what leaves the test code untouched, and a dedicated `.sandbar/gate-tmp` was rejected because its mount source must exist before bringup and a missing one is a gate red blamed on the branch. `SANDBAR_REQUIRE_PODMAN_TESTS=1` makes an unreachable podman a **failing test** rather than the silent skip this item is about: the day the socket breaks is otherwise the day the gate quietly stops covering what it was given a socket for. And the residual is a named pair of facts rather than a layer, both properties of the client or of the host's own session rather than of a container: `podman exec` exits 0 on SIGTERM only for a **local** client, and whether podman created a transient systemd timer is a question about the *host's* user session, which the runner (a container with none) cannot ask — so those assertions live in `gate-stack-hostpodman.test.ts`, guarded on the client being local (which skips even under the require flag: unreachable and not-local are different axes). #43 rewrote that pair without changing its size: the tcp topology facts left with the kind, and the systemd one arrived; the property that replaced tcp's — a dead port and a live one separating outright — is asserted *inside* the container, so the gate runs it every attempt. **The human's step is that file and — since #44 — `sandbox-stack-podman.test.ts`,** which is host-only for a reason close to the first's: it builds its anchor with the production `sandboxRunArgs` (keep-id, uid 1000) and then `podman exec`s in as the agent, so *the invoking user* has to be whoever runs the suite rather than whoever owns the socket. Note what is no longer the reason there: #43 took the `tcp` kind and its host-side publish out, so every sibling's probe would survive the socket perfectly well — only the anchor keeps that file where it is. **It was three files until #52, and what left is the shape to watch for.** `agent-sandbox-podman.test.ts` declared `needsLocalClient` on an explicit *unknown* — whether `--init` reaping observes the same way through a remote client had never been established — which is not what that flag is for, and it held a whole file out of the gate for as long as nobody measured it. Measured, it survives: every assertion in it is made *inside* the container by `podman exec`ing a `/proc` read, so the caller's netns, filesystem and signal handling (the three things that keep the other two host-only) are all out of the path. It is named in `podman-test`, which — with #45's `gate-run-podman.test.ts` beside it as the step's fourth file — reports **59 tests, 0 skipped**, counted with `vitest list` on this tree rather than carried forward from the 44 #52 measured over three files (#45 added that fourth, six more in `gate-stack-podman.test.ts` and two in `ensure-images-podman.test.ts`). That fourth file needs no `needsLocalClient`: it drives `runGateCommand` end to end and asks nothing about the host's own session, so every podman call in it goes through the same client as the rest. The total moves whenever a podman test is added, so a later mismatch is evidence that this number went stale rather than that a layer stopped running; what #52 was worth is the **two**. Both remaining files declare `needsLocalClient`, so host-only is a property each file enforces rather than one that survives only as long as the config's exclude glob and its by-hand `podman-test` file list agree — and the prose is load-bearing in both directions: describing the step as one file leaves the other's assertions exercised by nobody, and describing it as three sends a human to re-run what the gate now runs every attempt.
- **`mergeMode` stays `direct`, and hosted CI is out by choice.** #39 proposed closing the blind spot above with `mergeMode: "verified"` over a GitHub Actions job — the mode's stated purpose verbatim, an independent verdict the local gate cannot buy. It was built and then removed: this is a personal project, its tests belong on host machines, and no cycle should wait on a hosted runner. The trade was stated rather than hidden, and #48 has since paid most of it back: the podman layer is covered by the gate itself, and what a human still runs by hand is two files — the pair of local-client facts in `gate-stack-hostpodman.test.ts` and `sandbox-stack-podman.test.ts`'s anchor chain (#44). (`agent-sandbox-podman.test.ts`'s `--init` reaping was the third until #52 measured it through the socket and moved it into the gate.) Note the two are ONE unit if it is ever reinstated: `requiredChecks` must name the job exactly as the forge reports it, because a required name that never appears is `missing-required`, fatal every cycle by design. `.github/workflows/` holds only `auto-tag.yml`, which is release bookkeeping and gates nothing.
- **Bootstrap ordering.** The orchestrator driving a cycle is whatever `dist/` held at **launch** — which, since #65's relaunch-after-landing, is at most one landing old: a queued chain of outer-loop issues runs slice N's code while building slice N+1, instead of running the series-start code for the whole series. That is the strongest form self-hosting can have, and it sharpens the residual rather than removing it: a merged regression in the outer loop now mis-drives the very next cycle *unattended*, one relaunch later. Recovery is a hand `git revert` while preflight refuses to start on the leftover branches. Keep issues touching `run.ts`/`inner-loop`/`merger` serialized (blocked-by) rather than parallel, so a regression has only one downstream slice in flight when it bites.
- **The suite must not depend on ambient git config.** The gate runner has no global identity (nor would any hosted runner), so a test whose *production code under test* shells out to git with plain `process.env` needs a repo-local one (`forge-verify-git.test.ts` sets it on the merger-worktree stand-in). Setting `GIT_*` on the test's own calls does not reach the adapter's.
- **Nor on the ambient working directory being a repository.** The gate runner mounts the worktree at `/workspace` and nothing else, so `/workspace/.git` is a gitlink to a `.sandbar/repo.git/worktrees/<branch>` path that exists only on the host — and a *broken* gitlink is a fatal 128 from git's gentle setup, not a shrug, so it sinks even `git config --global`, which needs no repository at all. Any git call in a test that inherits `process.cwd()` therefore passes on a developer's host, where that path resolves, and fails only in the gate (`agent-sandbox.test.ts`'s identity test did exactly this, #25). Name the directory: a temp dir for a `--global` read, the fixture repo otherwise. It reproduces without podman — run the file from a scratch directory holding a `.git` file that points nowhere, `vitest run --root <repo> <file>`.

## When making changes

- **Strict TypeScript** — `strict`, `noUncheckedIndexedAccess`, `noImplicitOverride`. Array/Map lookups are `T | undefined`; handle accordingly.
- **`*.test.ts` files are excluded from `tsc`** (see `tsconfig.json`) but checked by `vitest`. The strict type-checking gate is on production code only.
- **Always import with `.js` extensions** even from `.ts` files — NodeNext resolution.
- Module headers (the long comments at the top of `src/*.ts`) are the authoritative architecture notes per module. Update them when behavior changes; future Claude reads them first.
