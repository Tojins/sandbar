# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm run build` — compile `src/` → `dist/` via `tsc` (also runs on `prepare`).
- `npm run check` — type-check only (`tsc --noEmit`). No lint tool is configured; this is the only static gate.
- `npm test` — run the Vitest suite (`vitest run`, non-watch).
- `npx vitest run src/plan-resolver.test.ts` — run a single test file. Add `-t "<name>"` to filter by test name.

Node ≥ 20 is required. The package is ESM (`"type": "module"`); imports inside `src/` use the `.js` extension even when the on-disk file is `.ts` (NodeNext resolution).

## What this package is

`@offergeist/sandbar` is a **library**, not a CLI. It exports `run(config: RunConfig)` from `src/index.ts`. A host repo wires it up by supplying its own `Containerfile`(s), env file, anchor docs (`CLAUDE.md`, `CONTEXT.md`, optional ADR dir), and a **gate stack** — the containers and steps that produce a verdict about a commit (`config.gateStack`, #24). The reviewer's coding standards ship built-in (`prompts/coding-standards.md`); a host may optionally extend them with its own `CODING_STANDARDS.md` (`config.codingStandardsPath`) but is not required to. Sandbar then drives an issue-tracker-driven (GitHub Issues via `gh`) coding-agent loop against that host.

## Architecture — the four-phase outer loop

The orchestrator (`src/run.ts`) cycles plan → execute → merge → finalise until an exit condition fires. Each phase has a dedicated module and the dataflow between them is intentionally narrow.

1. **Phase 1 — Plan** (`src/plan-resolver.ts`): purely deterministic. Lists GitHub issues labelled `ready-for-agent`, parses each body's `## Blocked by` section, and selects the top-K unblocked issues (default 3) sorted by issue number. No LLM involvement.

2. **Phase 2 — Inner loop** (`src/inner-loop.ts` + `src/inner-loop-machine.ts`): each planned issue runs in parallel (`Promise.allSettled`) inside its own agent sandbox + per-issue gate stack (a podman pod on a podman network). The issue worktree is prepared **before** the sandbox/stack pair starts (stack `mounts` bind-mount fixture files from it). The inner loop is ralph-style — up to `maxImplAttempts` (default 8) attempts in the **same** sandbox so commits accumulate on the issue branch.
   - All transitions live in a pure state machine (`inner-loop-machine.ts`); `inner-loop.ts` is I/O glue that executes the action the SM emits and feeds the result back as an event.
   - Per attempt: build 3-layer prompt → run implementer agent → parse `<promise>` token (`promise-parser.ts`) → if `COMPLETE` **and the worktree is clean and HEAD is still the issue branch**, run **gate-1** (the host's gate steps in the issue's stack, `gate-stack.ts`). `COMPLETE` over a dirty tree is re-prompted to commit instead, and a HEAD that has wandered off `refs/heads/<branch>` is re-prompted back onto it (once) — see the clean-tree and on-branch invariants below. On gate-1 green, run the **reviewer** — strictly advisory, never commits — which emits `<verdict>APPROVED|CHANGES-REQUESTED</verdict>` (parsed by `verdict-parser.ts`). On `APPROVED` → `DONE`. On `CHANGES-REQUESTED`, the prose is stashed and the loop runs another implementer attempt with the prose surfaced in its prompt.
   - **Two orthogonal budgets.** Each implementer pass consumes one of `maxImplAttempts`; each reviewer pass consumes one of `maxReviewRounds` (default 5). Exhausting impl attempts → `NEEDS-HUMAN` (last gate trace). Exhausting review rounds → `NEEDS-HUMAN-REVIEW` (latest reviewer prose).
   - **HARD-ERROR is for infra failures only.** The SM never emits it; the runner wraps unhandled exceptions (setup, container) as HARD-ERROR so the outer-layer `decideAfterTerminal` can retry with a fresh sandbox (up to `HARD_ERROR_MAX_RETRIES = 2`).
   - **UI-prototype escalation (#21).** An implementer that judges the issue to imply non-trivial *user-visible* UI with no prototype in the issue emits `<promise>NEEDS-UI-PROTOTYPE</promise>` + a `<ui-impact>` block and terminates immediately — no gate, no reviewer, no retry. The judgment is the agent's alone (there is no deterministic detector, and it must fire before a diff exists); the prompt's tiebreak is "when unsure, escalate". Deliberately not guarded on zero commits: a late escalation beats a merged guess.
   - Terminals: `DONE | NEEDS-INFO | NEEDS-UI-PROTOTYPE | NEEDS-HUMAN | NEEDS-HUMAN-REVIEW | HARD-ERROR`.

3. **Phase 3 — Merge** (`src/merger.ts` + `src/resolve-loop.ts` + `src/merger-worktree.ts` + `src/forge-verify.ts`): procedural. Runs in a **dedicated ephemeral worktree** detached at `origin/<sourceBranch>` (`createMergerWorktree`), never the operator's primary checkout — so uncommitted operator edits can't be swept into a merge commit (issue #10). For each DONE branch in ascending issue order: capture `preMergeSha`, `git merge --no-ff`, then either succeed and push, or invoke the **agentic resolve loop** for conflict OR post-merge-gate-red. The resolve loop sees the bodies of all sibling issues in the cycle so it can reason about cross-branch intent collisions. On `<promise>ABANDON</promise>` or budget exhaustion, the merge is reverted to `preMergeSha` and the branch is skipped. The operator's local branch fast-forwards on their next pull.

   **How the cycle lands is `config.mergeMode` (#22).** `direct` (default) is a single `git push origin HEAD:<sourceBranch>` at the end. `verified` gives the forge the last word (`src/forge-verify.ts`): force-push the merge result to a scratch `integrationBranch`, poll **that sha's** check runs, and only green earns `git push origin <sha>:<sourceBranch>`. Red feeds the failing jobs' logs (capped at `MAX_FAILED_JOB_LOGS`, elision stated in the trace) to the resolve loop in `forge-red` mode; with `VERIFY_MAX_ROUNDS` rounds the loop gets at most `VERIFY_MAX_ROUNDS - 1` shots, since the last round's red is terminal. The loop's own local gate is then only a cheap pre-filter between expensive CI rounds, never the verdict. Cost is one CI run per cycle when green, up to `VERIFY_MAX_ROUNDS` otherwise — and a round is also consumed with no agent involvement when `origin/<sourceBranch>` moves and the result has to be re-merged.

   **Reading the checks is the whole safety argument, and six things independently break it** — each has been a real green-on-red: the listing must be **paginated** and cross-checked against `total_count`, counting **distinct run ids** (a truncated read of an all-green first page is not a verdict, so an incomplete listing is `pending`; and because the pages are unordered and fetched separately, a run can come back twice while another never does — counting rows would hit `total_count` with the red one unread. A missing `total_count` or run id throws rather than defaulting); supersession is per **(suite, name)**, never per name (two suites legitimately report the same job name, and collapsing them lets one suite's success erase another's failure); a green snapshot must **settle** across `GREEN_SETTLE_POLLS` identical polls (`workflow_run` chains and `fromJSON` matrices create checks *after* earlier ones conclude); `skipped` is **not** a pass (a job the `if:` guard skipped ran nothing); and an **unfinished check outside `requiredChecks` still holds the verdict up** — it will conclude, and it can conclude red, so skipping past it would make green mean "everything that had finished when I looked was fine". The forge also reports verdicts in a *second* place — the legacy commit-status API, which Buildkite/Jenkins/older deploy apps use and which creates no check run — so failing statuses are folded in as synthetic `status:<context>` runs. That fold is deliberately one-way: a failing status turns a verdict red, a pending one is never waited for (third-party integrations leave statuses pending forever), so it can never manufacture a green or a new way to hang. On top of those, `requiredChecks` is mandatory and non-empty — it is the floor of checks that must *exist*, the only way to distinguish "hasn't started" from "will never run". A check outside that list still sinks the cycle if it fails. And the exist/never-exist distinction is *acted on*: a required name still absent once every other check on the sha has concluded, held for the grace window, is `missing-required` and fatal — a name that doesn't match what the forge publishes (`test` vs `test (20.x)`) is the likeliest misconfiguration there is, and parking on it spends a full CI timeout every cycle.

   Verification failure is a **cycle-level** outcome (the forge judged the composed result; the red isn't attributable to one of several individually-gated merges), so the whole cycle resets to the sha the merger worktree started at, `merged` comes back empty, and every merged issue is skipped as `forge-unverified` with a comment naming the **verified sha** (not the scratch branch, which the next cycle overwrites) and saying it may not be the one at fault. The comment's lede is written from the *reason*: on `source-moved` the checks passed and the cycle lost a race, on `checks-timeout` nothing was rejected at all — telling an author their build failed when it went green sends them to read a passing log. If the resolve loop committed fixes during verification, the comment says those commits are being discarded — they live on the merge result, not on the issue branch. **Parked vs fatal is a judgment about whose failure it is:** checks that never conclude park (CI was slow); anything that is a property of the repo rather than of this cycle's code is `fatal`, because it recurs every cycle and parking would quietly convert the whole backlog to `agent-stuck`. Fatal covers: a sha the forge never builds at all; a required check name that never appears; a rejected integration push; a fast-forward refused while `origin/<sourceBranch>` turns out **not** to have moved (a successful re-merge that produces no commit proves the branch is where it was, so the refusal was branch protection, a hook, or a token without push access); and anything thrown out of the landing itself — an unreachable forge for `CHECK_POLL_MAX_CONSECUTIVE_ERRORS` polls, an unreadable response. All of them arrive as `MergerError` → loud halt, and `MergerError.partial` carries the tracker state already applied so Phase 4 still runs for those issues before the halt. That wrapping is load-bearing rather than decorative: verified landing runs *after* earlier issues in the cycle were commented and de-labelled, so a raw throw would leave them on no queue and under no handoff label. **The same wrapping covers the per-issue loop (#33)**, where the writes actually originate and where the throw sites are not hypothetical: `getIssueBody` throws `SandbarError` by design (a resolve agent reasoning about cross-branch intent without the issue specs is worse than a halted merge phase) and runs at the top of every resolve loop, and `runGate` throws rather than reddens when an `issue`-lifecycle container has died under it (#24 D5). Either one arriving on the second branch of a cycle strands the first. `partial.merged` is `[]` on every one of these paths, never the local `merged` — a halt means nothing landed, which holds by construction because the merges exist only in the ephemeral merger worktree; `run.ts` asserts it, so forwarding them would trade one halt for a more confusing one. That an unexpected throw can leave that worktree mid-merge is not an objection: the partial describes tracker writes already durable on the forge, not the state of a directory about to be deleted. **The wrapping stops the instant the cycle lands** (`landed` in `runMergerWithAdapter`), and that boundary is the point: past the push, `merged: []` and `pushed: false` are lies, and a partial that lies is worse than none — run.ts would report a halt, finalise only the skipped, and leave landed issues open, queued and unclosed against a source branch that has already moved. Throws *before* the first tracker write are left raw for the mirror reason (nothing to carry, and the top-level handler prints a stack this branch does not). The log sink is inside the boundary, not outside it: `emit` wraps its own failure, because `no merges, no push` fires exactly when every issue in the cycle was parked and an ENOSPC there would strand all of them. One residual window is accepted and known: the verified path's fast-forward happens inside `runVerifiedLanding`, which logs one line after it, so a throw from that single write is still wrapped and would report `merged: []` against a branch that did move (`fastForwardSource` catches and returns `rejected`, so that log line is the whole of it). And because run.ts's merger-halted branch never reaches the top-level handler that prints stacks, `asHalt` attaches the original error as `cause` and that branch prints its stack for anything that is not an operator-actionable `SandbarError` — otherwise wrapping would make unexpected bugs *quieter* than leaving them raw. A fast-forward rejected because `origin/<sourceBranch>` genuinely moved mid-verification is neither: the composed result changed, so it is re-merged and **re-verified**, consuming a round. Landing is always a fast-forward of locally-authored commits, so `openPullRequest` changes attribution not at all — the PR is an audit/review handle the forge marks merged on its own (create-or-**update**: a PR surviving an earlier cycle is re-titled, never left describing issues it no longer contains).

4. **Phase 4 — Finalise** (`src/finalize.ts` + `src/finalize-inputs.ts`): per-issue branch lifecycle (push/delete worktree + branch), bot-prefixed issue comments, label flips (`ready-for-agent` ↔ `labels.needsInfo`/`labels.agentStuck` — those are the only two sandbar ever applies). The `needs-ui-prototype` input reuses the needs-info label (same human round-trip: supply the missing artifact, re-label) but pushes the branch **only** when the escalation arrived after commits — otherwise there is nothing to hand over and pushing would publish a ref identical to the source tip, so the empty branch is deleted instead. That delete escalates to `-D` only once `branchIsContainedInOrigin` confirms the branch holds nothing unpushed: `hasCommits` is per-sandbox-cycle, so a HARD-ERROR retry reports `false` while an earlier attempt's commits are still on the branch. **A `git branch -d` refusal is never on its own a licence to force** — it also fires when the local source branch merely trails origin. Pure orchestration via `FinalizeAdapter`; the real adapter shells out to `git`/`gh`. The `review-budget-exhausted` input pushes the branch and posts the **latest reviewer prose only** (not the per-round transcript — that stays in the run-log for offline diagnosis).

   **It runs in two passes, straddling the merge (#30).** The inputs are built by two pure functions in `finalize-inputs.ts`: `terminalFinalizeInputs` over Phase 2's non-DONE terminals, `mergeFinalizeInputs` over the merger's merged/skipped lists. The first pass runs **before** Phase 3, because nothing in it depends on the merge having happened, and the merge phase has more than one way to throw something that is not a `MergerError` — since #24 a `ContainerBringupError` from the merger stack is the live one. Finalising afterwards meant that throw escaped to the top-level handler and exited before a single write, discarding the whole cycle's Phase-2 output — NEEDS-INFO questions unposted, NEEDS-HUMAN traces unposted and unparked (so the issue kept `ready-for-agent` and burned another full attempt budget next run), reviewer prose gone — for a failure that happened after all of it and had nothing to do with it. `MergerError.partial` is unaffected: it still carries the tracker state the merger had already applied, and the second pass finalises it before the halt. The mirror-image risk is accepted as strictly smaller: a required side-effect failing in the first pass now stops the cycle before the merge, but a DONE branch that misses its merge keeps its commits and its `ready-for-agent` label, so preflight classifies it `resumable` (#13) and the next run continues from it. That resume is not automatic once the pass has parked anything — an `agent-stuck` issue is an open issue no longer queued, so its leftover local branch is preflight-`unmerged` and refuses the next run until the operator clears it, which is the steady state every successful parking cycle already produces and costs a `git branch -D` against a branch already on origin. The prose an agent produced once and nobody stored has no such fallback. One knock-on worth knowing: `getIssueBody` renders comments, so the resolve loop's sibling-issue context now includes the handoff comment a sibling earned this cycle — context rather than noise, and bot-stamped, but those comments are addressed to a human and phrased as imperatives.

### Exit conditions (`src/exit-conditions.ts`)

The outer loop terminates on the first of:
- **plan-empty** → success (exit 0)
- **stuck-same-plan** — same plan as previous cycle AND 0 DONEs this cycle (exit 2)
- **stuck-zero-dones** — `MAX_CONSECUTIVE_ZERO_DONE_CYCLES = 2` (exit 2)
- **budget** — `issuesAttempted >= maxTotalIssues` (default 50, exit 3)

`MAX_ITERATIONS = 100` in `run.ts` is a defensive ceiling — the conditions above terminate first.

`SILENT_NOOP_RETRY_LIMIT = 2` caps per-issue retries when the resolve-loop reports `resolved` but HEAD did not advance (the "silent `git merge --abort`" failure mode). Under the cap, the branch is discarded and the issue stays `ready-for-agent` for the next cycle's planner.

## Key design constraints

- **Pure decision functions where possible.** The inner-loop state machine (`step`, `decideAfterTerminal`), `parsePromise`, `parseVerdict`, `renderReviewerSlot`, `resolvePlan`, `applyCycle`, `checkInvariants`, `finalizeOne` are all pure functions over their inputs. I/O wrappers (`fetchCandidates`, `realAdapter`, etc.) are thin shells around them. Add tests against the pure layer; don't mock `gh`/`git` if you can table-test the decision instead.
- **Adapters for I/O boundaries.** `MergerAdapter`, `FinalizeAdapter`, `ResolveAdapter` define the contract; tests use fakes, production uses `realAdapter(...)`. Don't reach for `execFile` from new code if there's an adapter slot. The *real* adapters are the blind spot in that scheme — a fake satisfies the contract no matter what argv the real one builds — so `realVerifyAdapter` takes an optional `exec` seam and its argv/parsing are table-tested (`forge-verify.test.ts`), with the git primitives exercised against actual repos in `forge-verify-git.test.ts`. Behaviour that git defines is asserted by running it, not by asserting the command string: does a non-ff push reject rather than clobber, does a failed merge leave `MERGE_HEAD` (and *where* — in a linked worktree it is under `.git/worktrees/<name>/`, which is why `isMergeInProgress` asks `git rev-parse --git-path` instead of stating a path), which stream does `git merge` write `CONFLICT` to (stdout, so a reason built from stderr alone loses it), and how much the scratch ref's `--force-with-lease` really protects (only against a write landing between the `ls-remote` and the push — it is read fresh each round, so anything already on the ref is overwritten. That is intended for a ref sandbar owns, and is why config confines `integrationBranch` to the `sandbar/` namespace). The gate stack gets the same treatment (#24): its argv builders (`containerRunArgs`, `podCreateArgs`, `stepExecArgs`, `mountSpec`, `parsePortBindings`) are pure and table-tested in `gate-stack.test.ts`, and what *podman* defines is asserted by running podman in `gate-stack-podman.test.ts` — that a connect to a published port succeeds with nothing listening (hence the settle window), and that a pod container running as root writes worktree files owned by the invoking user (hence dropping `--userns=keep-id` is survivable). That file skips itself when podman or its image is unavailable, resolved at **collection** time: a `runIf` flag set in `beforeAll` arrives too late and silently skips everything, which is a test file that passes by never running. The podman file also pins what `ok` alone cannot: that an `issue` container keeps its **container id and its state** across gate runs while the `attempt` container gets a new id (an `ok`-only assertion passes both the recreate-the-database-every-attempt regression and the reuse-stale-code one), that a red gate carries the log of a container the failing step never ran in (D9 asserted on a single-container stack is vacuous), and that an `attempt` container which will not come up is a gate red while a dead `issue` container throws. `checkWorktreeImageUids` takes a `UidProbe` seam for the same reason — the D3 rule decides whether a run proceeds at all, and its argv (`--entrypoint id`, not a trailing `id -u`) is the whole argument.
- **Every shell-out names the repo; nothing inherits `process.cwd()` (#34).** `config.cwd` is what the lock, the podman scope, the worktrees, the merges and the tracker writes are all about — and `DEFAULT_CWD()` is `process.cwd()`, so on the author's own checkout the two coincide and an omitted `cwd` is invisible. On a host that sets `config.cwd`, which the config explicitly supports, preflight was inspecting *and* `git branch -D`-ing a different repo from the one the run belonged to (which also quietly qualified #32: the destructive delete was under *a* lock, just not the one covering the repo it deleted from), `ensureIssueBranch` wrote the issue branch into that repo, `prepareWorktree`/`createSandbox` rooted the whole worktree tree there while `worktreePathFor(config.cwd, …)` computed somewhere else, `fetchCandidates` read its tracker for both the plan and preflight's resume classification, and the implementer's and reviewer's anchor layers quoted its history and its issues. The parameter is therefore **required and positional** everywhere it was threaded (`runOk`/`captureOk`, `ensureIssueBranch`, `fetchCandidates`, `fetchIssueText`, `ProjectAnchorOptions`, `InnerLoopConfig`): an optional `{ cwd }` is precisely what went missing, and it goes missing silently. The remaining exceptions are principled rather than leftovers — `fetchIssueStates` names the repo in its GraphQL variables, and `worktreeRemove` derives the repo three levels up from the worktree path (which is sound only while `workDir` is a single path segment, and nothing validates that). Podman calls need no cwd at all, being host-global; preflight's `image exists` is threaded anyway because `runOk` takes the parameter unconditionally, and that is the one call in the module where a bad `cwd` would turn a true answer into a false one — `execFile` fails `ENOENT`, `runOk` swallows it, and every image is reported missing with a `podman pull` line that will succeed and not help. `acquireLock` mkdirs the directory before preflight runs, so it is not reachable today. **The two path classes are handled differently on purpose.** `envFilePath` is resolved against `cwd` once, in `resolveConfig`, because every consumer (run.ts's GH_TOKEN check, preflight's credential invariants, the sandbox's env resolver) only ever reads it on the host. **`cwd` itself is resolved to absolute in the same place, and that is not tidiness.** Now that every git call runs *with* `cwd` as its working directory, a relative one is applied twice: `worktreePathFor("sub/repo", …)` is passed as an argument and re-resolved against `<launch>/sub/repo`, which real git turns into `sub/repo/sub/repo/.sandbar/worktrees/merger`. Preflight's `worktree remove` survives it on git's suffix-match fallback; `merger-worktree.ts`'s `worktree add` does not, and podman rejects a relative `-v` source outright, so `merger.ts`'s `-v ${cwd}:/workspace` would fail every resolve-loop attempt. Fixing it at the source is what makes the per-call-site threading safe — and it retires the first half of #28's scope argument (two repos configured `cwd: "."` can no longer hash one scope) while leaving the symlink half exactly where it was, which is why `run.ts` still canonicalises with `realpathSync` rather than `resolve`. `claudeMdPath`/`contextMdPath`/`adrDir`/`codingStandardsPath` must stay exactly as the host wrote them, because they are emitted as `@refs` the agent resolves from the repo root *inside its sandbox* — so only the host-side `existsSync` probe is rooted at `cwd`, and that probe is silent in both directions (a real `CONTEXT.md` dropped from the prompt, or a dead `@ref` handed to the agent). **Known residual, pre-existing and NOT fixed here:** `cwd` is the host checkout while the agent reads the issue **worktree**, which is seeded from `origin/<sourceBranch>` — so the probe and the reader still disagree whenever the file is uncommitted on the host (probe says exists, agent finds nothing) or is added by the branch itself (probe says absent, so a reviewer judging the commit that adds `CODING_STANDARDS.md` is handed no `@ref` to it). #34 was about naming the wrong repo; this is naming the wrong tree, and it wants the worktree path threaded into both anchor builders. Pinned against two real repos with `process.cwd()` pointed at the wrong one (`preflight-git.test.ts`, `git-ops.test.ts`, `prompt-cwd.test.ts`) and, for `gh`, through a shim on PATH that echoes its own working directory (`plan-resolver-gh.test.ts`). **Every half of the fix is pinned by at least one assertion that fails when that half alone is reverted, which is the property worth stating** — not that every assertion in those files is a cwd pin. Two are deliberately not: `leaves an unmerged branch alone` is a merged-ness assertion, and the `MERGE_HEAD` pair pins the `resolve(cfg.cwd, gitDir)` half rather than the exec-cwd half. The trap those files exist to avoid is a test that stands in the same directory it configures — it passes just as happily with the fix deleted, which is why the converse case chdirs to the *other* repo instead of the one it points config at. **The `gh` calls are the standing gap:** they name a directory, never `--repo ${ghOwner}/${ghRepo}` the way `forge-verify.ts` does, so a `cwd` whose `origin` disagrees with the configured `ghOwner`/`ghRepo` splits sandbar's tracker access in two — `fetchCandidates` lists from one repo while `fetchIssueStates` resolves the same numbers in the other — and nothing validates the agreement.
- **Per-issue isolation, inside a per-run scope.** Every issue gets its own podman network (`sandbar-<scope>-net-<id>`), pod (`sandbar-<scope>-pod-<id>`) and containers (`sandbar-<scope>-<id>-<name>`); the merge phase gets the same under `merger`, and the agent sandbox is `sandbar-<scope>-<uuid>`. `cleanupOrphanContainers` sweeps stale prefixed resources at start and between cycles — **including pods**, which is not tidiness: a pod's infra container is named `<pod-id-prefix>-infra` (a podman hash) and matches no sandbar prefix, so a container-only sweep would leave the pod and its network alive forever. The naming prefixes are centralized in `src/naming.ts`, which also lists the legacy `sandcastle-*`/`sandcastle/*` prefixes.
  - **`<scope>` is `w` + 8 hex of the workdir the run locked (#28), and it is a safety property, not a namespacing nicety.** Podman names are host-global while the lock is per-workdir, so two runs against different repos each hold their own lock legitimately and then collide — and both halves of the collision were destructive: `startStack` force-removes a namesake pod before creating (a survivor of a crash is stale and must never be reused), which reached into the sibling's *live* stack; and the sweep force-removes by prefix at startup and between cycles, which by name alone could not tell "orphan of a dead run" from "live resource of another run". The scope is what makes that distinction decidable — one lock ⇔ one scope, so anything in this run's scope is this run's or a dead predecessor's on the same workdir. Everything outside it is invisible. **The two must partition the host identically, and that is the caller's job, not the hash's:** `proper-lockfile` resolves symlinks on the path it locks, while `resolveConfig` passes `config.cwd` through untouched, so `run.ts` hashes `realpathSync(lockPaths.workDir)`. Hash the configured string instead and two repos both configured `cwd: "."` get one scope and two locks — #28 verbatim — while one workdir reached through a symlink gets one lock and two scopes, stranding its debris in a scope nothing computes and nothing reports.
  - **Image tags are the one podman resource class the scope does NOT partition** — they are host-supplied names and `config.images` maps tag → Containerfile. Two workdirs sharing a `sandboxImage` tag on one host will race the build and then silently share whichever image won, built from one repo's Containerfile. On a shared host, give each workdir its own tag. The per-branch tags `rebuildOn` creates (#37) are the exception and are scoped, because sandbar picks those names — see below.
  - **What the sweep can no longer attribute it reports rather than removes.** `findUnattributableResources` names pre-scope `sandbar-*` and legacy `sandcastle-*` debris at startup with copy-pasteable `podman` commands. Not "remove it anyway, it's probably old": a pre-#28 sandbar running concurrently is precisely the case here, and a wrong guess is silent and destructive. The leading `w` in the scope is what keeps this decidable — a uuid's first segment is also 8 hex, so without it the old `sandbar-<uuid>` sandbox name would read as scoped. Accepted residual: a scope whose workdir never runs again leaks its debris, since no live run may claim it — the price of never destroying a sibling. The report therefore repeats every startup until the operator acts; nothing else clears it. Neither function is allowed to be silent about podman failing, and the two halves differ on purpose: a failed **list** throws (a blind sweep cannot know what it missed, so continuing would assert "no debris" on no evidence), while a failed **remove** is collected into `SweepResult.failures` and reported (it knows exactly what leaked, and `startStack` force-removes a namesake next cycle — throwing would let one wedged leftover block every future run). Preflight already hard-fails on a missing runtime before the sweep runs, so the old "runtime not installed" excuse for swallowing either was unreachable.
- **Container runtime is podman.** Hard-coded `RUNTIME = "podman"` in `src/runtime.ts`; the agent sandbox uses the in-house `podman()` provider (`src/agent-sandbox.ts`), now constructed with an explicit `imageName: config.sandboxImage` rather than falling through to `defaultImageName(repoDir)` (which silently coupled the image to the host's *directory name*, #24 D7).
- **The gate stack is config-driven (#24).** `config.gateStack` (REQUIRED — what it takes to test this repo is repo identity, no preset) is `{containers, steps}`. A container carries image, `lifecycle`, env, image `args`, read-only `mounts`, `mountWorktree`, `servesWorktree`, `hold`, `readiness` + `readinessTimeoutMs`, `postReadyCommands`. A step is `{name, in, command, timeoutMs?}` — argv `podman exec`'d in a named container, bounded per step (#26). Milliseconds, not the `timeoutSeconds` #26 proposed: two units inside one `gateStack` literal is worth more than writing `900` instead of `900_000`. `resolveGateStack` validates all of it at resolve time (before the lock), because every one of those mistakes otherwise surfaces as an opaque podman error minutes in: unknown `step.in`, duplicate container names, duplicate step names (compared **trimmed** — the rule exists so the failing step is identifiable in the trace, and `test` and `test ` render identically there), `hold` + `args`, a relative or `/` `mountWorktree`, a colon in **any** mount path including `mountWorktree` (which every valid stack has, so it is the most-travelled `-v` spec sandbar builds), a relative `containerPath` or empty `hostPath` (empty resolves to the worktree *root*), an empty `postReadyCommand`, a container setting the reserved `CI` key (sandbar applies it last, so the consumer's value would be silently lost), a NaN or non-positive timeout — `readinessTimeoutMs` **and** `step.timeoutMs`, since node reads `timeout: 0` as "no bound" and NaN compares false against every deadline, so both are the one value a bound must never silently become — **two containers on the same `tcp` readiness port** (pod members share a namespace so only one can listen, and the single publish would report both ready as soon as either binds — the settle window's green-on-red, re-entering through config), **a stack where nothing mounts the worktree** — which would return the same verdict for every commit, green included — and **`lifecycle: "issue"` on an un-held container that mounts the worktree** — it boots branch code at bringup, which contradicts D5's definition of `issue` (depends only on image + env, which is *why* its bringup failure is infra) and so blames the environment for a branch that breaks its own startup. Scoped to **un-held** deliberately: under `hold` the entrypoint is `sleep infinity` and nothing of the branch's runs at bringup, so `issue` is honest there — and it is the only home for per-issue setup, since `postReadyCommands` run once per *container* while an `attempt` container is recreated every gate run. That shape re-opens the misblame window through its own `postReadyCommands`, which is the consumer's argv and the consumer's call. `mounts` is what an issue container uses when it only needs fixture files from the worktree. The check runs **after** the reachability rule below, because #29's own reproducer trips both and only the reachability error names the reported symptom — fixing the lifecycle first would just hand back a config that throws the other error next run.
  - **The steps must be able to see the code, and that is not structurally decidable (#29).** "Something mounts the worktree" is satisfied by a stack whose every step runs in a container that cannot see the branch — the same verdict for every commit, verbatim the failure the check claims to prevent. But the fix is not "every step's container mounts it": an app that mounts the worktree and serves it over 127.0.0.1 to a playwright container is correct and fails that. The two are byte-identical in config (a stale mount a refactor left on a database looks exactly like the app, and a realistic database declares `readiness` too, so readiness separates nothing). So the **sound** half is enforced — at least one worktree-mounting container is stepped into, which every ordinary stack satisfies for free — and the serve-over-loopback shape declares itself with `servesWorktree: true`. That declaration is itself checked where it is decidable: rejected on a container that mounts nothing (nothing to serve), and on `hold` **with no `postReadyCommands`** — `sleep infinity` plus nothing exec'd after it is a container that provably runs nothing. Held *and* daemonizing from a `postReadyCommands` entry is accepted, since that is the only route for an image whose ENTRYPOINT is not a shell. A **throw, not a warning**, because the failure mode is silent and green — a startup warning scrolls past and the gate merges broken code until someone re-reads it.
  - **One pod, not an anchor chain.** Containers share a network namespace via `podman pod`, so the stack addresses itself as `127.0.0.1` and publishes nothing *for its own use* (a `tcp` readiness port is published loopback-only on an ephemeral host port, because the probe runs on the host — see below). The `--network container:<anchor>` pattern is a docker tax sandbar doesn't owe: the anchor owns the `--dns` flags and its removal destroys the namespace, so an anchor can never be a per-attempt container. The pod holds the #18 resolvers and survives every container's removal, so `anchor` never appears in sandbar's config.
  - **`lifecycle` decides whose failure a failed bringup is (D5).** `issue` containers depend only on image + env → infra → throws → HARD-ERROR → retry with a fresh stack. `attempt` containers mount the worktree and run branch code → **gate red**, with the container's log as the trace. Backwards, an agent that breaks the service bootstrap burns two fresh-stack retries reproducing the same failure and lands on NEEDS-HUMAN with an "environment" trace. Default is `attempt` — the safe side, since a container wrongly reused across attempts gates stale code. The mapping has to hold for the stack's whole life, not just its first second, so two liveness checks back it: a container with **no `readiness`** is still asserted alive after a grace interval (`podman run -d` exits 0 for an entrypoint that dies immediately, so otherwise a dead mail catcher passes bringup and every step that talks to it blames the branch), and the `issue` containers are re-checked **before every gate run** — a database OOM-killed at attempt 4 throws rather than reddening, so the fresh-stack retry does its job instead of burning the budget against a corpse. **That check has to be able to see a container that no longer EXISTS (#36),** which `podman inspect` cannot say: it exits 125 both for a removed container and for a podman that is merely unwell, so the one state that is conclusive evidence of death read as "could not answer" and was waved through — and every later step exec'ing into it then exited 125 and reddened the gate against the branch, the exact misblame the check exists to prevent, reached through the check. `podman container exists` (0 in any state, 1 for gone) is what separates them, asked only on the path where inspect already failed, so it costs nothing in the ordinary case and needs no matching on podman's prose, which differs per subcommand (`no such object` from `inspect`, `no container with name or ID … found` from `exec`). The point is to shrink "unanswerable", not to abolish it: a timed-out `exists` is still no evidence, since reading that as death would turn a slow host into a HARD-ERROR storm — and `exists` is asked **only when `inspect` exited non-zero on its own**, never when it timed out, because a wedged podman cannot answer the second question either and the second 15s would come straight off the readiness budget (`pollUntilReady` tests its deadline only *between* probes, so a doubled worst case doubles the overshoot and halves how many polls a 60s budget buys). Classification is table-tested through an injectable probe (`PodmanProbe`), which is the only way to reach a timed-out inspect or a SIGKILLed `exists` — the answers whose misreading *is* the storm — since no real podman produces them on demand. The check runs **once per gate run**, at the top, so a container removed between it and step N still reds that gate: the misblame is narrowed from every remaining attempt to exactly one, not eliminated. The two death states are reported differently because they imply different next steps — a stopped container still has a log to read, a removed one has no log and an operator question about who removed it. `throwIfDead` draws the same distinction during bringup, where the stake is only a misleading message (a removed container polled to its readiness deadline and reported "did not become ready").
  - **Nothing that shells into a container may hang.** The run holds the single-instance lock while the gate works and node's `execFile` has no default timeout, so an unbounded exec is not a slow gate but a run that never ends and never tears down. Readiness probes and `postReadyCommands` are bounded by the container's readiness budget, the calls sandbar makes *about* a container rather than through it (`logs`, `inspect`, `container exists`) by `LOG_READ_TIMEOUT_MS`, and the tcp probe carries a socket timeout (a dropped SYN yields neither `connect` nor `error`). Note `readinessTimeoutMs` alone does **not** give this: the poll loop tests its deadline only *between* probes, so one probe that never returns hangs forever inside a valid budget. Steps are bounded per step by `step.timeoutMs` (#26, default 15 min) — a lint step and a browser suite do not want the same ceiling and the consumer is the only one who knows which is which. **But the bound cannot be node's `timeout:` option, and that is the sharpest thing in #26:** node kills the child with SIGTERM, `podman exec` *exits 0* on SIGTERM, and node reports an error only for a non-zero code or a non-null signal — so the call **resolves**. A hung suite was a green gate, a hung `exec` readiness probe a container reported ready, a hung `postReadyCommand` a database reported seeded; the latter two had carried `timeout:` since #24 and neither had ever been able to fail. So `boundedPodman` owns the deadline, kills with SIGKILL, and `timedOut` is a flag the timer sets rather than anything inferred from an exit code. **Every** podman call in the module goes through it — including the teardown in `stop()`, where the same green-on-red made sandbar report a clean `pod rm` of a pod that was still running, under a comment insisting failures there are never swallowed. The create/destroy calls (`pod create`, `network create`, `run`, `rm`) get a much larger `CONTROL_TIMEOUT_MS` because they do real work and 15s would be a spurious bringup failure; they are bounded at all because `reapKilledStep` tolerates a failed remove on the grounds that the next gate run force-removes the container first, so an unbounded remove *there* would be #26's hang reached through #26's fix. Note the class of a control-plane throw is load-bearing: a flaked `pod inspect` raises a plain `Error`, never a `SandbarError` — `inner-loop.ts` rethrows `SandbarError` past HARD-ERROR, which would drop the issue for the cycle with no terminal, no comment and no label flip while leaving it queued. Validation rejects a non-positive, NaN or infinite `timeoutMs`, and the reason is the opposite of node's: the deadline is a `setTimeout` sandbar owns, so 0 and NaN fire on the next tick — every step killed before it runs — and Infinity never fires. A timeout is a **gate red, not a HARD-ERROR** (D5's argument: a suite that hangs is the branch's code, and a hang that is genuinely environmental recurs and exhausts the budget onto NEEDS-HUMAN with the same trace), carrying `exitCode: 124`, the step's name, the bound, and — per D9, and this is the case that needs them most, since a hang's own output is usually empty — the stack's container logs, collected *before* the reap below. **And killing the client reaps nothing:** the process keeps running inside the container (pinned against real podman, for the timer's SIGKILL and for the SIGTERM node sends on a maxBuffer overflow alike — so both kills reap). The only handle podman gives that is total, and that needs no `kill` binary in an image sandbar does not control, is the container itself — so `reapKilledStep` removes it, which is free for an `attempt` container (the next gate run recreates it anyway) and is followed by an immediate re-bringup for an `issue` one. Be precise about what that re-bringup prevents. Until #36 the answer was a red gate *against the branch*: `assertIssueContainersAlive` could not see a removed container at all, so every later step targeting it exited 125 and reddened, D5's blame mapping running backwards for a container sandbar itself removed. That check now catches it, which demotes the re-bringup from load-bearing to a worthwhile optimisation — the alternative is discarding a working stack and the rest of the issue's attempts on a HARD-ERROR, for a container sandbar knows exactly how to put back. The cost is more than re-running `postReadyCommands`: everything the container accumulated beyond its declared setup goes with it — a schema an earlier gate step migrated, rows an earlier attempt wrote — and a held `issue` container is exactly where consumers are invited to keep that. Still better than leaving a runaway inside it for the rest of the issue, or reporting a red the branch cannot act on. A recreate that **fails** is the single exception to "a killed step is always a gate red": the bringup error wins, the step name and D9 logs are discarded, and the run takes a HARD-ERROR. There is deliberately **no** bound on the gate as a whole: a run stops at the first red, so one hung step costs one step's bound, and a second number could only kill a legitimately slow run without being able to name what it killed. The residual — N slow but *passing* steps may run for the sum of their bounds — is finite and computable from the config. The `log` follower is the one thing here with no deadline at all, and its bound is a **kill, not a timeout**: `podman logs -f` is unbounded by design, so `waitForReady` owns it in a `finally` and kills it on every path out. Deliberately not registered with `onCleanup` — that registry never forgets an action, so one entry per container per bringup would grow without limit. The signal story is weaker than "covered transitively" and is stated exactly in the module header: SIGINT/SIGTERM work (cleanup removes the pod, and a follower whose container is gone exits ~1s later), but SIGKILL, SIGHUP (untrapped) and a teardown that throws early all orphan a follower on a quiet container, which blocks in read and outlives its parent. It holds no lock and no podman resource, so it is a stray process, not a leak that blocks the next run.
  - **`--userns=keep-id` is impossible in a pod** (podman refuses to combine them) and `--user 1000:1000` maps to a *subuid*, not the invoking user. Container root under rootless podman maps to the invoking user, so an image behind `mountWorktree` must run as root **or** as the host uid. Enforced before the run by `checkWorktreeImageUids`, which resolves the uid **empirically** (`podman run --rm --entrypoint id <img> -u` — `run <img> id -u` would pass `id -u` as *arguments* to the image's own ENTRYPOINT and answer a different question) rather than parsing `.Config.User` — a non-numeric `USER agent` is exactly the case an inspect-based check skips and that then fails as a silent EACCES mid-gate. `config.images[].buildArgs` is the escape hatch for aligning a genuinely non-root image at build time.
  - **`log` readiness FOLLOWS the log; it does not re-read it (#31).** The obvious implementation — `podman logs` every 500ms — is quadratic in the log's size (~120 full reads of a growing log across a 60s window, on exactly the frontend dev server someone gives a `log` readiness to), and past `MAX_BUFFER` node kills *every* read, so the container can never go ready **even after the pattern is printed** and the timeout says `logs unavailable`, which reads as "the pattern never appeared" and sends the operator to the wrong place. Following also reports a genuine podman failure as what podman said — the follower keeps a bounded tail of its stderr and quotes it on a non-zero exit — instead of flattening it into that same string. Note `podman logs` writes podman's own diagnostics and the container's stderr to one fd, so that tail is whichever spoke last, and the readiness pattern is matched against both. **A followed stream splits a line wherever the driver likes** — an unterminated partial line arrives as its own chunk under `k8s-file` (journald buffers per line, so the driver is pinned explicitly in `gate-stack-podman.test.ts`) — so `scanChunk` carries the last `pattern.length - 1` bytes of each stream across chunk boundaries; without it a pattern written as `PAR` then `TIAL` is missed forever, the new silent failure that makes the cheap `--tail N` fix unacceptable. That carry is sound **only because a followed stream is delivered once, in order**: the other candidate, a rolling `--since` cursor, must re-read an overlap window to avoid losing lines (the cursor has to be captured *before* the read), and re-delivery makes `carry + chunk` manufacture matches that were never in the log. Streams are scanned **separately**, not concatenated — podman keeps container stdout and stderr apart, so joining them invents a seam no reader of the log would see. **Decoded through a `StringDecoder`, not per-chunk `toString`** — a chunk boundary is a *byte* boundary, and decoding chunks independently replaces both halves of a split multi-byte character with `U+FFFD` before the carry ever sees them; `✓ Ready in` (Next.js) and `➜  Local:` (Vite) are exactly the patterns this feature invites, so that would be a silent miss reported as "pattern not in log yet". A follower that dies is **restarted** rather than latched unready (`podman logs -f` also ends when the container does): re-reading from the start is idempotent for a substring test and the poll interval rate-limits it. `throwIfDead` ends the wait for a container that *exited* and, since #36, for one that was **removed**; what still restarts a doomed follower every poll to the deadline is `unknown` — podman refusing to answer, or answering that the container is there while `inspect` still cannot say whether it is running — because that is deliberately not evidence of death. `deathNote` is what keeps that legible, appending the follower's death count and podman's last words to the timeout rather than letting it read as the consumer's pattern never appearing.
  - **`tcp` readiness is probed from the host**, through a loopback-only `127.0.0.1::<port>` publish with a podman-assigned ephemeral host port (so concurrent stacks can't collide). Probing inside the namespace would need a shell and a socket tool in images sandbar doesn't control — and mail catchers and scratch-based services, the ones that most need a TCP probe, have neither. **A bare connect is a green-on-red**: the rootless port forwarder accepts at the host and asks the backend afterwards, so `connect` succeeds against a pod with nothing listening. The probe therefore requires the socket to stay open for `TCP_SETTLE_MS`; a dead backend and a mid-initialisation mariadb are both closed ~190ms after connect, a serving one is not. Pinned in `gate-stack-podman.test.ts`.
  - **A red gate carries every container's log tail** (D9) — when a browser step fails because the backend is 500ing, the diagnosis is in a container the step never touched. It rides in its own `GateResult.containerLogs` field rather than on `stderr`, and that separation is load-bearing: `summarizeGateFailure` collapses lines sharing a timeout signature, and a service log is full of near-identical lines, so folding them in would have it collapsing text that was never one test run. Callers summarize the step output, then append.
  - **`config.sandboxImage` is required**, and `config.images` (default `[{tag: sandboxImage, containerfile: "Containerfile"}]`) is what sandbar builds; `stdinContext` builds with no context at all. Every *other* referenced image must already be pulled — preflight refuses with the exact `podman pull` line rather than pulling, so no run does silent network work at startup.
- **An image that bakes dependencies is a function of the BRANCH, and the tag could not say so (#37).** `ensureImages` skipped any entry whose tag existed, and the build context is the host checkout because no issue worktree exists that early — so exactly the image #24 was built to serve (one carrying `node_modules` or a browser, so a gate attempt installs nothing) gated every branch against the *source* branch's dependencies. Both directions are silent false verdicts: a branch that adds a dependency reds with a module-not-found nobody can reproduce and can spend the whole attempt budget onto `agent-stuck` for a config artefact, and one that removes or downgrades a dependency greens against something it deleted. Under `mergeMode: "verified"` it resurfaces as a mysterious red on the integration branch after the local gate went green, CI having built the same images from the branch under test. The fix keeps the consumer-declares/sandbar-owns split: `images[].rebuildOn` names the paths the image is a function of, `image-inputs.ts` hashes them — **plus the Containerfile's own bytes** (an image is a function of its recipe) **and the entry's `buildArgs`** (config the tag-only key also ignored) — and that hash is the real cache key in two places. At startup the hash is recorded as an image **label**, so a tag left from before the operator pulled new deps is rebuilt rather than reused for its name; and before **every gate run** the gated worktree is hashed, with a match using the base image and a difference getting a content-addressed variant tag (`naming.ts`) built from *that worktree*.
  - **Per gate run, not per issue, and that is the whole correctness argument.** An issue branch starts identical to source, so resolving once at `startStack` would answer "unchanged" for the reachable case: the agent adds the dependency during attempt 1 and gate-1 runs immediately after. `startStack` therefore brings issue containers up with the images config *names* — which is safe because nothing of the branch runs there (`resolveGateStack` refuses `lifecycle: "issue"` on an un-held worktree-mounting container, and a held one's entrypoint is `sleep infinity`) — and the first `runGate` recreates whatever the branch moved. Cost of getting it wrong the other way: putting a per-branch build outside a gate run leaves it only a throw, i.e. HARD-ERROR, i.e. two fresh-stack retries reproducing the same broken lockfile and an "environment" trace.
  - **An unbuildable image is a gate RED, not a HARD-ERROR** — D5's argument, one level up: the image is a function of the branch, so a lockfile that does not install is the branch's to fix. It arrives as `failedStep: "image:<tag>"` carrying the build's own output, which is why the per-branch path *captures* the build (the base build inherits the console instead: a cold multi-minute build should show progress, and its failure halts the run in front of the operator watching it). For the same reason **an `issue` container recreated because its image changed reds rather than throws** — a deliberate exception to D5, whose "depends only on image + env" is exactly what stops being true when the branch authors the image. That recreate also **moves `assertIssueContainersAlive` after it**, which is not cosmetic: `bringUp` removes before it creates, so a recreate that fails leaves the container *gone*, and checking aliveness first would report sandbar's own removal as "it came up once and something killed it" — an infra HARD-ERROR blaming the environment for an image the branch authored, reached through the check that exists to prevent misblame. `running.map` is therefore updated only after the recreate succeeds, so the next gate run retries it and reds again instead. What the check still catches is unchanged: a container nothing touched that died on its own between gate runs.
  - **The image resolution runs after the dirty-tree refusal** (a tree that gets no verdict should not pay for a build) and before any container is created. Variant tags carry the run scope *and* the content hash. The hash makes reuse decidable — but the tag holds only its first 8 hex, so reuse is decided by reading the **full** fingerprint back off the image's label, not by `image exists`: the name alone is a 32-bit key, and a leftover tag from a crashed run in this scope would be accepted on it. The in-flight map stops two parallel issues racing one name, and it **evicts a rejection** — deduplicating work in flight is not an argument for caching a failure, and cached, one transient registry 5xx is a dead end rather than a bad verdict (the fingerprint does not move unless the agent touches the lockfile again, so every remaining attempt re-throws the same stale error, no build is ever retried, and the issue parks with a trace telling its author their dependencies do not install). The scope is what makes a crash's leftovers reapable, and that is *implemented*, not merely asserted: `sweepBranchImages` reclaims this scope's variants at startup and is blind to every other scope, because the run-end removal is an `onCleanup` action and so does not survive SIGKILL — and these are the largest things sandbar creates.
  - **`reapKilledStep` is the one bringup that neither precedes nor follows a `running.map` update, and recreating from the declared image there is #37 reintroduced through its own fix.** A timed-out `issue` container put back on the base image while the map still says it is on the branch's variant is never seen as stale again, so every remaining attempt gates against the source branch's dependencies — silently, green included. It therefore recreates through `withImages(..., ctx.running.map)`: the map **as it stands**, since this is a restore of what was running and not a new resolution (re-resolving mid-red would pay a build for a gate whose verdict is already decided). Pinned by a podman test that fails on the one-word regression; an `ok`-only or id-only assertion passes with the bug present.
  - **The build is bounded and reaped.** `images[].buildTimeoutMs` (default 45 min) is a deadline sandbar owns, killed with SIGKILL and flagged by the timer rather than inferred from an exit code — the same discipline `boundedPodman` uses, and per entry for the same reason `step.timeoutMs` is per step. It exists because a `rebuildOn` build runs *inside* a gate run, from a recipe the implementer agent wrote, while the run holds the single-instance lock; unbounded it is not a slow gate but a run that never ends. Live builds are tracked in one module-level set with a **single** `onCleanup` entry (that registry never forgets an action), so a signal cannot leave a `podman build` running detached to apply a tag `builtTags()` never saw.
  - **D3 is re-asked for anything the branch builds.** The Containerfile's own bytes are in the fingerprint, so a branch is explicitly free to change the recipe's `USER` — and the startup check runs once over the *declared* images and would never see it, leaving a silent mid-gate EACCES, the one failure D3 exists to convert into a refusal. A freshly-built variant behind a worktree-mounting container is probed before any container gets it, and a bad uid is an `ImageBuildError` → gate red, because the branch authored the change. A *reused* variant is not re-probed (it was probed when it was built), and an image no worktree-mounting container runs is never probed at all — widening it would refuse a perfectly good mariadb on uid 999.
  - **`rebuildOn` is validated into non-inertness, because inert is the bug.** Paths are repo-relative with no `.`/`..`/empty segment, must sit **inside the containerfile's own directory** — that directory is the build context, so a path outside it can never be `COPY`d and the image cannot be a function of it, which would rebuild on every change and produce a byte-identical image (the README's own first example was that config) — must **exist in the host checkout** (a typo matches nothing in every tree, compares equal everywhere, and silently restores the pre-#37 behaviour), cannot combine with `stdinContext` (no context, so nothing in the repo can enter the image) or with an absolute `containerfile` (the rebuild re-roots at the worktree), and must be on an image some `gateStack` container runs. The **agent sandbox is deliberately not a use**: its image is resolved once, when the sandbox is created, before the branch exists — and the agent can install into its own sandbox, so a stale layer costs it a command, not a verdict.
  - **The fingerprint encoding is fussy on purpose** — a hash two trees can share is a false verdict wearing a hash. Declared paths are sorted (a property of the set, not of the writing order), every record is length-prefixed (otherwise `a="b", b=""` and `a="", b="b"` stream identically), a directory is walked in sorted order with every entry contributing its relative path (so a file moving between two hashed directories changes it), a symlink contributes its target string rather than the bytes it points at (following it hashes one file twice or leaves the root), and an absent path contributes an absence marker (so a deleted lockfile and an empty one differ). Files are streamed, since `rebuildOn` accepts a directory.
- **A gate verdict is about a COMMIT, so the tree is asserted ≡ HEAD (#24 D1).** `dirtyWorktreePaths` (`git-ops.ts`) gates both entry points: the inner loop reads it after every implementer attempt and the SM routes `COMPLETE` + dirty to another attempt with "commit your work" (no stack bringup paid), and `stack.runGate()` re-checks it so gate-2 in the merger worktree is covered when the resolve agent leaves edits. Deliberately **refuse, not clean**: `git clean -fd` would delete exactly the set this reports — untracked, non-ignored files, overwhelmingly a forgotten `git add`. A materialized-commit tree was rejected too: build artifacts are gitignored and live *inside* the mounted tree, so a second tree costs a cold build every attempt (~768M of ext4 copying per issue for outdoor) for a verdict identical to the assert's. **Corollary on consumers:** a gate step must write only into gitignored paths, or its own exhaust is reported as uncommitted work every attempt until the budget dies — and when an attempt comes back with the **identical** dirty set, the loop stops there with `NEEDS-HUMAN cause: "uncommittable-worktree"` rather than spending the rest of the budget on a set the agent has already shown it cannot clear.
  - **The `--porcelain` read pins `status.showUntrackedFiles=normal` on the command line.** A bare `git status --porcelain` honours that setting, and `no` is common in large repos — it reaches a per-issue worktree from `~/.gitconfig`, `$GIT_CONFIG_GLOBAL`, or the repo's own `.git/config`, which every linked worktree shares. Inherit it and a forgotten `git add` reads clean: the gate mounts files in no commit, goes green, and the merger lands a branch that does not contain what was tested. Both D1 entry points go blind together, so gate-2 does not catch it. Same pin in `agent-sandbox.ts`'s `hasUncommittedChanges`, where it decides whether a worktree is preserved or deleted.
  - **The merger commits what `npm install` dirties.** `npm install` runs in the merger worktree between the merge and gate-2, and rewrites tracked `package-lock.json` exactly when merging two branches that both touched dependencies — which D1 would then refuse with a `worktree-clean` red that never mentions npm, while each resolve retry re-ran the install and re-created it. The update belongs in the merge result, so it is committed — but **only when the tree was clean beforehand**, since a dirty tree on entry means the resolve agent left edits, which is the case gate-2's check exists to catch.
- **And the commit has to be on the ISSUE BRANCH, which a clean tree does not prove (#27).** D1 asserts tree ≡ HEAD; `headMismatch` (`git-ops.ts`) asserts HEAD ≡ `refs/heads/<branch>`, read beside `dirtyWorktreePaths` after every implementer attempt. An implementer that commits on a detached HEAD — or on a scratch branch of its own — leaves a **clean** worktree, so gate-1 mounts a tree containing the work and goes green while the merger, which only ever reads the branch, cannot see any of it. **Be precise about how far that gets, because #27's own description is of the shape that is currently unreachable.** Commit capture reads `refs/heads/<branch>`, so an agent that detaches on its *first* attempt keeps `commitsAccumulated` at 0 and `parsePromise` already downgrades every `COMPLETE` — it never reaches a gate, and instead burns all eight attempts on "you made no commits this run" before dying as `NEEDS-HUMAN gate-red` naming a gate that never ran. The reachable bug is the ordinary review round-trip: attempt 1 commits on the branch, the reviewer asks for changes, attempt 2 writes the fix on a detached HEAD — `commitsAccumulated` is already positive so `COMPLETE` stands, gate-1 goes green on a tree containing the fix, the reviewer approves, and the merger lands **attempt 1's commits without it**. A green gate certifying a tree the branch does not contain, and a partial land presented as a complete one. Handoff comments must therefore never claim "no gate ran", "nothing merged" or "the branch never moved" — all three are false on the path that actually reaches the terminal.
  - **The check reads `git rev-parse --symbolic-full-name HEAD`, never `git symbolic-ref -q HEAD`.** The latter looks like it distinguishes detached (exit 1) from broken (exit 128) by exit code, but `-q` suppresses only git's *own* message and anything else on stderr still comes through: with `GIT_TRACE=1` in the operator's environment a detached HEAD exits 1 with ~80 bytes of trace, an exit-code-plus-empty-stderr test rethrows, and the mismatch is reported as an infra **HARD-ERROR** — two pointless fresh-sandbox retries, then a terminal that deletes the branch and posts no comment. An env var re-hiding exactly the failure the check exists to expose. `rev-parse` has no such fork: inside a valid repo it exits 0 either way and prints the literal `HEAD` when detached, so non-zero is unambiguously a real failure and is left to throw. It is also the command `prompts/implementer.md` tells the agent to verify itself with, so the check and the instruction are the same question. The branch-tip read is null-on-missing (a missing ref is data); the **HEAD sha read throws**, because it is the whole payload.
  - **Symbolic ref, not `rev-parse HEAD == rev-parse refs/heads/<branch>`** as the issue proposed: a sha comparison accepts a HEAD detached exactly at the branch tip, which is one commit from the bug while the corrective instruction is already identical.
  - **One correction, then `NEEDS-HUMAN cause: "off-branch-head"`.** The asymmetry with `uncommittable-worktree`'s same-set rule is that there is no partial progress here — either HEAD is the branch or it is not, and the fix is two mechanical commands spelled out in the re-prompt. The test is on the previous attempt being off-branch, not off-branch *in the same place*: a new detached sha is not progress, and comparing positions would let an agent grind the whole budget by committing again. It fires on `COMPLETE` **and NO-SIGNAL** — every attempt spent off-branch strands more commits, and off-branch otherwise reads as `commitsAccumulated === 0`, so the agent is told it "made no commits" when it made several.
  - **Neither the re-prompt nor the orchestrator moves the ref.** `git branch -f` is safe only when the branch is an ancestor of HEAD; forcing it otherwise silently drops whatever the branch already had, trading a visible failure for an invisible one. So the agent is told to `cherry-pick`/`merge` unless it has checked — and because that rescue moves the ref *without creating a commit*, `agent-sandbox.ts` anchors the commit range at `refs/heads/<branch>` rather than at the worktree HEAD. With HEAD on the branch the two are the same commit; off it, the HEAD anchor makes a correctly-executed rescue count as zero commits and sends the agent the very message this check exists to stop sending.
  - **NEEDS-INFO and NEEDS-UI-PROTOTYPE are exempt from the correction, but not from the reporting.** Re-prompting them would risk spending the budget on a question the agent had already formed and would swap a precise handoff for a generic one. But "they land nothing anyway" is not a reason to stay quiet: commits are counted on the branch, so an off-branch escalation reports `hasCommits: false`, and finalize then deletes the branch and posts only the `<ui-impact>`/`<questions>` block — the detached sha would exist in no comment, no ref and no log, and go at the next `git gc`. That is #27's own failure arriving through the terminal the check chose not to guard. Both terminals therefore carry the `HeadMismatch`, and `STRANDED_COMMITS_NOTE` appends it to the comment. Its prose **branches on `headRef`**: a detached HEAD is unreachable and on gc's clock, so the reader is told to `git branch <rescue-name> <sha>` now; a scratch branch is a real local ref that survives worktree removal and gc, so telling that reader their work is about to be pruned would send them to rescue something in no danger.
  - Inner-loop only: the merger worktree is detached *by design*, so unlike D1 this has no second entry point in `stack.runGate()` — and needs none, since nothing runs between the implementer result and gate-1.
  - **Known, pre-existing and NOT fixed here:** the `needs-human` arm pushes the branch unconditionally, so a stuck issue whose agent never committed publishes an empty `sandbar/issue-N-*` ref to origin that nothing ever deletes. `off-branch-head` makes it more likely but does not introduce it — `gate-red` with zero commits does the same — and the fix needs `hasCommits` on a terminal that does not carry commits today.

- **Branch naming is load-bearing.** `sandbar/issue-<n>-<kebab-slug>` (prefix in `src/naming.ts`) — the preflight cleanup, orphan sweeper, and worktree path computation (`worktreePathFor`) all rely on this prefix. Don't change it casually.
- **Verified merge mode is about independence, not coverage (#22).** The local gate and the code under test share one process, one podman, one image cache, one env file and one author — nothing disagrees. CI is a second, differently-authored implementation of "does this work". So a coverage gap belongs in `gateStack.steps` (cheaper, per-attempt); `mergeMode: "verified"` exists for the thing expanding the gate can't buy. Its non-negotiable invariant: **no unknown verdict ever lands** — and "unknown" includes a partial read, an unsettled snapshot, a skipped job, an unfinished check nobody named, and a check that was never reported, not just a pending one. `integrationBranch` is a remote-only scratch ref (never a local branch: it is pushed as `HEAD:refs/heads/<b>` from the detached merger worktree, so the `refs/heads/sandbar/issue-*` glob the preflight cleanup uses can't reach it, and `resolveMergeMode` rejects a name inside that namespace). It must also *start* with `sandbar/`: the ref is force-pushed every round, so pointing it at a branch someone else uses would destroy that branch on cycle 1, and the lease is no defence against that.
- **Issue branches seed from `origin/<sourceBranch>`,** not local. The preflight emits a soft warning when local is ahead of origin because per-issue worktrees won't see unpushed work.
- **Single-instance lock.** `src/lock.ts` uses `proper-lockfile` for the atomic acquire plus a `run.pid` sidecar for stale-PID takeover. Don't try to run two sandbar processes against the same workdir. Two against *different* workdirs is supported since #28 — the lock's workdir is also what derives the podman resource scope, so the two mechanisms cover the same partition by construction. **The takeover has to remove proper-lockfile's lock DIRECTORY itself, not call `lockfile.unlock` (#32).** `unlock` resolves against a module-level registry of locks *this process* holds and returns `ENOTACQUIRED` for anything else, so against the only holder a takeover can ever face — a dead **other** process — it was a guaranteed no-op, swallowed, leaving recovery from a crashed run entirely to proper-lockfile's 10s mtime staleness, i.e. to the timer the sidecar exists to skip. It succeeded in exactly one arrangement, the same process locking twice, where the recorded pid is our own and therefore alive and the takeover is never reached — which is also the arrangement a same-process *test* constructs, so the first version of `lock.test.ts` certified the broken path as working. Anything pinning the takeover must cross a process boundary or it is pinning the bug. Removing the dir is gated on positive evidence the holder is dead (`process.kill(pid, 0)` → ESRCH); an unreadable sidecar and pid `0` both fail **closed**, and a removal that fails leaves the sidecar alone because it is the next launch's only evidence. **The lock is taken before preflight, not after (#32).** Preflight is not a read-only phase: it fetches, and `deleteMergedIssueBranches` runs `git branch -D` over every `sandbar/issue-*` branch it finds merged — which made the one operation in startup that mutates the repo the one operation the lock did not cover, reached by both of two racing launches before the loser was turned away. (The branch *classification* is not part of that argument: a concurrent run's in-flight branches map to issues still open and still `ready-for-agent`, since the label flips happen in Phase 4, so they read `resumable` rather than a spurious `unmerged`.) The ordering costs nothing to reverse — `acquireLock` is `retries: 0`, so there is no lock *wait* for a fail-fast config error to duck under; a second launch simply hears "another sandbar is running" first, which is the actionable complaint of the two. Preflight's `process.exit(1)` now `await runCleanup()`s first, which recovers the **sidecar** rather than the lock — proper-lockfile's own exit handler rmdirs held locks even on a bare `process.exit`. Preflight still precedes the orphan sweep and every container operation, which is the dependency those rely on for a working runtime.
- **Promise-token contract.** Agents signal state with a single `<promise>TOKEN</promise>` tag. Implementer: `COMPLETE` (which also means *the worktree is clean* and *HEAD is `refs/heads/<branch>`*) | `NEEDS-INFO` (paired with `<questions>`) | `NEEDS-UI-PROTOTYPE` (paired with `<ui-impact>`). Resolve-loop: `COMMITTED` | `ABANDON` (paired with `<reason>`). Anything else is a no-signal — the loop re-prompts. The orchestrator gates *between* attempts; the agent never decides "this is green".
- **Verdict-token contract.** The reviewer emits a single `<verdict>APPROVED|CHANGES-REQUESTED</verdict>` tag (parsed by `verdict-parser.ts`). Missing or malformed token defaults to `CHANGES-REQUESTED` — convergence relies on the bar being sharp, i.e. on the coding standards (the built-in `prompts/coding-standards.md`, plus any project `CODING_STANDARDS.md` that extends them) being precise enough to be deterministic, not on round-trip retries. The reviewer is read-only: prompt instructs it not to modify the branch, commit, push, or run gates.
- **Prompt prose lives in `prompts/*.md`, not in code.** `src/prompts.ts` loads templates and does `{{placeholder}}` substitution; `prompt.ts` and `resolve-loop.ts` load them into module-level consts at import and fill the placeholders. Keep substantive instructional prose in the markdown files; only structural scaffolding (headings, code-fence wrapping, data interpolation, which optional block to include) stays in TS. The `prompts/` dir sits beside `src/`/`dist/` so the same `../prompts` path resolves from both, and is shipped via package.json `files`.
- **Logs are append-only and unbuffered** (`src/logs.ts`). Crash-safe by construction; don't introduce in-memory buffering.

## When making changes

- **Strict TypeScript** — `strict`, `noUncheckedIndexedAccess`, `noImplicitOverride`. Array/Map lookups are `T | undefined`; handle accordingly.
- **`*.test.ts` files are excluded from `tsc`** (see `tsconfig.json`) but checked by `vitest`. The strict type-checking gate is on production code only.
- **Always import with `.js` extensions** even from `.ts` files — NodeNext resolution.
- Module headers (the long comments at the top of `src/*.ts`) are the authoritative architecture notes per module. Update them when behavior changes; future Claude reads them first.
